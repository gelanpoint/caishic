## 一、T-001 质量阈值拍板

### 1.1 继承基线项（照 `docs/standards/nfr-baseline.md` 的 **P2 列**，无偏离）

| 阈值项 | 取值 | 依据 |
| --- | --- | --- |
| 接口响应时间 | p95 < 500ms、p99 < 2s | `nfr-baseline.md` §2.1 P2 列 |
| 慢查询 | 单查询 > 500ms 告警、> 2s 视为缺陷 | 同上 |
| 页面首屏加载 | < 2s（本机访问，比"常规办公网络"更宽裕 → 不标偏离） | 同上 |
| 依赖漏洞修复时限 | 高危 24 小时内、中危 7 天内 | `nfr-baseline.md` §2.3 P2 列 |

> **依赖漏洞时限的限定**：本期运行期依赖仅 `Flask` 一项、**不引入漏洞扫描工具**。
> 该时限是「**发现漏洞后的响应约定**」，**不是自动扫描门禁** —— 不许把它写成门禁。

### 1.2 基线委托本文件 / 基线无此项 —— 父代理裁定值

**背景（前次核查结论）**：`nfr-baseline.md` 中**只有**响应时间、慢查询、依赖漏洞时限有数字；
**测试覆盖率是基线把它委托给本文件**（基线原文："覆盖率阈值见 `docs/standards/quality-gates.md`"）；
**圈复杂度 / 单文件行数 / 单 PR 行数 / 测试金字塔 / 重复率在基线里根本没有条目**。

| 阈值项 | 裁定值 | 度量方式与说明 |
| --- | --- | --- |
| 测试覆盖率 | **涉钱路径行覆盖率 ≥ 90%**；**整体行覆盖率 ≥ 70%** | 只能用 Python 标准库 `trace` 度量 → **只有行覆盖、没有分支覆盖**。因此该值低于常见 P2 口径（80%/95%）属**诚实取值，不是放水** —— 此说明必须保留在文件里，使数字可被独立复核 |
| 圈复杂度 | 单函数 ≤ 10（McCabe） | **本项未全自动**：人工抽查涉钱路径 + `ast` 自写脚本粗查。**该标注必须保留** —— 不标会让后来者误以为它在自动跑 |
| 单文件行数 | ≤ 400 行 | 可用标准库脚本自动统计（可自动化） |
| 单 PR 改动行数 | ≤ 400 行（超出须拆分） | `git diff --stat` 可自动统计（可自动化） |
| 测试金字塔比例 | 单元 : 契约 : E2E ≈ **5 : 3 : 2**（按用例数） | 按测试文件分组脚本统计（可自动化） |
| **重复率** | **不设数值阈值** —— 改为「**人工抽查关注项，不设门禁**」 | **理由**：无自动化工具且不引入依赖；**一个无法自动验证的阈值就是又一个假指标**。本项目已依次打掉 `AC-006`（不可判定）、"价签更新率"（系统感知不到）、"日均智能秤交易占比"（分母拿不到）—— 重复率不应成为第四个。**此理由必须写进文件** |

### 1.3 红线项：**二进制判定，不用百分比**

> **写法本身的含义**：`"身份证字段出现率 0.1%"` 是**逻辑上错误**的表述 —— 允许 0.1% 就等于允许出现。
> **零就是零。** 下列五项一律写成「必须 0 次 / 100% 通过」。

| 红线项 | 判定 | 对应 |
| --- | --- | --- |
| 涉钱路径对账断言「订单总额 = 支付流水 = 分账明细」 | **必须 100% 通过（失败 0 例）** | `AC-003`、`REQ-020` |
| 身份证 / 银行卡字段扫描（请求体 + 响应体 + 持久化记录 + 静态扫描） | **零命中** | `AC-012`、`NFR-012`、宪法 §2 |
| 补传成功后本地副本 | **必须为空**（`payload_json` 为空 + `purged_at` 非空 + `data/` 无残留暂存文件） | `NFR-013` |
| 绝不静默丢弃交易 | **零发生**（达阈值仍接受；暂存失败必须报错且不得标记成功） | `NFR-014`、`REQ-016`、`REQ-030` |
| 静态资源外部域名 | **零个** | `REQ-025`、`AGENTS.md` §3 硬要求 4 |

## 二、依赖范围裁定（原阻塞 T-007）

### 2.1 问题

`constitution.md` §1 的依赖白名单为「`Flask` + Python 标准库」。
而测试与静态检查工具链（`pytest` / `coverage` / `radon` / `pylint`）**一个都不在白名单内** → `T-007` 开工即撞宪法。

### 2.2 裁定：**修正条款表述，而非把测试框架塞进白名单**

**关键判断**：宪法 §1 的白名单管的是**运行期技术栈**（系统用什么构建、演示机上要装什么）。
`pytest` / `coverage` 是**开发期工具**。把两者混在一条白名单里，**本身是条款的表述缺陷** ——
因此正确动作是**修条款**，不是破例。

**落盘要求**：

1. 新增 **`docs/adr/0004-依赖范围界定-运行期与开发期.md`**（状态 `已接受`）：
   明确白名单约束**运行期**依赖；**开发期工具单列，不进 `requirements.txt`、不装到演示机**；
   照 ADR 规范写偏离/澄清理由、代价、重新评估触发条件；
2. **`constitution.md` §1 修订**（属 §6 人工评审范围，**AI 只能起草与提议**）：
   - 白名单条目补一句「**本白名单约束运行期依赖**」；
   - 新增小节「**开发期工具**」：`pytest`、`coverage`（以实际选用者为准）**仅限开发与测试期**，
     **不得出现在 `requirements.txt`、不得被 `run.py` 或 `app/**` 引用**；
   - 修订需在 `docs/PROJECT-STATE.md` 留「宪法修订记录（含批准依据）」，**不许悄悄改**；
   - 客户接口人（真人负责人）另行报备。
3. **依赖清单分离**：`requirements.txt`（运行期，**只有 Flask**）与 `requirements-dev.txt`（开发期）；
4. **机械检查（必须带灵敏度验证）**：用 `ast` 扫描 `run.py` + `app/**` 的 import，**确认不含任何开发期依赖**；
   **故意在 `run.py` 里 `import pytest` → 检查必须变红**，移除后恢复绿；
5. **端到端实证**：在**只装了 `requirements.txt` 的干净环境**里，`python run.py` **必须能起来**。
   这才是「演示机只装 Flask」的真凭据，不是口头承诺。

### 2.3 保留回退权

若落地时发现 `ast` 扫描或干净环境验证的**自身成本**超出预期，
**执行 Agent 应立即上报，退回「全部用标准库（`unittest` + `trace` + `ast`），零新增依赖」方案** ——
那时会有实测依据，不是预判。
