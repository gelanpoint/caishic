# 菜市场数字化交易与佣金系统 —— 提交说明

## 一、这个项目在解决什么

农贸市场数字化在过去几年有一个通行做法：**给商户装智能秤，然后从交易里抽佣**。
我们为此做了实地调研，把 26 条结论和 30 处来源链接（28 个独立来源）整理在 `docs/调研报告-现实情况.md`。

调研的结论不太好看：

- **抽佣这条路有三例仓库内可核的失败**：成都温江红桥农贸市场（2‰/笔，最后全额退还，负责人被约谈）、赣州龙南虔锦智慧市场（商户搬走，佣金收不到一分）、南宁 7 个市场（2012–2015，POS 收购全线停止）。唯一活下来的是**向买方收费**的温州菜篮子批发市场（**这是调研事实；说明见本节末的"如实说明"第 1 条——本系统并未实现向买方收费**）。
- **商户拒绝的真正原因不是钱**。南宁商务局的原话是：**"部分经营户之所以屡屡拒绝，说白了就是这些人今后不能再搞'八两秤'了。"**
- **政府免费送设备也不够**。绵阳免费送了智能秤，但"维修也不及时"，设备积灰弃用；**衡阳（邮政免费配秤）、杭州（统一配秤并统一检定维修）**的做法才是活的。
- **钱其实不来自商户**：郑州 14 个市场 1000+ 商户、1.4 亿投入；达川区交通银行 3 年 200 余万；建行大连、上海宝山都有银行或政府付费的案例。

**所以我们的方案把方向反过来：堵住作弊，而不是让商户多付钱。**

## 二、方案的核心判断

| # | 判断 | 依据 |
|---|---|---|
| 1 | **不向商户抽佣** | 三例失败；系统仍实现可配置的佣金引擎（主链路要求），但明确论证"为什么不该收这笔钱" |
| 2 | **硬件由市场开办方承担，含维护与统一检定** | 绵阳（免费但无维护 ⟶ 积灰弃用）vs 衡阳/杭州（免费+统一检定+免维护 ⟶ 存活） |
| 3 | **秤是唯一的物理锚点** | 流程强制"选品 → 称重 → 计价"，系统不接受手工输入重量和金额 |
| 4 | **顾客扫码页只显示"有真实来源"的字段** | 字段白名单，多一个即失败；调研里顾客说"扫过好几次空码、无效信息之后，再也不信这个标签了"——**信任是一次性的** |
| 5 | **验收看使用率，不看装机量** | 装机量口径下"维护投入"的考核收益为 0——这正是"设备装完积灰也能通过验收"的机制来源 |
| 6 | **离线可补传、绝不静默丢弃** | 暂存阈值是**告警线不是上限**；补传用幂等键，重复补传记审计日志且不阻断后续 |
| 7 | **默认配置选非 AI 秤档** | 有真实报价区间；功能最多最贵的那档不是默认 |

**范围声明**：`spec.md` §6 明确列出 **11 条"不做"**（含外送、真实硬件/支付对接、多市场多租户、权限体系、电子价签、发票、会员营销、顾客端 App 等），每条都写明依据。

## 三、交付物与怎么验证

**技术栈**：Python 3.11+ / Flask / 标准库 `sqlite3` / 纯静态前端（无构建、**无 CDN**、无外部字体图标）/ 原生进程。
**运行期依赖只有 Flask。** 断网可跑。

**跑起来**：

```
Windows：双击 start.bat       Linux/macOS：./start.sh
```

启动后自动建库并导入种子数据（幂等），打印**本机局域网 IP、两个入口地址、数据文件路径**。

**演示主干（对应"Demo 跑通主干"）**：

```
秤端点图标选品 → 称重 → 自动计价 → 收款（现金 / 收款码，都进支付流水）
顾客扫码 → 看摊位信息 + 本笔明细 + 本摊标价一致率
改价（收款前）与退货（反向冲正、重复提交只冲减一次）
离线开关 → 暂存 → 补传 → 待补传归零
运营端：佣金口径 / 日终聚合 / 结算单 / 对账 / 使用率指标 / 审计日志
```

**现场三种降级方案都在**：同机双窗口（无 WiFi 时）、局域网手机真机扫码、端口被占用时按提示换端口。
逐步骤的演示脚本见 `docs/演示脚本.md`。

**规格完备性**：33 条功能需求 / 24 条验收标准 / 14 条非功能需求 / 31 个 HTTP 端点（含 14 个错误码）/ 19 张表 25 个索引。
`specs/market-trade-flow/` 下有完整的发现过程（`discovery.md` 含 `D-01`~`D-14` 决策表与被否方案的理由）、规格、接口契约、数据模型与任务分解。

## 四、AI Coding 与验证过程

**这套系统由 AI Agent 分批实现**，过程留痕在 `AGENTS.md`（红线 `RL-1`~`RL-9`、命令、演示硬要求）与 `docs/PROJECT-STATE.md`（逐批次实测证据、四个检查点签署记录、未决问题台账）。

我们坚持的三条做法：

1. **每个"检查类"产出都要带灵敏度负例**——把修复关掉必须变红。
   不满足这条的检查一律视为摆设。例：使用率指标曾经有两个分子在**写死时也照样通过**，被发现后补了"先制造分子≠分母"的负例。
2. **数字和路径必须脚本核对**，不靠记忆。提交前核对了 REQ/AC/端点/错误码数量与全部引用路径——**当场就抓到两处过时数字**。
3. **人工检查点由人签署，AI 不代签**。四个检查点（CP-A~CP-D）各自由负责人核对证据后才签署。

**过程中抓到的三个真实缺陷，都不是测试报出来的**：

| 缺陷 | 只有什么方式才能发现 |
|---|---|
| `start.bat` 在特定控制台代码页下会把中文注释解析成命令，**失败提示被顶掉** | 真的按现场方式双击启动（测试全绿、`run.py` 直跑正常） |
| 测试捕获启动输出时依赖 `PYTHONUTF8`，**在没设该变量的机器上中文全变乱码** | 换一台/清掉环境变量再跑 |
| `.gitignore` 里未锚定的 `env/` 把 `sim/env/` 整个吞掉，**本地全绿、新克隆必炸** | 真的 `git clone` 一次 |

这三条后来变成了项目的两条交付铁律：**输出编码不许依赖环境变量，验收基线 = 清掉变量后仍绿**；**交付前跑一次「新克隆验证」**。

此外仿真正在补第四条：**机制结论必须带档位**。我们独立复跑时发现，一个场景的第三臂在
**60 日基线档下走秤率是 1.0000（与第一臂完全相同）**，看起来像"反例没复现"；
查事件流才发现**那 60 天里设备一台都没坏**（`device_mtbf_days=540`，期望故障约 1.1 次，种子恰为 0），
**机制没有载体**。改用压力档（MTBF 10 天 / 90 日）才显形。**"没跑出来"和"跑出来是好的"是两件事。**

**当前测试规模**：**527 项全绿**（在**清掉编码相关环境变量**的基线环境下），
分契约 / e2e（真实浏览器 + 真实二维码）/ 性能（真并发）/ 仿真（含多智能体回测与静态报告）四层。

## 五、仿真环境（额外交付）

除系统本身，我们建了一套**多智能体仿真**（`docs/sim-design.md` + `sim/`）：
有**会自己做决策的商户、顾客、市场方与监管**——商户在"合规 / 转暗（私下交易）/ 退出"之间权衡，顾客的信任随被欺骗的经历衰减或恢复。

**它要回答的问题不是"我们的设计好不好"，而是"这套设计放到真实环境里会不会重蹈那几次失败"**：

- 能不能复现"抽佣 ⟶ 商户流失"？
- 能不能复现"堵住八两秤 ⟶ 商户转暗"？
- 顾客信任一旦崩掉，**能不能恢复**？

**三条已经跑出来的机制结论**（都指向可操作的杠杆；完整档位与复现命令见 `docs/sim-验证结论实况.md`）：

1. **只堵不养，比不堵还糟**（最有说服力的一条）。在堵死私下交易的前提下，
   若市场方考核口径是**装机量**而非**使用率**，则维护投入的考核收益为 0 ⇒ 设备坏了不修：
   走秤率 **0.06**，显著低于"什么都不堵"的 **0.22**，也远低于"堵死 + 考核使用率"的 **0.59**（90 日压力档）。
   **推论：反作弊机制必须与考核口径配套上线，否则会造出一个"合规却没人用"的系统** ——
   而这正是绵阳"免费送秤但维修不及时→落灰"、以及多地"验收合格却闲置"的共同机制。
2. **抽佣同时让合规变贵、让转暗变划算**——因为商户的短秤收益远大于佣金本身。
   模型给出的杠杆**不是降佣金，而是让短秤可被发现**：抽佣 0→10% 只挪 **7.5 个百分点**，
   而检测率 0→100% 让转暗从 **0.80 降到 0.10**。与南宁商务局"不能再搞八两秤了"是同一件事的两面。
3. **顾客信任的可恢复性几乎完全由"采样机会的下限"决定**——所以工程上该动的是
   **强制抽检、公共计量公示**这类"保证总有样本"的措施，而不是去调信任恢复速率（那是观测量，不是可设计量）。

**仿真自己遵守的诚实约束**：参数文件强制标注每条参数的出处类型，**有真实来源的才允许用绝对阈值，
没来源的只能用序关系与区间不重叠**；"2% 佣金率"明确标注为**不是实测费率**（真实失败案例是成都的 **2‰**）。
设计文档里也写明了这个模型**最弱的一环是循环论证**（信任恢复的结论由几组没有来源的参数驱动），并声明不假装解决了它。

### 仿真**没有**独立验证那些实地失败案例 —— 这一点必须说清楚

我们对六条实地现象做了回测（`R1`–`R6`，逐条"成立 / 不成立 / 不稳健"三态），结果**六条全判"不成立"**。
但这个"不成立"**不是同一个意思**，拆开看是四类：

| 类别 | 占几条 | 含义 |
|---|---|---|
| **不可评估**（判据依赖无出处的参数） | 3 | **机制上就不能判** —— 这是诚实纪律在起作用，**不是失败** |
| **欠功效**（两组在中心档逐位相同） | 3 | **该档位可分辨度不够**，**不是"没有效应"**；稳健性扫描换档后会翻转 |
| **真不通过** | 1（`R4-c`） | 判据可判，值没达到 |
| **判据本身有问题** | 1（`R3-c`） | 判据把"预算压到 0.3×"这个外生政策与"预算随考核指标变化"这个内生响应混为一谈，**按原文永不可能成立**，已修订判据形式 |

**所以我们不写"仿真验证了我们的设计"**。正确的表述是：

> **仿真如实报告：在登记参数与出处约束下，上述失败案例无法被独立判定 —— 多数是因为我们拒绝给无出处的参数下精确阈值。**

**这恰恰说明仿真没有被用来给结论背书。** 本方案的依据仍然是调研报告的 **26 条结论 + 30 处来源链接**。

顺带一个诚实的对照：仿真显示**在登记参数下，2% 佣金不足以翻转商户的决策**
（`走秤率` 与 `ExitRate` 两组逐位相同）。这与现实中多个市场因抽佣而垮掉的记载**不一致**，
我们保留这个不一致、不去调参数把它"调成一致"。

**系统与仿真的接线不是纸面的**：live 模式下佣金口径是**真的 `PUT` 写进系统**的，
由 `app/domain/commission.py` 计算 —— 实测系统日佣金 5699 分 ÷ 已结算订单 284872 分 = **200.1bp**；
换一条口径佣金随之变化，**仿真里没有第二份佣金口径**。此外 `--mode=live` **真实调用了全部 31 个端点**（2082 次调用，覆盖清单由实际请求反推）。

## 六、我们如实说明的不足

- **本系统未实现"向买方收费"**。调研里唯一活下来的温州模式是向**买方**收费，但本 MVP 的佣金引擎
  **只实现了"向商户抽佣"这一种形态**：契约把 `rate_bp` 限定为 1~10000（即写不进 0%），
  且收费对象 `pay_object` 字段**只被记录、不参与计算**（配 `merchant` 与 `customer` 算出的佣金金额相同）。
  这是**规格空白**而非实现缺陷 —— 契约从未规定 `pay_object` 如何影响计算。
  要支持需走规格变更流程，**不在本次交付范围**。登记见 `docs/sim-验证结论实况.md` 的 `L-01`。
- 部分硬件报价、年故障率、运维费用占比只有区间或缺失，报告中**逐条标注**为待校准假设。
  特别是**设备年故障率（MTBF）无任何公开数据**，因此仿真中涉及设备故障的结论
  **只给方向、不给现场数值**（见 `V-01` 的适用条件）。
- 仿真是**模型推演**，不能证明设计正确，只能检验结论在参数变化下是否稳健。
  其中"顾客信任能否恢复"（`Q3`）是**循环论证** —— 由几组无来源参数驱动，我们给区间不给点值，
  **并明确声明这一点未被解决**。
- 三家此前口头讨论中有、但**无法在公开来源核到**的案例（含具体金额与处分表述）**未进入任何材料**，
  只保留在附录对照里以备复核。
