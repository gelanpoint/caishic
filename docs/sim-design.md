## 0. 阅读导航与三句免责

- **只想看"怎么算"，不看"为什么"** → §3.2（商户效用）§3.3（消费者信任）§3.6（设备维护）；这三处是全篇的机制核心。
- **只想看"仿真凭什么可信"** → §7（验证与校准）——**这是本设计最重要的一节**。
- **只想看"哪些数字是查来的、哪些是编的"** → §9（参数来源总表）+ 附录 A（口述事实核对）。
- **只想看"要花多少活"** → §8（工作量拆解）。

**三句必须写在最前面的免责（它们决定了这份文档可以被怎么用）：**

1. **仿真不能证明设计正确。** 它能证明的是：**在给定的参数与机制下，系统设计会导向哪一类结局，以及结论对哪些参数敏感**。凡关键参数无真实数据的结论（见 §9 中标记「假设，待校准」的每一项），其可信度上限就是"机制自洽"，**不是"现实必然如此"**。
2. **本设计里凡是带数字的论断，都在 §9 标了出处或标了「假设」；没有第三种。** 术语约定：`[源:结论 N]` = 《报告》第 N 条结论；`[源:D-xx]` = `discovery.md` 决策表；`[源:Q-xx]` = 项目**自己已承认的**未决/未验证项；`[假设:A-xx]` = §9 的假设参数表条目，**待校准**。
3. **§8 的实现任务全部依赖一个尚未获批的 app 侧最小改动（`T-SIM-00`，业务日时钟接缝）。** 未获批时 `--mode=live` 只能跑**一个真实营业日**，跨月结论一律降级为 model 模式结论（见 §2.6 与 §7.3）。

## 1. 这个仿真存在的理由：五个问题与它们的判定标准

仿真不是"再讲一遍设计"，它必须**能给出可被反驳的答案**。下面每个问题都配一个**可计算的判定**与**一条能被推翻的判据**。无法被推翻的答案（"总体会更好"之类）在本设计里一律视为不合格输出。

| # | 问题 | 判定量（详见 §6） | 可被推翻的判据（写死，不许事后解释） |
| --- | --- | --- | --- |
| `Q1` | **抽佣 2% 时商户流失率是多少？多久开始出现？** | `ExitRate(m)`（月度流失率）、`t_first_exit`（首次非零流失的月份）、`Survival12` | 同一套其他参数下，`2% 组` 的 `t_first_exit` 必须**严格早于** `0% 组`，且 `ExitRate` 全程不低于 `0% 组`；若两组结果无显著差异（置信区间重叠），判定"抽佣不是流失主因"，**本设计的机制假设被推翻** |
| `Q2` | **堵死"八两秤"后，商户的应对是什么（退出 / 转暗 / 接受）？** | `ShareExit / ShareShadow / ShareComply` 三份额随时间演化；`ShadowRate` = 私下交易笔数 ÷ 实际总交易笔数 | `ShadowRate` 在"系统堵死"组必须**先升后降**（转暗是过渡态而非终态）；若堵死后 `ShadowRate` 单调上升且不回落，说明模型里"堵死"只是把交易赶走、并未消灭作弊动机 → 该结论与 `D-09`（验收看使用率）的政策含义冲突，须如实报告 |
| `Q3` | **消费者扫码率与"扫到空壳信息"的关系？信任被打掉后能否恢复？** | `ScanRate(t)`、`TrustIndex(t)`、恢复半衰期 `t_half` | 存在一条**临界线**：初始信任低于 `T_crit` 时空壳比例一旦超过 `s_crit`，`TrustIndex` 在 12 个月内**不得**回到初值（即"不可恢复区"非空）。若任何参数下都能恢复，则"信任陷阱"不存在，本设计的核心机制假设被推翻 |
| `Q4` | **设备维护预算不足时，多久出现"设备闲置"？** | `W_q`（平均修复等待）、`DeviceIdleRate`、`ScaleUseRate` | 维护预算低于临界值 `B_crit` 后，`ScaleUseRate` 必须呈现**正反馈下降**（预算↓ → 可用率↓ → 走秤↓ → 系统侧收入↓ → 预算↓）。若观测不到正反馈（下降是线性的、可自行稳定），则"死亡螺旋"假设被推翻 |
| `Q5` | **哪些参数组合下系统能活过 12 个月？** | 存活区域 `S` 与其在参数网格上的**面积占比**、最敏感参数排序（`S` 的定义见 §6.9） | 必须同时满足两组**外部对照**：**温州口径**（向买方收 0.5%–6%、免摊位费、出门查验）`[源:结论 12]` 的参数点**必须落在存活区**；**三例有出处的失败口径**（温江 `[源:结论 9]` / 龙南 `[源:结论 10]` / 南宁 `[源:结论 11]`）的参数点**必须落在失败区**。任一条不成立，说明模型的判别力不足，**不得**用其结果论证"什么参数下能活" |

> **Q1 / Q2 / Q4 / Q5 都依赖一个系统自己看不到的量：私下交易总量。** 它在仿真里是已知的（仿真即上帝视角），在现实中只能靠人工盘点或抽样得到 —— 这正是项目 `Q-15` 承认"系统自有数据算不出市场口径占比"的同一个量。
> **本设计据此做两件事**：① 把这类指标**显式标记为"仿真独有、不可被现场数据证伪"**（§6 表的「口径来源」列）；② 它们的验证只能靠**序关系与单调性**（上表判据），不能靠绝对值。**这是本设计最重要的一条诚实边界。**

## 2. 架构

### 2.1 最高优先的设计原则：sim 与 app 的唯一耦合面是 HTTP 契约

```
        ┌──────────────────────────── 仿真侧（只依赖 Python 标准库） ────────────────────────────┐
        │                                                                                      │
        │  sim/cli.py                                                                          │
        │     │                                                                                │
        │     ├─ sim/core/     时钟 · 事件循环 · 确定性随机流 · 事件日志 ────────────┐          │
        │     ├─ sim/agents/   商户 / 消费者 / 市场方 / 监管                        │          │
        │     ├─ sim/env/      市场 · 摊位 · 客流 · 设备机队 · 维修队列              │          │
        │     ├─ sim/rules/    效用 · 离散选择 · EWMA 适应 · 信任更新 · 口碑        │          │
        │     ├─ sim/observe/  指标计算（§6）· 汇总 · 静态 SVG/HTML 报告              │          │
        │     └─ sim/verify/   已知现象回测（§7.1）· 敏感性（§7.2）· 一致性（§7.3）  │          │
        │            │                                                              │          │
        │            └── sim/bridge/ ──┬─ model_adapter.py  （进程内直接调 sim/rules）│          │
        │                              └─ live_adapter.py   （stdlib http.client）──┐ │          │
        └──────────────────────────────────────────────────────────────────────────┼─┼──────────┘
                                                                                   │ │
                    HTTP（31 端点，唯一跨侧接口，只读契约，不 import app）        │ │
                                                                                   ▼ │
        ┌──────────────────────────── 主系统（不改业务逻辑） ────────────────────────┐ │
        │  app/（Flask + sqlite3）· run.py（子进程启动，MT_DATA_DIR 指向隔离目录）    │ │
        └────────────────────────────────────────────────────────────────────────────┘ │
                                                                                        │
                                     sim 结果的消费方（只读产物，无外部资源）────────────┘
```

**为什么把"只走 HTTP"写成最高优先级原则**（而不是图省事 import `app.create_app()`）：

1. `--mode=live` 的全部说服力在于"**这套设计真的能跑**"。若 sim 直接调领域层函数，它证明的只是"领域函数能跑"，**端点、会话鉴权、错误码、幂等、日聚合这些契约行为全部绕过了** —— 那就退化成了另一份纸上模型。
2. **唯一耦合面 = 契约被冻结的那 31 个端点**（`rest-api.md` §2）。契约一旦是唯一接口，仿真跑通就等于给契约做了一次**业务级压测**，这是可对第三方交代的证据。
3. 反向收益：sim **不能**顺手"改一点 app 让它好跑"。任何"让仿真跑通"的 app 侧改动都必须走 `RL-1/RL-2`（先改 spec，再改代码），这就挡住了"为了跑出好看结果而改被测系统"这条最危险的路。
4. **机械可检查**：`tests/sim/test_sim_no_app_import.py` 用标准库 `ast` 扫描 `sim/**` 的全部 `import`，断言不存在 `app` / `run` / `werkzeug` 导入 —— 沿用项目 `T-007` 的做法，**并带灵敏度负例**（故意在某模块 `import app` → 必红）。

> **三处实测得来的、与设计文本不完全一致的事实（如实登记；不自行改 `app/**`）**：
>
> 1. **「抽佣 0%」在 live 模式不可精确表达**：契约 §3.24 的 `rate_bp ∈ 1~10000`，而 `S0` / `S1-②`
>    声明的是 `0bp`。live 模式取下界 `1bp = 0.01%` 并在报告里标 `clamped=true` + 原因。
>    **这不动摇 `Q1` 的序关系结论**（1bp 与 200bp 仍差 200 倍），但「0%」这个字面值在 live 模式下
>    **不存在**，引用时必须带这句。**要精确表达 0% 须改契约或数据模型，属系统侧改动。**
> 2. **「当日最后一笔固定走收款码」**：若把 `POST /api/mock/payment/callback` 的出现交给随机数，
>    「31/31 全覆盖」就变成碰运气的事（`cash_share=0.7`、每天 2 笔时整轮一次都不出现的概率 ≈ 0.09）。
>    覆盖判据不能靠运气，故留一个**确定性**样本。
> 3. **`PUT /api/admin/commission-rules` 的语义是「新增一条口径」**（`data-model.md` §2.14 保留历史生效期），
>    对已有该口径的库再跑必然 `MT-1012`。live 模式对「库里那条与本次完全一致」的情形**复用并在报告里标明**
>    （`reused_existing_rule`），不一致则**原样抛错** —— 不静默改口径、也不换个费率蒙混过去。
>
> **live 实测（2026-10-03，`python -m sim --mode=live --scenario=S1 --live-arm=0 --live-days=30 --live-txns=4`）**：
> HTTP 调用 **2082 次** / 营业日 **30** 天 ⇒ 判据①**31/31**、判据②**30/30 天 `balanced=true`**、
> 判据③重发后**同一交易号**且列表 `total` 不变（HTTP **201 → 200**）、判据⑤数据目录落在
> **`C:\mt-sim\live-S1-…`**（实测 **p50 19.6ms / p95 40.6ms**，样本 2082）、判据⑥`app/**`（33 文件）与
> `specs/**`（6 文件）树指纹**运行前后一致**；判据④由 `tests/sim/test_live_run.py` 复用
> `tests/contract/sensitive_scan.py` 扫 **2082 条真实响应体** → **零命中**。
> **「佣金由系统算」的交叉核对**：写进系统的口径 `rate_bp=200`，系统给出的日佣金合计 **5699 分**，
> 同期已结算订单总额 **284872 分** ⇒ 实收费率 **200.1bp**（差额来自逐日四舍五入）；
> 结算单佣金合计与看板佣金合计**同为 5699 分**（同一处口径 `stall_day_facts`）。
> 对照：同 seed、同一编排的 `S0`（写入 1bp）实测佣金合计 **15 分** —— 佣金确实随**系统里的口径**而变，
> 不是 sim 自己算的。**`--mode=model` 未受影响**：`git archive HEAD` 导出的改动前 `sim/` 与当前代码同参数
> 跑出的 `events.jsonl` / `metrics.json` SHA-256 **逐字节相同**。

> **`tests/sim/` 的两条实现纪律**（都是项目已经踩过的坑，不要重踩）：
> ① **用例一律用唯一模块名导入**（`sim_support` 之类的专名），不要新增与 `tests/conftest.py` / `tests/contract/conftest.py` 同名的 `conftest.py` —— 项目曾因"同名 conftest 撞车"导致 10 个文件收不起来（提交 `cabe4e1`）。
> ② **sim 侧不得复用 `tests/contract/contract_support.py` 的 HTTP 助手**（`bind_stall_session` / `create_priced_transaction` / `session_headers` 等）：它们会让"唯一耦合面 = HTTP 契约"这条纪律变成"复用测试夹具"，而夹具本身可以绕过契约。sim 的 live 适配器**自己实现** HTTP 调用（stdlib `http.client`），这正是它作为契约压测的价值所在。

### 2.3 数据流（`--mode=live`，一次营业日）

```
clock(day=d) ──► 商户 agent 决策：是否设价目表
                    └─► POST /api/merchant/session  → X-Stall-Session
                    └─► POST /api/merchant/price-list (copy_from_previous_day)
    │
    ▼ 时段块到达过程（§5）→ 每个顾客事件
consumer agent 选摊（logit，§3.3）
    └─► 商户 agent 决策：走秤 / 私下 / 拒绝
          ├─ 走秤：POST /api/merchant/transactions           (Idempotency-Key)
          │        ├─ 需要改价? POST .../{no}/price-change  (>50% 时回传 confirm_over_threshold)
          │        ├─ POST .../{no}/payment  (cash | qr)
          │        │        └─ qr → POST /api/mock/payment/callback (success/failed/timeout)
          │        └─ 小概率退货 → POST .../{no}/refund
          └─ 私下：**只在 sim 内部记账**（系统不可见 → 这就是 §6 的"私下交易"口径）
    │
    ▼ 消费者扫码决策 → GET /api/customer/receipts/{no} 或 /api/customer/stalls/{stall}/profile
    │   （读到的字段是否"有采集来源" → 决定信任更新的 o 值，§3.3）
    │
    ▼ 日终：POST /api/admin/daily-aggregate → GET /api/admin/reconciliation
    │        → GET /api/admin/metrics/usage → GET /api/admin/dashboard
    │        → GET /api/admin/audit-logs（抽查留痕只增不改）
    ▼ 月末：POST /api/admin/settlements → GET /api/admin/settlements
    │        → 商户 agent 更新 EWA → 退出/作弊/继续决策
    │        → 市场方 agent 决策维护预算与是否继续 → 监管 agent（季度）
    ▼ observe/metrics → CSV/JSON/HTML（纯静态）
```

**31 个端点必须全部被真实调用至少一次**（`--mode=live` 的完成定义之一，见 §8 `T-SIM-07`）。其中三个"非业务流"端点（`/healthz`、`/api/admin/categories`、`/api/admin/aliases`）由**日初配置阶段**调用；`PUT /api/admin/commission-rules` 由**场景装载阶段**调用 —— 这样"抽佣 0% / 2% / 温州式"就不是 sim 里的一个变量，而是**真的写进系统佣金口径**，`--mode=live` 下的佣金数字由 `app/domain/commission.py` 算出（而不是 sim 自己算一遍）。**这一点是"live 模式不是纸上模型"的关键证据。**

### 2.4 确定性可复现（仿真可信度的地基）

- 全局 `--seed` → `random.Random(seed)` 派生**每 agent 独立子流**：`stream_key = hash(seed, agent_id, purpose)`，`purpose ∈ {arrival, choice, cheats, trust, breakdown, repair, …}`。
  **为什么必须分流**：若所有 agent 共用一个流，那么"新增一个消费者"会平移后续所有随机数，导致两次运行无法做**单因子对照**（对照组之间的差异会被随机噪声掩盖）。分流后，A/B 场景的**同一 agent 同一 purpose 的随机数完全一致** —— 这是 §7.1"复现已知现象"能做成对照实验的前提。
- **产物自证**：`--mode=model --seed=S` 两次运行的 `metrics.json` 与 `events.jsonl` 的 SHA-256 **必须逐字节相同**；`--seed` 不同则必须不同（`T-SIM-01` 的验收）。这是"结果不是手写的"的第一层机械证据。
- 交叉污染检查：live 模式运行前后对 `data/market_trade.sqlite3`（演示数据）取哈希，**必须不变**；sim 只用自己的 `MT_DATA_DIR`（`data/sim/<run_id>/db/`）。

### 2.5 参数出处必须是**数据结构的一部分**（把"诚实标注"变成机械检查）

`sim/calibration/params.json` 的每一条**强制**形如：

```json
{
  "P-01_scale_unit_price_cents": {
    "value": 1350, "unit": "元/台", "range": [135000, 256600],
    "provenance": { "kind": "sourced", "ref": "结论 23", "quote": "普通溯源秤 1350 元/台" }
  },
  "A-11_mtbf_days": {
    "value": 540, "unit": "天", "range": [180, 1095],
    "provenance": { "kind": "assumed", "ref": "《报告》第九节（自认数据缺口）",
                    "calibration": "报告明确承认『设备每年坏多少、修一次多少钱，没有公开数据』；故只做区间敏感性，结论不得依赖其点值" }
  }
}
```

`tests/sim/test_param_provenance.py` 逐条断言：`provenance.kind ∈ {sourced, assumed}`；`sourced` 必须有 `ref`，且 `ref` 必须匹配 `^结论 \d+$` 或 `^D-\d+$`；`assumed` 必须有非空 `calibration`。**灵敏度负例**：把某条的 `kind` 改成 `sourced` 但删掉 `ref` → 必红；把一条 `assumed` 的 `calibration` 清空 → 必红；**把 `Q-xx` 标成 `sourced` → 必红**。

> **`Q-xx` 一律归 `assumed`（`2026-10-02` 父代理裁定批准的口径收紧）**。`Q` 是**项目自己登记的"待确认假设"**（见 `discovery.md` 的未决项），不是调研出处 —— 把它当"有出处"，正是本文档要防的"把假设写成事实"。设计初稿曾把 `^Q-\d+$` 列进 `sourced` 的合法 `ref`，**那是错的**：实现（`sim/core/params.py` 的 `SOURCED_REF_RE`）从一开始就**不含** `Q-xx`，文档已按裁定同步改齐 —— **文档写一套、实现另一套，就是新的漂移源**。
>
> 于是"主体探索频率来自 `Q-9`"这类条目，写法是 `kind = "assumed"` + `ref = "Q-9"` + **必填的 `calibration`**（说明它是项目自认的待确认假设、以及打算怎么实测校准）。`assumed` 的 `ref` 是自由文本，仅用于指回它想对标的真实数字或自认缺口。

> **这条检查的意义**：设计文档里的"参数标注必须诚实"是一句承诺，承诺会漂移；**把出处写进参数文件并由测试强制，它才变成约束**（这正是项目 `T-036` 家族"不验证灵敏度的验证是摆设"的同一条逻辑）。

### 2.6 两种运行模式

| | `--mode=model` | `--mode=live` |
| --- | --- | --- |
| 交易落库 | sim 进程内的"记账世界"（`model_adapter.py`） | **真实 HTTP** 打到 `app/` 的 31 个端点 |
| 佣金/日聚合/结算/三指标 | sim 按 `data-model.md` §5.1 同一口径复算 | **由系统算**（`commission.py` / `metrics.py` / `settlement.py`） |
| 速度 | 见下方「性能预算」（**先算账，不拍脑袋**） | 慢（受 HTTP 与 SQLite 写盘限制，参照项目实测：`D:` 盘 p50 297ms/请求 → **1 营业日全量 ≈ 分钟级；360 日 ≈ 小时级**） |
| 用途 | 敏感性分析、存活区域扫描、蒙特卡洛置信区间 | **证明"这套设计真的能跑"**：契约行为、幂等、对账等式、日聚合/结算链路 |
| 业务日推进 | 仿真时钟自由推进 | **必须**依赖 `T-SIM-00` 的时钟接缝；未获批时只能跑 1 个真实营业日 |
| 完成定义 | 同 seed 逐字节可复现 + §7.1/§7.2 判据 | 31/31 端点被调用 + `reconciliation.balanced=true` 全营业日成立 + §7.3 一致性容差内 |

**性能预算（这一节的数字是算术，不是承诺；先用一次实测标定再定目标）**

先把账算清楚，再谈"快"：

```
单次全量 model 运行 = 10 摊 × 360 营业日 × ~115 笔/日      ≈ 41 万笔交易
每个场景 R=200 次重复                                      ≈ 8300 万笔
7 个场景（S0–S6）                                          ≈ 5.8 亿笔
```
**纯 Python 下 5.8 亿笔量级不可能"几分钟跑完"** —— 若按每笔 20 μs（乐观）算也要 ~3 小时以上，加上 agent 决策开销只会更多。故本设计**明确不做"R=200 全量 × 7 场景"**，改用**两级预算**：

| 级别 | 用途 | 做法 | 量级 |
| --- | --- | --- | --- |
| `L1` 全量 | `R1`–`R6` 的判据、`S1`–`S6` 的**主结论**、model↔live 一致性 | 全 360 日逐笔仿真，`R = 20` 次 | 7 场景 × 20 × 41 万 ≈ **5700 万笔** |
| `L2` 压缩 | **敏感性扫描、存活区域扫描**（`Q5`） | **代表日抽样**：每 30 个营业日只仿真 3 个代表日（覆盖三个时段块），按月权重还原；交易的**逐笔**决策仍是真的，只是不逐日跑 | 网格 512 组 × 12 月 × 3 日 × 1150 笔/日 ≈ **2100 万笔** |

- **`L2` 必须先通过与 `L1` 的一致性校验**（同一 seed 下，把 `L2` 的还原值与被抽样掉的日子在 `L1` 里的真值比对，容差按 §7.3 的口径）。**这条一致性校验是使用压缩模式的准入条件**；过不了就退回 `L1` 并如实报告"敏感性扫描的规模受限"。
- **性能目标（待实测标定，不给编造的绝对秒数）**：以"单次全量 360 日运行"的实际耗时 `t_run` 为基准，`T-SIM-06` 落地时必须实测并写入 `docs/sim-results.md`；**运行总时长按 `t_run × R × 场景数` 由脚本估算并打印**，超预算时由使用者显式调小 `R`（而不是偷偷降精度）。
- **`R=20` 的理由**：§7.1 的判据绝大多数是**序关系**（组 A 严格差于组 B），而非绝对值。20 次重复在"效应量大"的判据上足够；若某条判据在 `R=20` 下区间重叠 → **该判据降级为"不稳健"并如实报告**，不得靠加大 `R` 去凑显著性。

**速度的诚实提示**：项目自己的实测记录显示，数据目录在 `D:` 卷时请求 p50 297ms、p95 770ms（根因是磁盘 fsync，不是接口实现，见 `docs/PROJECT-STATE.md`「下一步动作」第 1 条）。**live 模式的长周期运行必须把 `MT_DATA_DIR` 放在 `C:`**，否则 360 个营业日的 HTTP 全量跑不完。这一条写进 `T-SIM-07` 的操作约束，现场演示前必须实测确认。

## 3. Agent 决策模型

### 3.1 共同地基：有限理性 + 异质性 + 随经验适应

**为什么不用"最优反应"**：真实商户不会解最优化问题。本设计采用三件套（ABM 的标准做法）：

1. **有限理性**：决策基于**局部信息 + 简化启发式**（阈值触发、锚定调整、EWMA 估计），不是全局最优；
2. **异质性**：每个 agent 的参数从**分布**中抽取（不是同一个"平均商户"重复 10 次）——这是 `Q2`（不同商户不同应对）能被回答的前提；
3. **随经验适应**：结果会反馈进下一期决策（商户用 EWA 更新对各策略的估值、消费者更新信任、市场方按可用率调预算）。

符号约定：`i` 摊位、`j` 消费者、`M` 市场方、`R` 监管；`t` 营业日、`m` 月；金额一律**分**（与系统一致，`rest-api.md` §1.4），比例一律**万分比 bp**（与系统一致，`commission_rule.rate_bp`）。

### 3.2 商户 Agent（默认 10 个摊位，必须异质）

#### 3.2.1 行动空间（三选一 + 程度）

```
A_i = { comply(d=0)         走秤、不短秤
      , evade(d>0)          走秤但短秤；或"转暗"绕开系统私下成交
      , exit }              退租 / 搬离市场
```

**"转暗" = evade 的极端形式（`ρ_shadow = 1`，该笔完全不走秤）**。三个行动恰好对应 `Q2` 问的"退出 / 转暗 / 接受"，所以 `Q2` 的答案就是三个行动被选中的份额（§6 的 `M-06`，三者之和恒为 1）。

#### 3.2.2 效用函数（月频决策，当期收益 + 跨期忍耐）

```
U_i(a, m) = Π_i(a, m)                 经营毛利
          − Λ_i(a, m)                 平台相关成本（佣金 + 设备分摊 + 操作摩擦）
          − Ψ_i(a, m)                 查处与信誉损失
          − Ω_i(a, m)                 客流反噬（短秤被老顾客察觉）
          − Σ_exit·1[a = exit]        退出的一次性转换成本
```

**逐项展开（写清每一项的含义与量纲）**

**(1) 经营毛利 `Π`** —— 短秤收益在这里，**这是 `结论 13` 的数学化**

```
comply :  Π = V_i(m) · g_i
evade  :  Π = V_i(m) · ( g_i + (1 − g_i) · d_i )
```
- `V_i(m)`：摊位 `i` 的**实际**月度流水（含走秤 + 私下，元）。仿真里已知，系统不可见。
- `g_i`：毛利率（蔬菜/水果/肉类/水产分别抽 `[假设:A-01]`）。
- `d_i`：**短秤幅度** = 1 − 实际给重/标称重。**`d = 0.2` 有名称级出处**：`结论 13` 南宁商务局原话把这类行为直接称为**"八两秤"**（8 两 / 1 斤 = 0.8）→ `d = 0.2` `[源:结论 13]`；`d_i` 的**分布**无出处 `[假设:A-03]`。
- **短秤收益的解析形式**：`ΔΠ = V · (1 − g) · d`。即"每 100 元流水、毛利率 25% 时，八两秤每月多赚 15 元/100 元流水"。量级与 `结论 13` 的定性判断一致（"这直接损害了某些人的利益"），**但 15% 这个具体数没有独立实测来源**，它是 `g` 与 `d` 的推算，必须在报告里标为推算而非观测。

> **为什么必须把作弊收益写成效用里的一项真实项**：`结论 13` 是全部 26 条结论里最锋利的一条 —— 它给出了**"商户拒用的真根因不是不会用，而是不能再少给称"**。若模型不把这项写进效用，模型在数学上就只能得出"商户拒用是不理性的"，从而**结构性地无法复现三例有出处的翻车**（温江 / 龙南 / 南宁，`结论 9/10/11`），也就没有资格回答 `Q1`/`Q2`。

**(2) 平台相关成本 `Λ`**

```
Λ = V_scale(m) · rate_bp/10000 · 1[pay_object = merchant]      ← 佣金（只按"走秤"流水计）
  + dev_amort_i(m)                                             ← 设备分摊（自费口径才有）
  + f_op · n_txn(m)                                            ← 操作摩擦成本
  + 5000/12 · 1[云软件自费]                                     ← 云软件（结论 26）
```
- `rate_bp`：**真的来自系统配置**（`PUT /api/admin/commission-rules`），不是 sim 里的常量。抽佣 2% → `rate_bp = 200`。
- `dev_amort_i`：市场方出资 → `0`；商户自费 → `3750~4600 元/台` 按 36 个月折旧 + 可能的云软件 `5000 元/年` `[源:结论 26]` → 约 **521 元/月**（推算，非实测）。
- `f_op`：**操作摩擦**（`结论 6` 绵阳原话："操作麻烦""我自己买秤字很大，智慧公平秤显示屏字太小""电池质量差，每天都必须充电""有些按键反应比较慢"）→ 建模为**每笔额外耗时 `Δt` 秒 × 时间机会成本 `w`**。`[源:结论 6]`（定性）`+ [假设:A-10]`（`w` 与 `Δt` 的取值）。
- **注意 `Λ` 里的第一个"只按走秤流水计"** —— 这一项是**核心耦合**：抽佣让"走秤"变贵，同时让"转暗"变划算（私下流水不付佣金）。三例有出处翻车（`结论 9/10/11`）的机制链就是从这里长出来的。

**(3) 查处与信誉损失 `Ψ`**

```
Ψ = p_check(R) · F_short            ← 被查概率 × 罚款（仅 evade）
  + p_check(R) · Loss_rep          ← 被查后的声誉/信用二次损失
  + 1[改价被顾客看到] · φ_consist   ← 标价一致率下降带来的客流损失（REQ-008 的顾客可见指标）
```
- `p_check(R)`：**由监管 Agent 决定的自变量**（§3.5），不是常数。这正是题目要求的"作弊成本 = 被查概率 × 罚款，用监管强度做自变量"。
- `F_short`：短秤罚款。**仓库内唯一的行政罚款数字是 `结论 2`：儋州某市场开办者因场内商户屡次未明码标价被罚 2 万元** —— 注意它罚的是**市场开办者**、事由是**明码标价**，**不是**商户短秤。故 `F_short` 只能拿它做**量级类比** `[假设:A-14]`，**不许写成"短秤罚 2 万"**。

**(4) 客流反噬 `Ω`** —— 这一项是把"作弊不是免费的"写进模型

```
Ω = κ_detect · p_detect(d_i) · V_i(m) · loss_share
```
- 机制：短秤若被老顾客发现 → 回头客流失 → `V_i` 下降。`p_detect` 随 `d_i` 增大而上升（越狠越容易被发现，尤其在"扫码有记录 + 明码标价 + 公平秤复称"的环境里）`[假设:A-04]`。
- **为什么必须有它**：没有 `Ω`，模型会系统性高估短秤收益，使"堵死八两秤"看起来比现实更必要 —— 这是本设计**自己给自己埋的一个可被质疑点**，写在这里以免被当成疏漏（§9 与汇报里如实列为"最可能需要校准的一项"）。

**(5) 退出 `Σ_exit` 与退出触发（跨期，不是当期比较）** —— `Q1` 的"多久"就出在这里

```
参考点 R_ref,i   = 入驻前预期月净收入（由 D-05 的"入场承诺"与历史经验初始化）
忍耐触发          : EWMA_i(m) = (1−β)·EWMA_i(m−1) + β·U_i(chosen, m)
                   若 EWMA_i < R_ref,i − θ_exit 连续 n_breach 个月 → 进入退出评估
退出评估          : exit  ⟺  σ_exit·Σ_exit < (U_alt − EWMA_i)·H      H = 剩余租期(月)
```
- `θ_exit`（忍耐幅度）、`n_breach`（连续月数）、`σ_exit`（对转换成本的敏感度）`[假设:A-05/A-06]`。
- **校准锚（这两个是"事实"不是假设）**：成都青羊区"菜东家"智慧农贸市场 **2024-10 开始运营、数月即垮** `[源:结论 8]` → `n_breach` 与 `θ_exit` 的取值必须使"失败口径"组的退出时间落在**数月**量级；龙南案例是"**已有很多商户选择搬离市场**" `[源:结论 10]`（无时间点）→ 只用**序关系**（有手续费组必须出现非零流失，无手续费组不得出现）。
- **为什么用 EWMA + 连续突破而不是"当期效用为负就退出"**：真实商户不会因为一个月赚得少就走（搬迁有成本、有惯性）；用当期判据会导致流失率抖动、无法回答"多久开始出现"。这个机制选择本身就是"有限理性"的体现。

#### 3.2.3 学习/适应：经验加权（EWA-lite）+ 同伴传播 + logit 选择

```
Q_i(a, m) = φ · Q_i(a, m−1)                                    ← 记忆衰减
          + (1 − φ) · π_i(a, m)                                 ← 本期实得
          + ρ · (1 − φ) · Q̄_peer_i(a, m)                        ← 同伴传播（10 摊小网络，环形/全连）
P_i(a, m) = softmax( λ_Q · Q_i(a) + β_feas · feas_i(a, m) )
```
- `feas_i(a)`：**行动的技术可行性**（不是偏好）。`feas(evade)` 由**系统设计**决定：
  ```
  feas(evade) = (1 − ρ_anchor) · (1 − p_exit_check) · (1 − ρ_scan·coverage)
  ```
  - `ρ_anchor`：**"秤是唯一物理锚点"的实现程度**（`D-03`）。若交易必须走"选品 → 称重 → 计价 → 出收款码"，短秤在系统内**无法表达**（改重量 = 改价，留痕可见）→ `ρ_anchor → 1`。
  - `p_exit_check`：**出口查验交易凭证**的执行率（`结论 12` 温州模式的抓手："买方必须用市场的秤，出门查验交易凭证"）`[源:结论 12]`；执行率本身 `[假设:A-20]`。
  - `coverage`：顾客扫码覆盖率 —— 若没人看，短秤在系统内也留不下有效证据。**这一项把 §3.3 的信任/扫码与 §3.2 的作弊可行性连起来了**：扫码率低 → `feas(evade)` 高 → 短秤有生存空间。
- `φ`（记忆衰减）、`ρ`（同伴权重）、`λ_Q`（选择锐度）`[假设:A-07]`。
- **同伴传播的必要性**：`结论 10` 的"**已有很多商户**表示强烈抗议并**有许多商户**选择搬离"是**集体行为**，不是 10 个独立个体各自算账的结果。没有 `ρ`，模型无法复现"集体搬离"这种相变式现象。

#### 3.2.4 商户异质性（10 个摊位必须互不相同）

| 维度 | 分布/取值 | 出处 |
| --- | --- | --- |
| 品类 | 蔬菜 / 水果 / 肉类 / 水产（种子数据四类，58 个标准品类） | `data-model.md` §5、`app/seed_data/seed.json` |
| 规模 `V_i^base` | 分三档（小/中/大）；中档锚在"单摊位日均 80–150 笔" | `[源:Q-9]`（**项目自己标注"待确认假设，行业常识，未经调研验证"**） |
| 毛利率 `g_i` | 按品类抽 | `[假设:A-01]` |
| 风险偏好 | 对 `Ψ` 的权重（越保守越不短秤） | `[假设:A-05]` |
| 作弊倾向 `d_i` | 按"惯犯/机会型/守规"三类混合 | 三类划分来自 `结论 13` 的分层描述（"**部分**经营户…**某些人**的利益"）`[源:结论 13]`；比例 `[假设:A-03]` |
| 数据隐私敏感度 | 对"销售排行高 → 怕被涨租"的权重 | `[源:结论 15]` 原话（"商户会为数据隐私的曝光风险而不安，销售排行更高的商户则担心面临涨租问题"）；权重 `[假设:A-18]` |

> **异质性不是装饰**：`结论 13` 的措辞是"**部分**经营户""**某些人**"，`结论 15` 说的是"**销售排行更高的**商户则担心涨租"。若 10 个摊位同质，这两条结论在模型里根本没有落点，`Q2`（不同商户的不同应对）也就无从回答。

### 3.3 消费者 Agent（数百个，必须异质）

#### 3.3.1 两个决策

**(a) 选摊（logit 随机效用）**

```
U_ij = α_p·price_ij(摊位价 + 改价幅度) + α_t·T_ij(信任)
     + α_d·(−dist_ij) + α_w·(−wait_i) + α_q·quality_i + ξ_ij
P(选 i) = softmax(U_ij)
```
异质性：`(α_p, α_t, α_w)` 按三类抽取（**价格敏感型 / 信任敏感型 / 时间敏感型**）`[假设:A-09]`；三类比例无出处，**待校准**。

**(b) 扫码（是否打开扫码页看信息）**

```
p_scan_ij = σ( γ0 + γ1·T_ij + γ2·1[价格公示可见] + γ3·(−c_time_j) + γ4·1[出口查验/强制] )
```
| 参数 | 含义 | 出处/状态 |
| --- | --- | --- |
| `γ0` → `p_scan^base` | 扫码基线意愿 | **`结论 17` 明确承认"主动扫码评价的比例仍缺乏统计"** → **无源，`[假设:A-09]`**。这是本设计最硬的缺口之一 |
| `γ2` | 价格公示对扫码的拉动 | `[源:结论 1]` 湖州做法（实时改价 / 统一价签 / 抽拉式价格公示牌 / 可擦写标签）——**效果系数无数据** `[假设:A-19]` |
| `γ4` | 强制/查验的拉动 | `[源:结论 12]` 温州模式"出门查验交易凭证" |

#### 3.3.2 信任状态量（核心）

```
o_ij(t) = 1  扫码打开后看到**有采集来源**的真实信息（REQ-023 / AC-011 的字段白名单）
        = 0  空码 / 无效信息 / 无数据（"应付检查的贴纸"）
        = 缺省 未扫码

T_ij(t+1) = clip( T_ij(t)·(1 − δ)                                  ← 自然衰减
                + η(ν)·( o_ij(t) − T_ij(t) ),  0, 1 )
其中  ν = o_ij(t) − T_ij(t)，  η(ν) = η⁺ (ν ≥ 0)， η(ν) = η⁻ (ν < 0)，且 **η⁻ > η⁺**
```
- `η⁻ > η⁺`（负面偏差/损失厌恶）的依据是 `结论 16` 的原话：**"扫过好几次空码、无效信息之后，再也不信这个标签了，觉得就是贴来应付检查的贴纸。"** —— 原文用的是"**再也不信**"，这是**不可逆/极慢恢复**的语义，而不是"扣一点分"。`η⁻/η⁺` 的具体倍率 `[假设:A-08]`。
- `δ`（无接触时的自然衰减）`[假设:A-08]`。
- **恢复半衰期（`Q3` 的答案载体）**：
  ```
  t_half = ln2 / ( δ + η⁺ · p_scan · 1[信息有真实来源] )
  ```
- **正反馈陷阱（`Q3` 的"能否恢复"）**：
  ```
  T↓ → p_scan↓ → 采样机会↓ → 恢复更慢 → T 长期低位
  ```
  一旦 `T` 跌破 `T_crit` 且空壳信息比例超过 `s_crit`，`T` 就进入**不可恢复区**。这个反馈必须显式存在，因为它是 `结论 16`（"再也不信"）在机制上的唯一解释方式 —— 若没有它，模型只能得到"信任慢慢回升"这种与调研结论相反的结论。

#### 3.3.3 消费者异质性

| 维度 | 取值 | 出处 |
| --- | --- | --- |
| 比价倾向 `α_p` | 三类分布 | `[源:结论 11]`（"中老年顾客不接受""摊主进货需要现金周转"说明顾客结构是有差异的）`+ [假设:A-09]` |
| 信任水平初值 `T_ij(0)` | 分布（含"已经不信"的一档） | `[源:结论 16]`（已有人处于"再也不信"状态） |
| 时间成本 `c_time_j` | 分布（按当地工资折算） | `[假设:A-10]` |
| 支付方式偏好 | 现金 / 扫码 | `[源:结论 11]`（南宁摊主原话"买卖还是用现金进行交易比较好"；`D-04` 据此定为必须支持现金） |
| 复称意愿 | 有/无（决定能否发现短秤 → 影响 `p_detect`） | `[源:结论 6]`（绵阳"智慧公平秤"的存在意义即复称）`+ [假设:A-04]` |

### 3.4 市场管理方 Agent

#### 3.4.1 效用

```
U_M(m) = Income(m) − Cost(m) − RiskAssessment(m)
```
- **`Income`**：佣金（`pay_object = merchant|customer` 时按实收金额计，`REQ-017`）+ 摊位费/租金 + 银行合作费 + 政府补贴 + （可选）纳统/数据服务价值。
  - 银行付费量级：`[源:结论 19]` 达川"**交通银行达州支行提供三年期 200 余万元资金支持**"、原话"**政府不投钱、资金不外流**"；`[源:结论 20]` 建行大连"结算效率提升 60%、年度人力成本节约 20 万元"。
    ⚠️ **诚实边界**：结论 19 未交代覆盖几个市场、多少摊位 → **只能做"量级锚"，不能算出"每市场每月多少"**。用法：把银行付费设为 `[假设]` 区间，并在敏感性里报告结论对它的依赖。
  - 政府补贴：`[源:结论 3]` 上海宝山"智慧菜场按审计实际投入的 **50%** 补贴，单个项目最高 **200 万元**"（另有标准化菜市场 50%/150 万、信息化改造 50%/50 万；区与街镇各承担一半）。**到位率与延迟 `[假设:A-16]`**。
- **`Cost`**：设备采购摊销（真实中标价 `[源:结论 23/24/25]`）+ **维护预算 `B(m)`** + 计量检定 + 网络专线 + 人力。
- **`RiskAssessment`**：考核/督查风险。
  ```
  Risk = w1·1[使用率 < θ_use]·(督查风险) + w2·1[投诉率 > θ_cmp] + w3·1[验收不合格]
  ```
  - `[源:结论 4]` 武汉电视问政原话"**这就是验收不合格，因为不能有效使用，是形式主义**"，以及"区级验收后，市里按照 **10%** 的比例抽检验收"。
  - `[源:结论 9]` 温江案被国务院"互联网+督查"查实后"**全额退还**手续费、承诺不强制、**负责人被约谈**"。
    ⚠️ **诚实边界**：任务书口述提到"¥4,639.45"与"官员被处分"，**这两项在仓库内（含《报告》）均查无出处**（附录 A 已核）。本设计**不引用**它们。

#### 3.4.2 决策规则（三项，全部有界理性）

**(a) 维护预算（锚定 + 调整 + 迟滞）**
```
B(m+1) = B(m) · (1 + g),   g = clip( κ·(A_target − A_obs(m)), −g_max, +g_max )
决策迟滞：B 的变化在提出后延后 d_delay 个月生效
```
- `A_target`（目标可用率）、`κ`、`g_max`、`d_delay` 全为 `[假设:A-18]`。
- **迟滞是必要的**：`结论 6` 绵阳案例（2020 投放 → 2022 年 9 月回访才被报道落灰）说明"发现→修"之间存在以**年**计的滞后。无迟滞的模型会立刻把预算调到位，从而复现不出"落灰两年"。

**(b) 投诉响应** → 影响 `p_detect`、`feas(evade)`、监管侧的投诉量 `[假设:A-18]`。

**(c) 是否继续推行 `a_M ∈ {continue, reduce, abandon}`** —— 这里复现 `结论 4/5`（武汉）的**激励错配**

```
if  考核口径 == 装机量/验收:
        市场方最优策略 = 一次性装机通过验收，然后 B* → 0（维护不产生任何考核收益）
if  考核口径 == 使用率（D-09 / REQ-022 修订后的三指标）:
        B* = argmax_B [ Risk(使用率|B) 的下降 − B 的成本 ]  > 0
```
> **这是本设计里最有政策含义的一段**：`结论 4` 的"黑屏也能通过验收"不是某个人偷懒，而是**考核口径决定的最优反应**。把"装机量"换成"使用率"（`D-09`、`REQ-022`、`AC-005` 的分子分母全部系统自有）**在模型里会改变 `B*` 的符号**。这给出一条**可被反驳的设计论证**：若仿真显示换口径后 `B*` 仍为 0，则该论证不成立，必须如实报告。

### 3.5 监管 / 政府 Agent（可选，但 `Q1`/`Q2` 需要它）

```
决策频率：季度
自变量：  抽检强度 p_check ∈ [p_min, p_max]、罚款 F、补贴 s、考核口径
效用：    U_R = −计量投诉量 − 督查/舆情风险 − 执法预算成本 + 本地消费统计收益
规则：    if 投诉量(m) > T_cmp  → p_check ← min(p_max, p_check·(1+θ_up))
          if 投诉量(m) < T_low  → p_check ← max(p_min, p_check·(1−θ_dn))     ← 松懈也是内生行为
补贴：    按 结论 3 的 50% / 上限 200 万
```
- `p_check` 基准区间：**只有 `结论 4` 的"市里按 10% 的比例抽检验收"这一个数字**，但那是**验收抽检**、不是**日常计量抽检** → 二者只能作类比 `[假设:A-15]`（区间 1%–30%，在敏感性里全域扫描）。
- 投诉量下降的正向信号：`[源:结论 17]` 青岛"今年一季度计量投诉降了 50%"，**但同一报道指出"主动扫码评价的比例仍缺乏统计"** → **不得**把"投诉降 50%"当成"扫码有效"的证据（`结论 17` 自己就在质疑这个因果）。

### 3.6 设备与维护子模型（横跨商户与市场方；`Q4` 的机制）

**设备状态机**
```
ok ──(故障, TTF ~ Exp(MTBF))──► broken ──(报修→排队→维修, TTR ~ Exp(MTTR))──► ok
       （MTBF 无公开数据 [源:《报告》第九节][假设:A-11]；MTTR/维修单价同理 [假设:A-12]）
```

**维修排队**：`服务台数 c = floor(B(m) / c_tech)`；队列指标 `W_q`（平均等待），`A_i`（摊位可用率）。为保持标准库实现，用**离散事件队列 + 解析近似**（`W_q ≈ backlog / (c·μ)`）而非仿真库。

**两条不同的"设备闲置"通道（必须分开建模，否则会把绵阳和武汉混为一谈）**

| 通道 | 机制 | 历史对照 |
| --- | --- | --- |
| **(1) 物理不可用** | 设备 `broken` 且未修 → 当日走秤笔数上限 = 可用设备数 × 单机容量 → 溢出到私下交易 | `[源:结论 4]` 武汉 6 家市场"智能设备黑屏、连网都没通"；`[源:结论 5]` 2021 年回访 20 多家市场"电子化设备无法使用、闲置的情况屡见不鲜"，涉及 **318 家**改造过的市场 |
| **(2) 可用但不用（意愿通道）** | `A_i = 1` 但商户意愿 `w_i` 低 → 主动用回自己的秤 → 设备落灰 | `[源:结论 6]` 绵阳"从角落里把秤翻出来，上面已经落了厚厚一层灰"，摊主"**用自己买的秤**" |

**商户使用意愿（意愿通道的载体）**
```
w_i = σ( w0 + w1·A_i + w2·(−W_q,i) + w3·(−f_op) + w4·(−rate_bp·1[merchant]) + w5·1[免费+统一检定维修] )
```
- 正向证据：`[源:结论 14]` 衡阳（**邮政免费**配智能秤，摊主"比以前轻松了不少"）、杭州（**统一配秤并统一检定维修**，摊主"统一配秤为我们经营户减少了不少麻烦和纠纷"）。
- 反向证据：`[源:结论 14]` **绵阳的秤"虽然也是赞助的"，但"维修不及时"，结果落灰弃用** —— **"免费 ≠ 够"，必须"免费 + 免维护"**。这一条直接对应 `D-02`（市场方出资，且采购范围含维保与计量检定）。
- `w1..w5` `[假设:A-18]`。

**正反馈死亡螺旋（`Q4` 的核心，也是 `Q5` 存活分析的机制）**
```
B↓ → W_q↑ / A↓ → w↓ → 走秤笔数↓ → (若收入依赖走秤流水：佣金 / 纳统 / 银行考核) 收入↓ → B↓
```
**可复现性判据**：这一环若成立，则 `B` 与 `走秤率` 的时间序列应同时呈**单调下降且曲率加速**；若呈线性下降后自行触底（不加速），则本假设被推翻（见 §7.1 `R3`）。

## 4. 仿真时序

### 4.1 与系统营业日语义对齐

系统的营业日键是 `transaction.business_date`，由服务端 `date.today()` 派生（`app/domain/pricing.py` 第 152 行；`data-model.md` §2.8），日聚合/结算/三指标全部以它为轴（`REQ-018/019/022`）。**仿真时钟必须与它同轴**，否则 `--mode=live` 的日聚合与结算根本对不上。

| 仿真层 | 推进单位 | 与系统对应 |
| --- | --- | --- |
| `T0` 日初 | 1 营业日 | `business_date = d`；`POST /api/merchant/price-list` |
| `T1` 时段块 | 3 块（见下表） | 交易创建/改价/收款/回调/退货 |
| `T2` 日终 | 1 次 | `POST /api/admin/daily-aggregate` → `GET /admin/reconciliation` → `GET /admin/metrics/usage` |
| `T3` 周 | 7 营业日 | 客流系数（`[假设:A-19]`）；菜市场通常不休市 |
| `T4` 月 | 30 营业日 | `POST /api/admin/settlements` → 商户 EWA 更新 + 退出/作弊决策 + 市场方预算与继续决策 |
| `T5` 季 | 90 营业日 | 监管 Agent 抽检强度/补贴/考核口径 |

- **12 个月 = 360 营业日**（`Q5` 的判定窗口）。
- **决策频率的设计理由**：消费者**逐笔**决策（准连续）；商户**日频**更新信念、**月频**做结构性决策（退出/作弊模式/设备使用）—— 日频结构性决策会造成不现实的抖动，且现实中"换系统/搬走"是有周期的；市场方月频、监管季频。**这个频率分层是"有限理性"的一部分，不是实现方便。**

### 4.2 营业日内的时段块 `[源:Q-9 / P-13 —— 项目自己标注为"待确认假设"]`

| 时段 | 强度 | 依据 |
| --- | --- | --- |
| 05:30–06:00 | 开市准备（设价目表 / 复制上日价） | `REQ-003` `AC-015`；`结论 6`/`D-07`（营业前设价，现场不打字） |
| 06:00–09:00 | **主峰**（λ 最高） | `[源:Q-9]`（**项目自己标注为"待确认假设（行业常识，未经调研验证）"**） |
| 09:00–17:00 | 平峰 | 同上 |
| 17:00–19:00 | **次峰** | 同上 |
| 19:30 | 日终结算（闭市） | `REQ-018` |

> ⚠️ **口径纪律**：`Q-9`（主峰 06:00–09:00、次峰 17:00–19:00、单摊位日均 80–150 笔）在本项目里**不是查证事实**，是被明确登记为"待确认假设"的未决项。仿真**沿用**它，但**必须在报告里标注为项目已知假设**，且 `Q5` 的存活区域分析必须包含对它的敏感性 —— **否则就是拿一个未验证假设去支撑"能活过 12 个月"的结论。**

### 4.3 一个营业日的伪代码

```
for d in business_days(n_days):                       # T0
    business_date = d
    market_admin.allocate_maintenance_budget(d)       # 月频则仅月初执行
    for stall in active_stalls:                       # 商户日初决策
        if merchant.wants_price_list(stall):          # 意愿通道：不想用的商户直接跳过
            POST /api/merchant/price-list (copy_from_previous_day=True)
    devices.advance_one_day()                         # 故障/维修推进 → A_i, W_q
    for block in [主峰, 平峰, 次峰]:                    # T1
        for arrival in poisson(lambda_block):         # 到达过程
            j = consumer.pick_stall(category)         # logit
            a = merchant.choose_action(j, d)          # comply / evade / exit
            if a != exit and not shadow:
                POST /transactions → [price-change] → payment(cash|qr) → [callback] → [refund]
            else:
                sim_ledger.record_shadow_sale(...)    # 系统不可见（§6 口径来源标注）
            j.update_trust(scan_result)               # §3.3.2
    admin.post_daily_aggregate(business_date)         # T2
    observe.record_day(...)
    if is_month_end(d):                               # T4
        for stall in active_stalls: POST /admin/settlements; merchant.update_EWA(); merchant.decide_exit()
        market_admin.decide_continue_or_reduce()
    if is_quarter_end(d): regulator.update_intensity()  # T5
```

### 5.1 参数网格与重复

- **单因子敏感性（OAT）**：`[假设]` 参数逐项取 `{p10, p50, p90}`（或区间端点），其余固定在 `S0`。
- **全局敏感性**：拉丁超立方抽 `N=512` 组 `[假设]` 参数（标准库 `random` + 分层抽样即可，**不需要 numpy**），报告每个参数的秩相关（自写 Spearman，约 30 行）。
- **蒙特卡洛重复**：`L1` 主结论用 `R = 20`（§2.6 的两级预算），报告**均值 + 90% 区间**，不报单次结果。`R` 的取值理由：§7.1 的判据绝大多数是**序关系**而非绝对值，20 次足以分辨"效应量大"的组间差异；**若某条判据在 `R=20` 下区间重叠，则该判据降级为"不稳健"并如实报告，不得靠加大 `R` 去凑显著性**。

### 6.9 存活判据 `S` 的定义（`Q5` 的唯一口径，四个阈值全部标为假设）

```
存活(12 个月)  ⟺  ① CumCash(360) ≥ 0                      市场方 12 个月累计净现金流不为负
                ∧  ② 第 360 日在营摊位数 ≥ 70% × 期初       商户侧没散
                ∧  ③ 第 300–360 日平均 ScaleUseRate ≥ 60%   系统没被绕过（用真实交易占比，不是装机量）
                ∧  ④ TrustIndex(360) ≥ 0.5                  顾客还信（否则标签已作废）
```

- **四个阈值（`0` / `70%` / `60%` / `0.5`）全部是 `[假设]`**，无一有调研出处。**这一条必须直说**：`Q5` 的"能活过 12 个月"因此不是"事实证明"，而是"在我们定义的存活语义下的参数区域"。
- **它们的合法性来自外部对照，而不是数值本身**：唯一能约束它们的是 §7.1 `R5`（温州口径必须落入存活区）与 `R1`–`R3`（失败口径必须落入失败区）。**若需要调整阈值才能让两组对照同时成立，那说明模型判别力不足，必须如实报告 —— 不许调阈值凑结果。**
- 报告 `Q5` 时**必须四条分别给**（哪一条不满足），**不得**只给一个"存活 / 不存活"的布尔值。
- `60%` 这一门槛的旁证：`D-09` / `REQ-022` 已把验收口径从"装机量"改成"使用率"，故"走秤率"确是这套设计自己的成败判据；但**取 60% 而不是 50% 或 70%，是本设计的假设，不是需求规定的。**

## 7. 验证与校准（本节最重要）

### 7.1 第一层：复现已知现象（可否证伪的判据）

**方法**：把《报告》里的历史案例翻译成"参数设置 → 期望现象"的对照实验（pattern-oriented modeling 的用法）。**每条判据都写明"若不复现意味着什么"**。

| # | 参数设置（历史口径） | 期望现象（判据） | 若不复现意味着什么 | 出处 |
| --- | --- | --- | --- | --- |
| `R1` | 向商户抽佣（`S1-①`，2%）+ **无**免维护承诺 | `t_first_exit ≤ 6` 个月（**绝对阈值的出处是 `结论 8` 的真实时间量级"数月即垮"**，不是我们拍的）；12 月 `ExitRate` 显著高于 `S1-②`（0% 组），90% 区间不重叠；`ScaleUseRate` 单调下降 | 说明模型缺少"抽佣 → 走秤变贵 + 转暗变划算"的耦合 → 机制假设被推翻 | `[源:结论 9]`（**2‰ 就已被国务院督查并全额退还** → 2% 必然更严重，这是**单调性判据**，比绝对阈值更硬）`[源:结论 10]`（商户搬离）`[源:结论 8]`（"数月即垮"→ 约束 `t_first_exit` 的量级） |
| `R2` | 不抽佣 + 市场方出资 + **统一检定维修**（衡阳/杭州口径） | 与 `R1` 组**严格优于**：`ScaleUseRate` 高于 `R1` 组、12 月 `ExitRate` 低于 `R1` 组（90% 区间不重叠）、`DeviceIdleRate` 低于 `R1` 组；且与 `S0` 基线**无显著差异**（即"免维护"这一项单独就能把结局拉回基线） | 说明"免费+免维护"的正向机制没写对 | `[源:结论 14]` `[源:D-02]` |
| `R3` | 维护预算 `0.3×` | `W_q` 上升（`R3-a`）；`DeviceIdleRate` **显著高于足额预算组**（`R3-b`，区间不重叠）**且逐期加速上升**（`R3-c`）；`ScaleUseRate` 更低（`R3-d`，0.3× 组低于足额组，且自身逐期单调下降）。**`B`（维护预算）的绝对方向不作为判据** —— 理由与修订留痕见下方「`R3-c` 判据修订留痕（2026-10-03）」。绵阳案例给的量级参考（**2020 年投放 → 2022-09 回访**，跨度约 **21–32 个月**，报告未交代投放月份）**只用于判断"是否落在同一量级"，不作为通过/不通过阈值** | 观测不到加速 → "死亡螺旋"假设被推翻 | `[源:结论 6]` `[源:结论 4/5]`（武汉：2021 回访 20+ 市场仍闲置，318 家改造市场） |
| `R4` | 扫码页只有空壳字段（无采集来源）vs 有真实来源 | 空壳组 `TrustIndex` **单调不增**且 `t_half = ∞`（或 > 12 个月）；真实来源组 `T` 收敛到高位。**两组序关系必须成立** | 信任更新的不对称权重没起作用 → `Q3` 的"能否恢复"无从回答 | `[源:结论 16]`（"扫过好几次空码、无效信息之后，**再也不信**这个标签了"） |
| `R5` | 温州口径：向买方 0.5%–6% + **不收摊位费** + 出门查验凭证 | 存活 12 个月（§6.9 判据）；第 12 月摊位占有率 ≥ 期初 | 模型把"向买方收"和"向商户收"当成同一件事 → 这是本设计最需要避免的建模错误 | `[源:结论 12]`（**2001 年经温州市物价局批复，运行至今 20 余年**） |
| `R6` | **反例检验（防"怎么调都能活"）**：商户自费购秤（3750–4600 元/台 + 云软件 5000/年） | 走秤率**必须显著低于**市场方出资组 | 若自费组活得一样好，说明模型里的"自费"没有真实成本 → `结论 26` 的断言（"让商户自己掏钱买秤，基本等于注定被弃用"）无法被检验 | `[源:结论 26]` `[源:结论 14]` |

**绝对阈值 vs 序关系的取舍原则（写死）**：
- 凡**有真实数据**支撑量级的（秤价、费率、补贴比例）→ 可以用绝对阈值；
- 凡**关键参数无数据**的（MTBF、维修价、罚款、扫码基线、信任权重、退出阈值）→ **只允许用序关系 / 单调性 / 区间不重叠**作为判据，**禁止**用绝对月份/绝对比率。理由：在无数据处给精确阈值，等于把假设包装成事实 —— 这正是 `Q-19` 教训（"不验证灵敏度的验证是摆设"）的同类错误。

#### `R3-c` 判据修订留痕（`2026-10-03`，父代理裁定）

**① 原判据（已被本条取代）**：`B` 与 `ScaleUseRate` 同时单调下降。

**② 为什么它按原文永远不可能成立（实测，不是推断）**：本模型里维护预算 `B` 是**市场方的内生决策变量**，不是外生政策旋钮。`KPI=usage` + 使用率低 + 决策迟滞 6 期 ⇒ 每期把预算**上调**约 25%。`T-SIM-08` 在 `S-约束` 档（240 营业日）实测到的 0.3× 组预算序列是
**1.5e6 → 1.68e6 → 1.875e6 分**（单调**上升**）。故原判据的"单调下降"子句恒不通过。

**③ 根因**：判据把两件事**混为一谈**——
* **外生政策**：`R3` 的对照实验**人为**把预算压到 `0.3×`（这是实验设定，成立）；
* **内生响应**：压低之后市场方**自己**会根据 KPI 把预算调回去（这是模型行为，也是待检验的现象）。

原判据判的是后者（内生响应的绝对方向），而实验设计只能保证前者。

**④ 改成了什么（逐子句对应，无删项）**：`R3-c` 由「`B` 单调下降」改为**只判结果量** ——
**0.3× 组的 `DeviceIdleRate` 逐期加速上升**（后半程斜率 > 前半程斜率，且全程单调不降）。
裁定要求的另外两项（`DeviceIdleRate` 显著更高、`W_q` 上升）分别由 `R3-b` / `R3-a` 判定，
`ScaleUseRate` 更低由 `R3-d` 判定 —— **四项结果量全部有子句覆盖，`B` 的绝对方向不再是任何子句的判据**。

**⑤ 这是规格修正，不是放宽阈值**：阈值一个都没动（`R3-a/b/d` 的形式、依赖参数、方向均未改），
改的是**被判量的选择** —— 去掉一个由对照实验无法保证、且与模型接线直接冲突的量。
`B` 的预算序列**仍然留在 `backtest.json` 里**（字段 `excluded_evidence`），使"为什么原判据不可能成立"
可被第三方从产物直接复核，而不是只留一句结论。

**⑥ 档位硬约束**：`market_decision_delay_periods = 6` ⇒ 预算调整 6 期后才生效，
**至少要 7 个仿真月 = 210 营业日**才测得到任何按期变化。**90 日档（3 期）必然测不到**，
`S-约束` 档取 **240 营业日（8 期）**满足该下限；`tests/sim/test_verify_backtest.py` 有机械守卫
（`R3` 及其子句所用档位的 `days` 必须 ≥ 210），改小档位会当场红。

**⑦ 重跑要求**：修订后必须重跑 `R3` 并重新判定，**本节不预先宣布 `R3` 成立**；
复现命令：`python -m sim --backtest --backtest-only R3 --out-dir data/sim/verify/R3`

**⑧ 重跑实测落点（`2026-10-03`，档位 `S-约束` 240 营业日 / 8 期 / R=2）** ——
**三态判定：`R3` = `不成立`**

| 子句 | 判什么 | 结果 |
| --- | --- | --- |
| `R3-a` | `W_q` 上升（0.3× 组 > 足额组） | ✅ **通过** —— 6.42 天 → **74.68 天**，区间不重叠 |
| `R3-b` | `DeviceIdleRate` 显著高于足额组 | ✅ **通过** —— 0.784 → **0.988**，区间不重叠 |
| `R3-c`（修订后） | `DeviceIdleRate` 逐期加速上升 | ⚠️ **不可评估** —— 0.3× 组逐期序列 `[0.947, 1.0×7]`：**第 1 期即触顶 1.0**，其后连续 **7** 期持平 ⇒ 形状判据（斜率）在本档**没有观测空间**。按父代理 `2026-10-03` **第二层裁定**：**饱和判 `不可评估`，不判 `不通过`**；明令不得写成「触顶即视为非加速」 |
| `R3-d` | `ScaleUseRate` 更低且逐期单调下降 | ✅ **通过** —— 0.055 → 0，且逐期单调降到 0 |

- **`R3` 级三态：`不成立`**（收敛规则 `backtest.verdict_of`：**子句含 `不可评估` ⇒ `不成立`**，不可评估 ≠ 通过）。
- **`R3-c` 的 `不可评估` 既不支持也不否证「加速型死亡螺旋」**：本档**测不出**加速（饱和）⇒
  四类性质里它归 **① 不可评估**（`docs/sim-验证结论实况.md` V-05）。
- **量级与形状是两件事（不得混成一句）**：`R3-a/b/d` 说明死亡螺旋的**量级**在本档**复现了**
  （等待 6.42→74.68 天、闲置 0.784→0.988 且区间不重叠、走秤率单调归零）；`R3-c` 只管**形状**。
- **稳健性扫描**（无出处参数推到区间端点）：`repair_cost_cents=1e4` 与 `=1e5`、
  `device_mtbf_days=1095` 三处**序关系翻转**（退化成 `A=B`，即预算档位不再成为约束）。
  因已有子句不是 `通过`，按 `verdict_of` 的收敛规则报 `不成立`。
- **被移出判据的预算序列（可复核证据）**：0.3× 组逐期 **1500000 ×5 期 → 1680000 → 1875000 分**，
  逐期**单调上升** —— 与第 ② 条的实测一致（前 6 期完全不动，正是迟滞 6 期；90 日档连这一步都走不到）。

**⑨ 「另补一个不饱和档位」的实测结果：找不到，且有根因（`2026-10-03`，父代理第二层裁定第 3 条）**

裁定要求"把 0.3× 组闲置率调进 **0.8~0.95**、不触顶，那一档的结果才是 `R3-c` 的结论"。
**实测：24 个候选档位里没有一个满足**，且原因不是"没调到"，而是**两条结构性约束互斥**：

| 扫描 | 维度 | 结果 |
| --- | --- | --- |
| 维修单价 | `repair_cost_cents` = 1.6e6 / 1.45e6 / 1.4e6 / 1.3e6 / 1.2e6 / 1.0e6 / 0.9e6 / 0.8e6 | 一降到 1.45e6 以下，足额组与 0.3× 组的 `M-10` **几乎相同**（0.7842 vs 0.7833，`R3-b` 的区间不重叠失效）；0.3× 组仍是**末尾 3 期贴 1.0** |
| MTBF | `device_mtbf_days` = 12 / 20 / 30 / 45 / 60 / 90 / 120 / 180（× `repair_cost` 1.0e6 与 1.4e6） | **16 组全部**在末尾 3 期贴 1.0；MTBF 越大两组越接近（180 天时 0.5675 vs 0.5675） |

- **根因（实测，不是推断）**：`M-10` **口径①「摊位-日闲置」的饱和，直接成因是**该期**走秤率为 0**。
  取 MTBF=180 的 0.3× 组逐期对照：`M-04 = [0.594, 0.479, 0.305, 0.183, 0.727, **0, 0, 0**]`、
  `M-10 = [0.400, 0.400, 0.500, 0.711, 0.333, **1.0, 1.0, 1.0**]` ⇒ **走秤归零的期，闲置必然是 1.0**。
  于是"闲置率不触顶" ⟺ "该期还有摊位在走秤"。
- **两条互斥约束**：要让 `R3-c` 可判（闲置率不触顶）就必须 0.3× 组**不塌缩**；一旦它不塌缩，
  足额组与它**落回同一个数**（上表 0.7842 vs 0.7833、0.5675 vs 0.5675）⇒ `R3-b` 的「区间不重叠」失效。
  **即：在本模型 + 240 日档上，「`R3-c` 可判」与「`R3-b` 成立」互斥。**
- **由此得到一条更值得记的事实**：`M-10` 口径①与 `M-04` 在**走秤归零后是同一条信息**
  （`idle = 1` ⟺ `scale = 0`），所以修订后的 `R3-c` **不是**对 `R3-d` 的独立检验 ——
  要一个**真正独立**的设备死亡螺旋指标，应改用 `M-10` **口径②（设备-日，停摆 > τ）**，
  它不依赖是否还有人在走秤（但 τ_repair 无出处，只能用序关系）。
- **本轮不自行实施**（改判据形式超出"照裁定执行"）：上述两条候选改法交由负责人决定，
  已登记在 `docs/PROJECT-STATE.md` 的「仿真线未完成清单 / 接手落点」。
- **复现命令**：探针不常驻仓库（一次性取证脚本），但判据与扫描维度已登记在
  `sim/verify/r_criteria.py::BINDING_PROFILE` 的 `why` 里；重跑本条只需按上表维度改
  `BINDING_PROFILE["param_overrides"]` 后执行第 ⑦ 条的命令。

### 7.2 第二层：敏感性、稳健性与"结论能不能用"

1. **单因子扫描 + 全局 LHS（§5.1）**，报告秩相关排序。
2. **稳健性判据（写死）**：若某条结论在任一 `[假设]` 参数的合理区间内**翻转**，则该结论标记为 **「不稳健，不得作为论证依据」**，并在报告里与稳健结论**分区展示**。
3. **存活区域面积**：`Q5` 的答案不是"能活"或"不能活"，而是 —— 在 `[假设]` 参数空间上**存活区域的体积占比** + **最敏感参数** + **温州/失败组是否落在预期分区**。若存活区域只占极小体积（例如需要所有参数同时取极值），**必须如实报告"该设计对参数高度敏感"**，不得只说"存在能活的组合"。
4. **对未验证项目假设的强制敏感性**：`Q-9`（单摊日均 80–150 笔、主峰时段）必须在敏感性清单里，因为它支撑着容量与存活分析。

### 7.3 第三层：model ↔ live 一致性（证明"不是纸上模型"）

**做法**：同一批 agent 决策序列（同一 `seed`，`events.jsonl` 里记录每个决策的完整参数），分别喂给 `model_adapter` 与 `live_adapter`，逐日比对：

| 比对项 | 容差 | 依据 |
| --- | --- | --- |
| 当日走秤笔数 | 完全相等 | `REQ-018` 日聚合 |
| 当日总额 `gross_amount_cents` | 完全相等（整数分） | `REQ-020` 对账等式 |
| 当日佣金 | 完全相等 | `REQ-017` 按实收金额 |
| 三指标（含 6 个分子分母） | 完全相等 | `AC-005`「第三方可逐一核对」 |
| 结算单金额 | 完全相等 | `AC-023` |
| `reconciliation.balanced` | 全营业日 `true` | `AC-003` |

**外加三条硬证据（live 模式自己的）**：
1. **31/31 端点被真实调用**（覆盖率清单落盘，缺一不可）；
2. **幂等真的生效**：故意重放同一 `Idempotency-Key` 与同一支付回调 → 笔数不变、`replayed/is_duplicate` 出现（`AC-010`）；
3. **敏感字段零命中**：对 live 模式跑出的全部响应体与数据库文件跑一次敏感扫描 —— **现成可复用的三个原语**：`tests/contract/sensitive_scan.py::scan_json_for_sensitive(payload, where)`、`scan_text_for_sensitive(text, where)`、`scan_db_file(db_path)` → 与 `AC-012` 同一判据，**不另立一套正则**（同一个规则写两遍就是下次漂移的种子）。

**灵敏度负例（必须有，否则这套验证是摆设）**：故意篡改 model 侧一处（例如让 model 少记一笔），一致性检查**必须变红**；还原后必须复绿。**"不验证灵敏度的验证是摆设"是项目自己的规矩**（`T-036` 家族），仿真验证没有豁免权。

### 7.4 循环论证风险登记（自曝，不藏）

| 风险 | 具体形态 | 处置 |
| --- | --- | --- |
| **信任恢复的循环论证** | `Q3` 问"信任能否恢复"，而"能否恢复"几乎完全由 `η⁻/η⁺/δ` 决定 —— 我们设定"恢复慢"，自然就得出"恢复慢"。**这是本设计最站不住的一处** | ① 不给点值，只给区间；② 结论必须表述为**关于参数的命题**（"当 `η⁻/η⁺ > k` 时存在不可恢复区"），不表述为关于现实的命题；③ 用 `结论 16` 的**定性语义**（"再也不信"）作为区间的下界依据，并明确说明这是**语义推断而非测量** |

### 7.5 校准方案的三个档次（哪些有真数据、哪些只能假设）

**档 1 · 锚定（有真实出处，直接用）** —— 见 §9 的 `sourced` 条目：秤/摊位屏/网络的真实中标价、补贴比例与上限、微信通道费率、温州买方费率、上海商户自费口径、验收抽检比例、行政罚款量级（市场开办者）、银行合作资金量级。**注**：`Q-9`（单摊日均笔数、主峰时段）**不在本档** —— 它是项目自己登记的待确认假设，实现里标 `assumed`（见 §2.5 的裁定与 `P-13` 行的说明），故它进的是**强制敏感性清单**而不是"可直接使用"。

**档 2 · 匹配矩（用历史案例的定性特征当"矩"）** —— 把 `R1`–`R6` 作为 6 个**定性矩**（"2% 组必须比 0% 组差""自费组必须比出资组差""空壳组信任不得恢复"…），在 `[假设]` 参数空间上做网格/拒绝采样，找**同时满足全部 6 个矩**的区域。这就是 ABM 领域的 pattern-oriented modeling；**点名它是领域方法，不假称它来自本项目调研**。
- **匹配目标的可用性必须逐条说明**：成都青羊案例给了**时间**（2024-10 运营、数月即垮）→ 可用于约束退出时滞；龙南案例只有**方向**（商户搬离）→ 只能约束符号；温州案例给的是**20+ 年存活**→ 可用于约束存活区的存在性。
- ⚠️ **可用矩的总数只有 6 个，而待定参数有 20 项** → **"过度拟合 6 个定性矩"是真实风险**，必须靠 §7.2 的敏感性把"结论对哪些未校准参数敏感"讲清楚，而不是假装校准完整。

**档 3 · 不可校准 → 敏感性替代** —— `[假设:A-08]`（信任权重）、`[假设:A-11/A-12]`（MTBF/维修价，**《报告》第九节自己承认"设备每年坏多少、修一次多少钱，没有公开数据"**）、`[假设:A-14]`（短秤罚款）、`[假设:A-15]`（日常计量抽检基准）、`[假设:A-09]`（扫码基线，`结论 17` 承认"缺乏统计"）。**处置**：全域扫描 + 报告结论对它们的依赖强度，**不给它们编精确值**。

### 7.6 可复现与"不改被测系统"的最后两道闸

1. **同 seed 逐字节可复现**（§2.4）；不同 seed 分布重叠但不相同。
2. **仿真跑通不得要求改 app 业务逻辑**：`--mode=live` 的验证脚本在运行前后对 `app/**`、`specs/**` 取哈希，**必须不变**（唯一例外是 `T-SIM-00` 已获批的时钟接缝，且该改动必须在仿真任务之前独立提交、独立评审）。

> ⚠️ **计数纪律**：任务书口述称"抽佣 4 次失败"，但仓库内**只有 3 例**有出处（第 4 例"宁波 / 台州临海半年内闲置"检索零命中，见附录 A）。**故 `Q5` 的失败对照按 3 例执行**，不得把口述的第 4 例算进"已知现象复现"的判据数 —— 否则就是拿一个没有出处的案例充当校准矩。

## 12. 附录 C：与 `spec.md` 的关系（不改规格的部分与必须改的部分）
