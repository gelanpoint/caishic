# 演示游戏美术资源方案

> 对口规格：`specs/market-trade-flow/spec.md` 的 `REQ-048`（美术资源必须是仓库内本地文件 + 由仓库内脚本可复算生成）
> 与 `AC-037`（`app/static/**` 机械扫描零外网地址）。
> 产物生成器：`scripts/gen_game_art.py`；产物：`app/static/game/sprites/**`。
> 本文件是**方案与取舍的唯一说明处**；脚本里只留数据与机械校验，不复述本文件的论证。

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 用什么格式 | **PNG 精灵表（sprite sheet）+ JSON manifest**；6 张表 / 32 个精灵 / 合计 2592 字节 PNG + 4119 字节 manifest |
| 调色板怎么定 | **固定 24 色**（含 1 个统一描边色），高饱和、暖色调、无渐变无混色；`--check` 机械验证 PNG 每个不透明像素都落在这 24 色内 |
| 尺寸与网格 | tile **16px**；摊 32、秤 24、人物 16×24、商品 16、道具 32/16；显示放大只用**整数倍**（建议 3×/4×）+ 关闭插值 |
| 可复算怎么保证 | PNG 只写 `IHDR/IDAT/IEND`（**不写 `tIME`/`tEXt`/`pHYs`**）、每行固定 `filter 0`、zlib 参数逐项写死、JSON 固定键序；实测三个解释器（zlib 1.2.11 / 1.2.13 / 1.3.2）产出**逐字节相同** |

**验证边界（先说清楚，别让读者以为它更强）**：这些像素画是**程序生成**的，不是美术师手绘；
下面的"观感取舍"是**我的设计选择**，**风格接近度是主观判断** —— 本方案**不宣称"与开罗游戏一致"**，
只说我在哪些维度上做了靠拢、哪些维度明确没做（§2.2）。此外 §8 列了已知未做项。

## 1. 探索问题一：用什么格式？

### 1.1 结论

**PNG 精灵表 + JSON manifest**。每张表是一张 PNG，manifest 记录「精灵名 → 表名 + 表内像素矩形」，
引擎按**名字**取图、不关心布局。

### 1.2 为什么不选其它四种（逐项对比，含各自真实优点）

| 方案 | 断网可用 | 体积/性能 | 像素锐利 | 可复算 | 与引擎解耦 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **PNG 精灵表 + manifest（选用）** | ✓ 仓库内本地文件 | 6 张表合计 **2.6KB**；浏览器原生解码并缓存 | ✓ 关闭插值 + 整数倍放大即硬边 | ✓ 脚本生成，删产物重跑逐字节一致 | ✓ manifest 是唯一契约，改布局不动引擎 | **选用** |
| 逐像素 SVG | ✓ | 一个 16×16 tile 就要约 256 个 `<rect>` 节点，6 张表上万节点；DOM/解析成本高 | ✗ 默认抗锯齿，需 `shape-rendering="crispEdges"` 且仍要整数缩放 | ✓ 文本可 diff | ✗ 布局嵌在 SVG 里，改名要动文件 | 否决：**体积/性能/锐利度三输** |
| CSS `box-shadow` | ✓ | 每像素一条阴影（人物 16×24 = 384 条） | ✗ 边缘同样要跟抗锯齿斗 | ✗ 难生成、难审、难 diff | ✗ 美术塞进样式表 | 否决 |
| JS 内联数组（每像素一个数） | ✓ | 32 个精灵约 2 万个数字，且要写进**引擎的文件** | ✓ | ✓ | ✗ 把美术塞进 `game` 的写作用域，引擎文件还会被顶爆行数 | 否决：**职责越界** |
| data-URI PNG | ✓ | base64 比二进制膨胀约 1/3 | ✓ | ✓ | ✗ 二进制混进 CSS/JS，**不可评审**；每改一次要动引擎文件 | 否决 |
| 逐帧 GIF / WebP / APNG | — | — | ✓ | ✗ 编码器会写时间戳等不可控字段 | — | 否决（本期也**不需要**动画帧，见 §8） |

### 1.3 为什么 manifest 由脚本生成，而不是手写

manifest 里的 `w/h` 是 **PNG 的实际像素尺寸**、`x/y/w/h` 是**表内矩形**。若手写，改一次布局就要
同步改三处（画布尺寸、绘制偏移、manifest 矩形），**迟早漂移且不会报错**（错的是"图能显示但错位"）。
故 `scripts/gen_game_art.py` 的布局表 `SHEETS` 是**唯一来源**：同一张表既决定 PNG 尺寸、又决定
manifest 矩形，两者由同一段代码推出，**结构上不可能不一致**。

**取值原则**：① **一色多用**（表中标注"兼"的都是），把色数压到 24 —— 色板越小，画面越像"同一套";
② **亮/暗成对**（`skin`/`skin_shade`、`leaf`/`leaf_dark`、`steel`/`steel_dark`），只用**两档平涂**
表示体积，**不做渐变**；③ 三个身份的**上衣色彼此拉开**（橙红 / 蓝 / 青），远处一眼能分角色；
④ 只允许 **alpha = 0 或 255**（无半透明），`--check` 会机械拦截中间值 —— 半透明一进来，"有限色板"
就名存实亡了。

### 2.2 我靠拢了什么、明确没做什么（**这是取舍说明，不是"还原"**）

**靠拢的维度（作为设计目标）**：俯视视角；小网格（16px）单元；高饱和有限色板；统一深色描边；
暖色调为主（地面沙色、木色、橙红棚顶）；摊位以"棚顶条纹 + 货台 + 价签"三件套构成，远处即可识别。

**明确没做（也不打算在本期做）**：① 开罗系那种**斜 45° 的体素/建筑投影与高度差** —— 我的精灵是
**正俯视 + 正面平涂**，没有透视，人物和摊位都是"贴纸式"的；② 手绘级的细节密度（花纹、材质、光影层次）；
③ 逐帧动画（走路/称重/翻页）。

**因此**：说它"像素风、俯视、暖色调、有限色板"是**可核验的**（色板与尺寸都在文件里）；
说它"像开罗游戏"是**主观判断** —— 本方案**不宣称与开罗游戏一致**，也不把它当验收判据。

## 3. 探索问题三：尺寸与网格

### 3.1 精灵尺寸（manifest 是权威，引擎**不要硬编码**）

| 类别 | 精灵名 | 尺寸 | 说明 |
| --- | --- | --- | --- |
| 地形 | `tile_floor` / `tile_path` / `tile_grass` / `tile_water` | 16×16 | **铺满整格、无缝平铺、不描边**（描边会破坏拼接） |
| 摊位 | `stall_0`…`stall_3` | 32×32 | 2×2 格；棚顶条纹与台面货物**一起**变，四个摊位一眼可分 |
| 智能秤 | `scale_idle` / `scale_active` | **24×24** | 1.5 格；见 §3.3 |
| 人物 | `person_{boss,customer,admin}_{down,up,left,right}` | **16×24** | 宽 1 格、高 1.5 格，**脚在底边**（引擎按底边对齐即可站在格上） |
| 商品 | `item_0`…`item_7` | 16×16 | 1 格；8 个蔬菜轮廓彼此可分 |
| 道具 | `prop_computer` | 32×32 | 管理员桌上的电脑 |
| 道具 | `prop_crate` | **16×16** | 菜筐（与电脑同表但尺寸不同，故引擎必须读 manifest 而不能按表推） |

**为什么 tile 是 16px**：16 是"一个 tile 内还能画出一条描边 + 两档明暗"的最小实用尺寸；
再小（8px）人物五官与秤屏读数就没了，再大（32px）地图格子数会掉到个位数、俯视走位看起来像"小人国"。
地图尺寸由引擎定，16px 下 24×16 格 = 384×256 像素，放大 3× 即 1152×768，正好一块常见屏。

### 3.2 显示放大：只用整数倍，并关闭插值

- **整数倍**（建议 3× 或 4×）：非整数倍（如 2.5×）会让像素**落在半个像素上**，出现宽窄不一的
  "糊边/断行"，像素风的硬边就没了。故地图与精灵一律用整数缩放系数。
- 画布绘制前 **`ctx.imageSmoothingEnabled = false`**；若用 `<img>`/CSS 直接展示，加
  `image-rendering: pixelated`。
- **每个精灵四周留 1px 透明隔离带**（`GUTTER = 1`）：manifest 里的 `x/y/w/h` **已经是隔离带内侧的
  实际像素矩形**，引擎直接用即可。隔离带的作用是：万一引擎漏了关插值、或画布 backing store 因
  `devicePixelRatio` 出现非整数缩放，双线性采样最多只会吃到 1px 外 —— 那是**透明**，不会把隔壁
  精灵的边缘吃进来（否则会出现"每个精灵都镶着邻居的一条边"的经典串色）。
- 地面重复感：地形每种只有 **1 个 tile**，平铺后规律可见。这是**本期取舍**（见 §8）；若引擎想要
  变化，可以对同一 tile 做水平/垂直翻转（对 `tile_grass`/`tile_water` 完全无损，因为它们本身近对称）。

### 3.3 智能秤为什么能"一眼看出是秤"（`REQ-047` 的交互落点）

24×24 里画了三件结构性特征，缺一不可：**① 顶部显示屏头**（带 12×6 屏幕）、**② 中间立柱**、
**③ 底部秤台**（20×4 平板 + 两只支脚）。`idle` 与 `active` 的差异有**两处**（不是只有颜色）：

| | 屏幕 | 秤台 |
| --- | --- | --- |
| `scale_idle` | 暗灰底 + 两条 `steel` 短横（待机 `--`） | 空 |
| `scale_active` | **绿底 `screen_on`** + `ink` 点阵读数 **`25`**（3×5 自绘数字） | 台面右侧**放着一颗待称商品**（`fruit_red` + `leaf_dark` 蒂） |

## 4. 探索问题四：可复算怎么保证？

### 4.1 PNG 里哪些字段会让"重跑不一致"，逐个消除

| 易变来源 | 为什么漂 | 本方案的处理 |
| --- | --- | --- |
| `tIME` chunk | 写入编码时刻的时间戳 | **不写**该 chunk（chunk 清单恒为 `IHDR/IDAT/IEND`，§7 有实测） |
| `tEXt`/`zTXt`/`iTXt` | 常见编码器写 `Software`、`Comment`、`Creation Time` | **不写** |
| `pHYs` | 物理像素密度，可能带上环境相关值 | **不写** |
| zlib 压缩参数 | `level`/`strategy`/`memLevel` 不同 ⇒ 不同压缩字节 | `compressobj(9, DEFLATED, 15, 8, Z_DEFAULT_STRATEGY)`，**五项逐个显式写死**，不吃默认值 |
| 逐行自适应滤波 | 编码器按启发式**逐行**选 filter，换版本/换启发式就变 | **每行固定 `filter 0`（None）**，不做自适应 |
| chunk 顺序 / IDAT 分块 | 多块 IDAT 与顺序可自由选择 | 固定 `IHDR → IDAT → IEND`，**单块 IDAT** |
| JSON 键序与空白 | dict 序、缩进、有无末尾换行 | `sort_keys=True` + `indent=2` + 末尾换行 + `ensure_ascii=False` |
| 文件写入顺序 / 目录遍历 | `os.listdir` 序不保证 | 按 `SHEETS` 的**固定顺序**写；`--check` 比对按名字排序 |
| 时间戳/权限/文件系统 | 内容与 mtime 无关 | 产物只由字节决定，不依赖 mtime/chmod |

### 4.2 实测证据

1. **删产物重跑逐字节一致**：7 个文件的 `sha256sum` 两次完全相同（§7 ①）。
2. **PNG chunk 清单恒为 `IHDR/IDAT/IEND`**，6 张表全一致（§7 ④-D）。
3. **跨解释器一致（这条最硬）**：同一份脚本、同一份像素数据，在**三个不同 zlib 运行时**下产出
   逐字节相同的 7 个文件：

   | 运行环境 | zlib 运行时 | 与仓库产物比对 |
   | --- | --- | --- |
   | 系统 Python 3.10.12 | 1.2.11 | 基准（仓库产物由它生成） |
   | 仓库 `.venv` Python 3.12.15 | 1.3.2 | **7/7 逐字节一致** |
   | Windows Python 3.10.11 | 1.2.13 | **7/7 逐字节一致** |

4. **`--check` 自带复算**：`python scripts/gen_game_art.py --check` 会**现场重新生成到临时目录**再与
   现有产物逐字节比对。也就是说，复算能力不靠"上次测过"，而是**每次自检都真的重算一遍**。

### 4.3 这条能力的**边界**（不吹）

- **deflate 输出不受 zlib ABI 保证跨版本一致**。"三个版本一致"是**实测事实**，不等于"所有版本都一致"。
  这也是为什么 §4.2 第 4 条要把复算做成**每次现场比对**，而不是在文档里写一句"保证一致"。
- 若某天换到输出不同的 zlib，`--check` 会**变红**（这是设计意图：宁可报红，也不静默漂移）。
- 可复算覆盖的是**产物字节**，不覆盖"观感"：换一版绘制代码，产物当然会变 —— 那是**改版**，
  应当连同 manifest 一起重新评审，而不是当成"复算失败"。

## 5. 冻结的接口契约与取图方式

manifest 结构（`app/static/game/sprites/manifest.json`）：

```json
{
  "version": 1,
  "tile_px": 16,
  "sheets":  { "<sheet名>": { "file": "<文件名>.png", "w": 128, "h": 64 } },
  "sprites": { "<精灵名>": { "sheet": "<sheet名>", "x": 0, "y": 0, "w": 16, "h": 16 } }
}
```

- `sheets.*.w/h` = **该 PNG 的实际像素尺寸**；`sprites.*.x/y/w/h` = **表内像素矩形**（已含隔离带内侧）。
- 取图唯一路径：读 manifest → 按精灵名取 `{sheet,x,y,w,h}` → `sheets[sheet].file` →
  `drawImage(img, x, y, w, h, dx, dy, w*scale, h*scale)`，`scale` 为整数。
- **精灵名不得改名、不得少**（`--check` 机械比对最小集，见 §7 ③）。要加可以加，改名/删名即红。

6 张表：`terrain.png` 72×18、`stalls.png` 136×34、`scales.png` 52×26、`people.png` 72×78、
`items.png` 72×36、`props.png` 68×34。共 **32 个精灵**。

## 6. 复现命令汇总

```bash
# 生成（幂等：重复跑结果相同）
python scripts/gen_game_art.py

# 自检：重生成逐字节比对 + 矩形在表内 + PNG 尺寸与 manifest 一致 + 24 色板封闭 + 最小集无缺
python scripts/gen_game_art.py --check

# 生成到别处（不碰仓库产物）
python scripts/gen_game_art.py --out /tmp/gga

# 删产物重跑，逐字节还原（验收 ① 的原始形态）
sha256sum app/static/game/sprites/* > /tmp/a.sha
rm -rf app/static/game/sprites && python scripts/gen_game_art.py
sha256sum -c /tmp/a.sha
```

## 8. 已知未做 / 已知边界（诚实清单）

1. **程序生成，不是手绘**：所有像素由 `scripts/gen_game_art.py` 的图元组合画出，**没有美术师参与**。
   风格接近度是主观判断，本方案只说明取舍（§2.2）。
2. **没有逐帧动画**：人物只有 4 个**静态朝向**，没有走路循环；秤没有"数字跳动"帧；棚顶没有飘动。
   本期演示靠引擎做位移/高亮来表达动作。
3. **地形每种只有 1 个 tile**：平铺后规律可见。若要变化，引擎可对 tile 做翻转（§3.2）。
4. **没有阴影层与光照**：只有精灵自带的两档平涂暗面 + 统一的 1px 描边。没有投射阴影、没有昼夜变化。
5. **PNG 未做体积优化**：为可复算固定了 `filter 0` + 固定 zlib 参数，代价是体积（6 张表合计 2.6KB）。
   在这个量级上，"逐字节可复算"远比"再省 1KB"重要；若日后素材量涨到 MB 级，需重评这条取舍。
6. **`scale_*` 是 24×24，与 tile 16px 不成整数比**（1.5 格）。这是有意的：秤要能放下"显示屏 + 立柱 +
   秤台"三件结构才认得出（§3.3）。引擎**必须按 manifest 的 `w/h` 定位**，不能假设"所有精灵都是 tile 的整数倍"。
7. **交付包只含已跟踪文件**：`scripts/build_submission.py` 用 `git archive HEAD` 打包，
   故 `scripts/gen_game_art.py` 与 `app/static/game/sprites/**` **必须 `git add` 进提交**，
   否则演示包里没有美术资源（页面会是一片空白/色块，且**不会报错**）。
8. **脚本的 stdout 编码**：`main()` 在 stdout 被重定向时强制 UTF-8（`AGENTS.md` §3 的现场教训：
   输出编码不许依赖 locale / 控制台代码页）。这条只影响**提示文字**，不影响产物字节；
   实测修复前 Windows 控制台经管道捕获会出现乱码。
