## 1. 背景与约束

- **规模与成本敏感**：目标 100 台。单台成本直接决定方案能否落地（BOM 与出处见 `docs/hardware/秤端硬件选型与成本.md`）。
- **现场环境**：潮湿、油烟、粉尘、震动、宽温；**无专职运维**（`NFR-002` 已放宽「尽力而为」）。
- **功能面**（`ADR-0005` §3）：选品 → 称重 → **本地计价** → 收款码展示 → 本地持久暂存 → 网络恢复后补传。
- **计价必须与中台权威实现逐位一致**。权威实现 `app/domain/pricing.py` 的三条口径：
  1. `金额(分) = (单价(分/公斤) × 重量(克) + 500) // 1000`（`half_up_div`，**四舍五入，不是银行家舍入**）；
  2. 金额与重量**全程整数**（分 / 克），**不引入浮点**；
  3. 抹零只减总额、不计入标价一致率；改价计入。
- **宪法 §1 现行**：语言仅 Python 3.11+；框架 Flask；存储 SQLite（标准库）；运行形态原生进程。
- **可验证性约束**：本项目对「不可复现的验收等于没有验收」有明确纪律（`AGENTS.md` §3、交付铁律 1/2）。固件若无法在无硬件条件下被检验，就不该进入本仓库。

## 2. 候选方案对比

| 维度 | 方案 A：ESP-IDF（C）**采纳** | 方案 B：MicroPython on ESP32-S3 | 方案 C：嵌入式 Linux 单板 + Python |
| --- | --- | --- | --- |
| 满足需求程度 | 高 | 中 —— 能力够，但确定性与可审计性弱 | 高 |
| 开发成本 | 高 —— UI、协议、存储、称重驱动均自建 | 中 | 低 —— 与中台同语言，计价代码可来回复用 |
| 运维成本 | 低 —— 单一固件产物 + OTA | 低 | 中 —— 系统镜像、启动脚本、依赖版本 |
| 回退成本 | 中 | 低 | 中 |
| 迁移成本 | 低 —— 协议不变即可整层替换 | 低 | 低 |
| 团队熟悉度 | 中（本项目新增技能面） | 中 | 高 |
| 单台 BOM 量级 | 最低 | 最低 | 显著更高 |

> 方案 C 由负责人在选型时**已明确排除**，此处保留是为了让「为什么不用与中台同语言」这件事有据可查，不是为了重新翻案。

## 3. 决策与理由

**采纳方案 A：ESP32-S3 + ESP-IDF（C 语言）。** 理由逐条追溯到 §1：

1. **确定性**：计价是整数定点运算。C 的 `int64_t` 语义明确、无隐式大整数、无解释器版本差异；MicroPython 需额外证明其整数行为与序列化格式跨固件版本稳定，而这正是「两份实现漂移」最容易藏身的地方。
2. **可审计的持久化**：离线队列必须满足「绝不静默丢弃」（`RL-9` / `NFR-014`）。把队列写成 LittleFS 上的**定长记录 + CRC**，比在解释器堆上操作文件更可审计、更容易在断电场景下证明不丢。
3. **成本**：ESP32-S3 模组单价见硬件文档（出处可查），显著低于嵌入式 Linux 单板；100 台规模下这一项是决定性的。
4. **UI 路径成熟**：LVGL 在 ESP-IDF 上是成熟组合，可支撑「图标选品 + 数字键盘 + 二维码」这类界面，满足 `AC-006`（全程无文本输入、交互 ≤3 次）。

### 3.1 与 MicroPython 的取舍边界

若 `scale-fw/core/` 的复杂度预算被突破（见 §5 触发条件 1），**允许**把上层 UI 与网络编排改为 MicroPython，
但**计价与离线队列核心必须留在纯 C 的 `scale-fw/core/`** —— 这两处的正确性由 golden vectors 钉住，
换语言即等于换掉被验证过的那份实现。

### 3.2 本决策的代价与对冲（**缺一不可**）

C 侧计价是 Python 权威实现的**第二份实现**，这是「两套实现漂移」的经典风险。对冲三条：

| # | 对冲手段 | 为什么它不可省 |
| --- | --- | --- |
| a | **固件业务核心不依赖 ESP-IDF**：`scale-fw/core/` 为纯 C（仅 `<stdint.h>` / `<string.h>` / `<stdbool.h>`），可在**主机侧**编译并跑单元测试 | 没有它，固件逻辑在无硬件时完全不可验证；本机的验证路径为 `zig cc -target x86_64-linux-musl`（免 sudo、不依赖系统 libc/dev 头文件，实测可用） |
| b | **golden vectors**：由 `scripts/gen_pricing_vectors.py` 从 Python 权威实现导出，覆盖 0/1 克、50 公斤边界、半值四舍五入、抹零、改价；产物**可复算**，禁止手改 | 没有它，「逐位一致」只是口头承诺；向量集即交叉实现的**可执行契约** |
| c | **中台重算比对**：中台收到秤端上报后用权威实现重算，不一致即告警留痕，且**以中台结果入账** | 没有它，秤端被篡改或算错会直接污染账目；有它则中台始终是唯一账口 |

## 4. 后果

**正面**：

- 成本、功耗、确定性三方面最优；单一固件产物便于 100 台版本一致性管理（含 OTA）。
- 固件核心可在**主机侧**被单元测试覆盖，满足本项目的可验证性纪律。

**负面**（不得粉饰）：

- **偏离宪法 §1**：语言不再只有 Python。**已按宪法 §6 走完修订程序**（`2026-10-06` 负责人批准；单人交付场景按 `constitution.md` §8 的「角色帽子」映射），宪法 §1 已就地增设**秤端例外**并记录为 `v1.2`（见该文件 §1 与 §8）。**本 ADR 状态为 `已接受`，据此写固件代码不再受门禁阻塞。**
- 本项目技能面从「单一 Python」变为「Python + 嵌入式 C」，评审与测试成本上升。
- **无硬件在环能力**：本机（WSL2）无 ESP32-S3，无法验证真实称重采样、触摸、WiFi 射频与断电行为。可验证边界 = 主机侧核心逻辑 + 协议编解码；硬件在环登记为未决项 `Q-21`。
- 交叉实现的验证成本是**持续性的**：任何一次计价口径变更，都必须同时更新 Python 权威、golden vectors 与 C 实现，三者不一致时以用例变红为准。

## 5. 重新评估触发条件

1. `scale-fw/core/` 的纯 C 核心无法在既定复杂度预算内覆盖需求（说明选型与需求不匹配，须回到 `ADR-0005` §2 重评）；
2. golden vectors 中出现**无法用整数运算表达**的口径（即 Python 权威侧被迫引入浮点）——那说明计价口径本身需要重新设计，而不是 C 侧需要放宽；
3. 单台 BOM 成本超出硬件文档给出的**推荐档上限**（成本优势不再成立）；
4. 无硬件在环这一缺口导致**实际交付事故 ≥1 次**；
5. 若固件侧需要引入非白名单第三方组件（RTOS 之外的库、闭源 SDK），须另立 ADR —— 参照 `ADR-0004` 的依赖范围纪律执行。
