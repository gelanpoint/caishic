## 1. 背景与约束

关键数字与硬约束：

- **目标形态：100 台秤端 ↔ 1 个中台**（单市场 100 个摊位）。秤端分布在摊位现场，中台集中部署。
- **秤端在物理上无法集中**：秤是本方案唯一的物理锚点（`discovery.md` D-03），必须位于摊位。
- **断网是常态而非例外**：`REQ-014` 要求断网继续交易并在本地持久暂存；`REQ-015` 要求恢复后按客户端幂等键补传；`NFR-013` 要求补传成功后清除本地副本；`NFR-014` 要求绝不静默丢弃。
- `NFR-001`：峰值并发 <20（演示级）。`NFR-008` 现行文本为「**不适用**：全部本机访问，无跨网络调用」——**本 ADR 使该前提失效**。
- 宪法 §4「运行形态约束：本期为单机原生进程」；宪法 §1 语言仅 Python 3.11+（固件侧的偏离另立 `ADR-0006`）。
- 现场演示硬要求（`AGENTS.md` §3）第 3 条：**必须支持同机双浏览器窗口**分别扮演秤端与顾客端。

**本 ADR 的关键判断：这不是「微服务拆分」。**

`docs/standards/architecture.md` 的决策树问的是「要不要把单体拆成多个**服务**」（叶子 c）。其微服务触发条件清单是 **AND 不是 OR**，本项目逐条对照：

| 清单项 | 本项目实测 | 是否满足 |
| --- | --- | --- |
| 1. 2 个以上长期稳定团队（各 ≥3 人） | 单人交付 | 否 |
| 2. ≥2 模块发布节奏差异 ≥4 倍且已被事故证明 | 无此证据 | 否 |
| 3. 具备服务治理能力（发现/追踪/灰度） | 无 | 否 |
| 4. 有专人负责平台与运维（P2 要求 7×24） | `NFR-002` 已放宽「尽力而为」 | 否 |
| 5. 单体内模块化已被尝试并证明不够 | 未尝试，现行模块边界清晰 | 否 |

**五条全否 ⇒ 不选叶子 c。** 本次拆分的动因是**部署拓扑**：出现了一类**物理上必须位于摊位现场的设备**。这与「把中台拆成多个服务」是两件事：

- 中台内部**仍是叶子 a 单体**（一个代码库、一个进程、一个 SQLite），`ADR-0001` 继续有效；
- 新增的是一层**边缘节点**，它自己不构成服务网格里的服务，也不引入服务发现、网关、MQ。

故本 ADR 的定位是**在叶子 a 之外增加边缘层**，而不是升级到叶子 c。

## 2. 候选方案对比

| 维度 | 方案 A（默认方案）：维持单机 all-in-one | 方案 B：秤端边缘固件 + 中台中心服务（**采纳**） | 方案 C：100 台秤各跑一个完整单体 |
| --- | --- | --- | --- |
| 满足需求程度 | **低** —— 无法表达「100 个商家各一台秤」；秤端与中台无法分机部署 | **高** —— 与目标形态一致；`REQ-014/015` 的补传链路正是为此设计 | 高（单机功能上） |
| 开发成本 | 0（即现状） | 中 —— 新增固件侧实现 + 中台新增设备接入端点与市场维度 | 高 —— 100 份含佣金/结算/看板的单体 |
| 运维成本 | 低 | 中 —— 100 台固件的烧录与版本一致性；但设备侧无运维值班要求（`NFR-002` 已放宽） | 极高 —— 100 份数据库各自备份，口径漂移无法收敛 |
| 回退成本 | — | **低** —— 单机形态**保留不动**，分离形态是新增启动方式；回退 = 不启动固件 | 高 |
| 迁移成本 | — | 中 —— 中台需加市场维度与设备绑定 | 高 |
| 团队熟悉度 | 高 | 中 —— 中台侧是既有 Python 代码；固件侧（ESP32-S3 / C）为本项目新增技能面 | 中 |

> 方案 C 单独列出，是因为它是「100 个商家」这句话最直观的误读：**秤端不该承担佣金与结算**。
> 佣金口径必须唯一，否则 100 台秤会算出 100 套账 —— 这与本项目「数据可信度优先于功能数量」的核心主张直接冲突。

## 3. 决策与理由

**采纳方案 B。** 理由逐条追溯到 §1 的数字与约束：

1. **动因是物理部署，不是组织规模**：秤必须在摊位（§1），而佣金/结算/看板必须在数据汇聚处。两端分离是物理约束的直接推论，不是架构偏好。
2. **既有需求已为此铺好路**：`REQ-014`（断网继续交易 + 本地持久暂存）、`REQ-015`（按客户端幂等键补传、成功后清除本地副本）、`NFR-013`、`NFR-014` 描述的就是秤端↔中台这条链路。现行实现把「补传的对端」指向了同库（`app/domain/offline.py::sync_queue` 内直接调 `create_transaction`）——**本 ADR 是把对端从「自己」换成「中台」，不是新造机制**。
3. **不选叶子 c**：见 §1 的五条对照，全否。
4. **中台仍是单体、账口唯一**：新增的秤端接入端点在实现上**复用 `app/domain/pricing.py::create_transaction`**，中台侧不出现第二份记账实现。秤端只做「本地计价 + 上报」，佣金/日聚合/结算/看板一律留在中台。
5. **单机形态保留**：`AGENTS.md` §3 硬要求 3（同机双窗口）与既有 540 条用例依赖单机形态，本 ADR **不破坏**它；分离形态是**新增启动方式**，同机双进程即为分离形态的特例。

## 4. 后果

**正面**：

- 与「100 秤 ↔ 1 中台」的目标形态一致；秤端无佣金/结算逻辑，**账口唯一**。
- 单机演示形态保留，既有用例与现场演示脚本不受破坏。
- 离线链路从「模拟断网」变为**真实网络断连**，`AC-003` 的对账等式有了更硬的意义。
- 中台获得市场维度后，**第二个市场无需改表结构**即可装载。

**负面**（本 ADR 必须写清，不得粉饰）：

- **`NFR-008`（传输加密）的豁免理由失效**：原文本以「全部本机访问、无跨网络调用」为由判为不适用。拆分后跨网络调用真实存在，须重新登记放宽理由，并把 TLS 列为演进项（未决项 `Q-20`）。**本期采用「受控局域网 + 设备令牌 + 禁止暴露公网」**，这是放宽而非达标。
- **计价出现两份实现**（中台 Python 权威 + 秤端 C 本地计价）。对冲办法见 `ADR-0006` §3：(a) 固件核心不依赖 ESP-IDF、可主机侧编译测试；(b) 由 Python 权威实现导出 golden vectors 逐位比对；(c) 中台收到上报后用权威实现重算比对。**三者缺一，本 ADR 的结论不成立。**
- 中台数据模型新增市场维度，18 张表与 31 个端点均受影响，属**大范围改动**，须新迁移脚本且不得改写既有迁移。
- 新增固件版本一致性管理负担（协议不兼容风险）。`NFR-002` 已放宽运维承诺，但固件漂移是**本项目自行引入**的风险，不能拿 `NFR-002` 当挡箭牌。
- 本机（WSL2）**无 ESP32-S3 硬件**，固件无法做硬件在环验证，只能验证到「主机侧核心逻辑 + 协议编解码」。此项登记为未决项 `Q-21`。

## 5. 重新评估触发条件

可检查的具体条件，任一命中即须重开本 ADR：

1. 秤端数量超过 **500 台**，或单市场摊位规模使中台单进程写入成为瓶颈（参照 `R-003` SQLite 单写者风险）；
2. 出现**第二个市场**且需要跨市场结算、跨市场权限或跨市场报表（本 ADR 只保留市场维度，**不交付**多市场运营流程）；
3. 固件版本不一致导致的协议不兼容**实际发生 ≥1 次**；
4. 中台的设备接入端点出现**除秤端以外的第二类终端**（电子价签、摊位屏等，现行 `spec.md` §6 第 7 条仍排除）；
5. 秤端↔中台的计价比对告警在真实使用中**持续出现**（说明两份实现已漂移，须回到单一权威实现）。
