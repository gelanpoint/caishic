## 1. 背景与约束

- 宪法 §1 的「**依赖白名单**」原文为：`Flask`（及其在 `requirements.txt` 中锁定的传递依赖）/ **Python 标准库（一律允许）**。
  **该条目没有限定"运行期"还是"含开发期"** —— 按最宽的字面理解，它会把**测试框架与覆盖率工具**一并管住。
- 而实现环节的质量门禁需要测试与度量工具：`specs/market-trade-flow/tasks.md` 的 `T-007`~`T-014`（契约测试）
  与 `docs/standards/quality-gates.md` 的**行覆盖率 ≥90%/≥70%** 都要求一个测试框架与覆盖率工具。
  **若按字面执行，这一条会在 `T-007` 一开工就撞上。**
- **根因判断（关键，决定了本 ADR 的走向）**：这不是"缺了依赖"，而是**条款表述不清** ——
  宪法 §1 的表格标题是「**允许的技术栈**」，同表其余条目（运行形态、依赖来源）**语境都是运行期**，
  唯独白名单段没有写这个限定语。**把两期混在一条白名单里，本身就是条款缺陷。**
  因此正确的动作是**澄清条款**，而不是"破例把测试库塞进白名单"。
- 既有约束（决定了边界的保守方向）：
  - 演示机为**自有笔记本**、**一条命令启动**、**不依赖外网**，现场故障面要最小
    （`docs/adr/0003-技术栈偏离参考默认值.md` §1、`specs/market-trade-flow/spec.md` §1.2）；
  - 运行期依赖每多一项，现场就多一个装不上的可能 —— 这是 `ADR-0003` 收紧技术栈的**原意**。

## 2. 候选方案对比

| 维度 | 方案 A：按字面执行（白名单管全部依赖，测试只用标准库） | **方案 B（选定）：澄清条款 —— 白名单界定为运行期，开发期工具单列** | 方案 C（否决）：把 `pytest`/`coverage` 写入运行期白名单 |
| --- | --- | --- | --- |
| 满足测试与门禁需要 | 勉强：`unittest`（标准库）可跑测试；覆盖率只能用 `trace`，**没有分支覆盖率** —— 直接削弱 `quality-gates.md` 的覆盖率门禁 | 满足：成熟测试框架 + `coverage`（含分支覆盖） | 满足 |
| 现场风险（演示机） | 最低 | **低**：`requirements.txt` 仍只有 `Flask`，开发期清单不进演示机 | **高**：演示机被迫安装测试框架这类无用依赖 |
| 条款清晰度 | **固化模糊**：下次加测试工具仍要重新纠结"算不算白名单" | **清晰**：两期边界写死，新增测试工具不再需要改宪法 | 也清晰，但方向错：把开发期东西治理成运行期资产 |
| 长期治理成本 | 每次都要临时判断 | 一次性澄清（1 个 ADR + 宪法 §1 一节 + 1 个机械检查） | 每个开发工具一次 ADR 评审 |
| 回退成本 | — | 低（改回一处表述即可） | 中（已进入运行期清单，回退要再走评审） |

> **不粉饰方案 A 的优点**：A 的优点是**零新增概念**、与 `ADR-0003` 的现场稳定诉求最一致。
> 它被否决的理由是：**把"条款表述不清"固化下来**，代价会在下一次（以及每一次新增测试工具时）重复支付；
> 而 B 的收益是**条款变清楚**，成本可控且**边界可以机械验证**（见 §3 第 3、4 条）。

## 3. 决策与理由

**结论**：

1. **宪法 §1 的依赖白名单约束"运行期依赖"**（表述已在宪法 §1 就地修订，并保留修订记录）。
2. **开发期工具单列**：`pytest`、`coverage` **仅限开发与测试期使用**；
   **不得出现在 `requirements.txt`、不得被 `run.py` 或 `app/**` 引用**；
   其清单独立为 `requirements-dev.txt`（**不进演示机**）。
3. **机械检查（必须带灵敏度验证）**：用标准库 `ast` 扫描 `run.py` 与 `app/**` 的全部 `import`，
   确认不含任何开发期依赖；**故意在 `run.py` 里 `import pytest` → 检查必须变红**，移除后恢复绿
   （对应 `tasks.md` `T-007` 与 `T-036` 的同类做法）。
4. **端到端实证**：在一个**只安装了 `requirements.txt`** 的干净环境里，`python run.py` **必须能启动** ——
   这才是"演示机只装 `Flask`"的真凭据，不是口头承诺（对应 `tasks.md` `T-035`）。

**理由（逐条）**：

1. **根因是表述缺陷，不是依赖缺口**（§1 末）—— 修条款比破例更根本；一版让人分不清"白名单管不管测试框架"的宪法，下次还会绊人。
2. **保住了 `ADR-0003` 的原意**：演示机的运行期依赖**仍然只有 `Flask`**，现场故障面不增加。
3. **不把成本转移给人工**：方案 A 下"没有分支覆盖率"会把验证成本推给每个任务的人工核对；
   而这是**涉钱系统**（`P2`），`quality-gates.md` 的覆盖率门禁需要可靠度量。
4. **边界可验证，不靠自觉**：第 3、4 条两条检查都是机械的，且**按 `AGENTS.md` 要求自带灵敏度验证** ——
   "不可靠的约束等于没有约束"。

> **本 ADR 只界定依赖范围，不改运行期技术栈**：`Flask` + 标准库 + 纯静态前端 + 原生进程这一组选择不受影响。

## 4. 后果

**正面**

- 演示机运行期依赖**仍然只有 `Flask` 一项**，与 `ADR-0003` 的现场稳定目标一致。
- 开发期获得成熟工具链（`pytest` + `coverage`，**含分支覆盖**），支撑 `quality-gates.md` 的覆盖率门禁。
- 两期边界写死并可机械检查，未来新增测试工具**不再需要修订宪法**。

**负面（诚实记录代价，不粉饰）**

- **多出两个清单文件与一次宪法修订**："哪个文件该装什么"需要人记住 —— 防线是 `T-007` 的 `ast` 隔离检查与 `T-035` 的干净环境实证，**不能靠记忆**。
- **演示机上跑不了自动化测试**：`requirements-dev.txt` 不装到演示机，因此回归只能在开发机做。
  本期可接受（演示以人工走查 + 开发机回归为准），但**若评委要求现场跑测试，需重评**（见 §5 第 2 条）。
- **开发期依赖也是依赖**：`pytest` / `coverage` 自身的漏洞**不在**"运行期漏洞响应"（`quality-gates.md` §1.1）适用范围内。
  该边界明确写在 `quality-gates.md` §1.1 与其引用的本 ADR 中，**避免"高危 24 小时"的适用范围含糊**。
- **本次宪法修订属人工评审范围**：技术批准人 = 父代理（客户接口人由父代理另行报备）。
  该修订为**澄清性修订**，**不改变运行期技术栈与任何安全红线**；修订记录见 `constitution.md` §8 与 `docs/PROJECT-STATE.md`。

## 5. 重新评估触发条件

**任一触发即重评本 ADR 的范围界定**：

1. **项目转为生产化部署**（与 `ADR-0003` §5 第 1 条联动）—— 届时需重评发布流水线与依赖锁定策略（含漏洞扫描与 SBOM）。
2. **演示形态变为"必须在演示机上跑自动化测试"**（如评委要求现场执行测试）—— 需重评依赖清单的分离方式。
3. **开发期工具出现无替代的高危漏洞** —— 需重评工具选型；**注意：退路不是"把工具塞进运行期白名单"**（方案 C 已被否决）。
4. **第 3、4 条检查的自身成本超出预期** —— 退回**方案 A（按字面执行：测试只用标准库）**，
   此时退回是**基于实测依据的判断**，而非预判。

> 本期状态：四条均未触发（单机演示环境，开发机与演示机为同一台自有笔记本，但**依赖清单已按两期分离**）。
