## 1. 背景与约束

- **架构叶子不变**：`docs/adr/0001-单体与嵌入式数据库.md` 已判定本期走决策树 `Q1` 小用户档 → `Q1b` → **叶子 a**（单体 all-in-one + 单容器 + 嵌入式数据库）。本 ADR **只偏离叶子 a 的参考技术栈，不偏离叶子本身**。
  > **与 ADR-0001 的关系**：本 ADR **覆盖 ADR-0001 中关于"单容器"的部署形态表述**（本期为单机原生进程、不用 Docker、不产出 `Dockerfile`）；
  > ADR-0001 的**叶子判定（单体 all-in-one + 嵌入式数据库）不受影响**。ADR-0001 已就此加注「部署形态注记（2026-09-30）」，两边表述一致。
- **参考默认值**（`docs/standards/architecture.md` §三，叶子 a 行）：Python 侧为
  **FastAPI + SQLite + 服务端模板 + Docker 单容器**。
- 本项目的硬约束（数字与事实来源）：
  - **本期实现范围**为**单市场、单机、一条命令启动、不依赖外网**、数据存本地（`specs/market-trade-flow/spec.md` §1.2）；
  - **峰值并发 <20**、现场同时操作 ≤3（`spec.md` §1.2 与 §4 `NFR-001`）；
  - **无专职运维**、演示环境为**单机**（`spec.md` §4 基线适用性复核）；
  - **演示机为自有笔记本、可提前安装环境**，不做免安装打包（负责人 2026-09-30 确认，`docs/PROJECT-STATE.md` `Q-13`）；
  - 交付物为**比赛作品**，生命周期 `3B`，无年度级移交承诺。

## 2. 候选方案对比

| 维度 | 方案 A：叶子 a 参考栈（FastAPI + Docker 单容器）**（默认方案）** | 方案 B：本项目选定（Flask + 标准库 `sqlite3` + 纯静态前端 + 原生进程） |
| --- | --- | --- |
| 满足需求程度 | 满足：单体单容器，本机可跑 | 满足：同为单体单进程、单库文件，且天然满足"一条命令启动、不依赖外网" |
| 开发成本 | 中：需处理 ASGI 运行方式与容器镜像构建 | 低：Flask 同步模型与标准库 `sqlite3` 直接可用，无构建、无镜像 |
| 运维成本 | 中：演示机需安装 Docker 并具备可用镜像来源 | 低：仅需 Python 3.11+ 与 `requirements.txt`，无容器运行时需维护 |
| 回退成本 | 中：需回滚镜像与容器编排 | 低：换回上一版代码与数据文件即可 |
| 迁移成本 | 低：如赛后容器化，无需迁移 | 中：若赛后转为容器化部署，需补 Dockerfile 与镜像构建（已在 §5 列触发条件） |
| 团队熟悉度 | 中：需熟悉 ASGI 与容器编排 | 高：同步框架 + 标准库，无额外治理能力要求 |

> 「运维成本」与「回退成本」两行为必填项，均已填。
> **默认方案是方案 A**：本 ADR 记录的是**显式偏离**，不是"默认值不存在"。

## 3. 决策与理由

**结论**：本期采用方案 B —— `Python 3.11+` / `Flask` / Python 标准库 `sqlite3` / 纯静态前端（HTML + 原生 JS + CSS，无构建工具、无 CDN）/ **原生进程 + 启动脚本**（`start.bat` / `start.sh`），不使用 Docker。

> **产物可用性说明**：本节及下文点名的 `run.py`、`start.bat` / `start.sh` 与 `requirements.txt`
> **均由实现环节创建，本阶段尚不存在**；本 ADR 只约定其**形态与行为**，不表示产物已存在
> （启动行为与现场演示硬要求见 `AGENTS.md` §3）。

**理由（逐条，均可追溯到第 1 节的约束）**：

1. **`sqlite3` 是 Python 标准库** —— 存储层不引入任何需要原生编译的第三方驱动。
   同类项目里 Node 的 `better-sqlite3` 需要本地编译，是常见的环境翻车点；
   走标准库可把"现场装不上"这一类故障从源头去掉。
2. **前端不用 npm、不用构建工具** —— 静态资源全部为仓库内本地文件，
   规避"现场执行安装/构建失败"这类事故；同时满足"不依赖外网"的硬约束。
3. **不用 Docker** —— 演示机无需安装 Docker、无需拉取基础镜像，
   对**离线演示**最稳；多一个容器运行时就是多一个现场故障面，而本期**没有对应的收益**（单进程、单库即可）。
4. **环境前提已闭环** —— 演示机为**自有笔记本、可提前安装环境**（第 1 节），
   因此不需要免安装打包；"换机部署需要重新装依赖"这一代价是可接受的。
5. **并发量级不需要 ASGI** —— 本期峰值并发 <20（第 1 节），
   Flask 的同步模型完全够用；引入 ASGI 与容器编排属于**对本期需求过剩**。

> 注意：**这不是"降低技术门槛"，而是把工程的确定性放在功能数量之前** ——
> 与 `spec.md` §1.1 的核心主张（数据可信度优先于功能数量）同向。

## 4. 后果

**正面**

- 交付与演示路径最短：`python run.py`（或双击 `start.bat`）即可跑起，无镜像、无构建产物。
- 现场故障面最小：无 Docker、无 npm、无原生编译依赖；不依赖外网。
- 换机成本可控：`requirements.txt` + Python 3.11+ 即可重建环境。

**负面（诚实记录代价，不粉饰）**

- **Flask 生态弱于 FastAPI**：**没有**自动 OpenAPI 文档生成、**没有**原生 async 支持；
  接口契约需另行维护（后续实现环节的契约文档不能指望框架自动产出）。
- **不用 Docker 意味着环境依赖靠 `requirements.txt` 与启动脚本保证**：
  **换机部署时需重新安装依赖**，环境一致性不如镜像可复现；
  版本漂移的防线只有"锁定版本"这一条。
- **性能上限低于 ASGI 栈**：若并发形态变化（见 §5），本栈是第一个需要重评的对象。
- **Web 服务器能力有限**：Flask 内置服务器适合单机演示，不具备生产级并发与静态资源服务能力。

## 5. 重新评估触发条件

**任一触发即重评本 ADR 的技术栈选择**：

1. **生命周期由 `3B` 升级为 `3C`**（如赛后转为长期维护、需要移交），或项目**转为生产化部署**
   —— 届时必须重新评估**容器化**与环境一致性方案；
2. **部署形态由单机变为多机 / 需要对外提供访问** —— 届时需重评 ASGI 栈、生产级 Web 服务器与独立数据库；
3. **峰值并发超过 `ADR-0001` §5 的重评估条件**（并发写入摊位数持续 5 分钟以上超过 20）
   —— 与 ADR-0001 的第 1 条触发条件联动，同时重评存储与运行形态。

> 本期状态：三条均未触发（单机演示环境）。
>
> **本 ADR 只改技术栈，不改架构叶子**：若重评结论触发叶子变更，须另写新 ADR，并按
> `docs/standards/architecture.md` §六「已接受的 ADR 只能被新 ADR 取代」处理本文件的去留。
