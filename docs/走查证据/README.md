## 走查过程中修掉的**走查自身**的错误（**都不是应用缺陷**）

| 现象 | 真实原因 |
|---|---|
| 「第二笔开不出来，交易号不变」 | 走查脚本的 `wait_txn_no` 只等"不是 —"，而成交后**旧号还在**，于是立刻返回旧号。**专项探针已证实应用支持不刷新连续开单**（`T-…0001 → T-…0002`） |
| 收款码那笔迟迟不进售后区 | 收款码是**异步**的，要等支付回调落地。第一版不等回调就开下一笔 |
| 离线那步永远超时 | `#pending` 的显示形态是 **`N / 阈值 …`**（如 `0 / 200 笔`），不是裸数字，正则写错 |
| 「补传结果」打的是旧文案 | 补传结果在 **`#syncResult`**，而 `#offlineNote` 由**另一条异步链**同步写入，第一版匹配到了补传前的旧文案 ⇒ **假绿** |
| 顾客页「字段白名单」取到空数组 | 选择器猜错（`[data-field]` 不存在）。**这也是假绿**：取到空数组却照常往下走，而"白名单多一个就算失败"正是差异化卖点 |

> 记这一笔是因为：**走查脚本自己出假绿，比走查失败更危险**。
> 五处里有三处是"断言通过但没验到东西"。

## 走查查出的**应用侧**结论

**秤端支持连续开单，不需要刷新页面。** 走查一度怀疑"付款后没有『下一笔』入口"，
专项探针实测：一笔付完后直接点商品 + 计价 ⇒ 交易号 `T-…0001 → T-…0002`、金额正确、无报错。
**秤端页面上确实没有"下一笔"按钮，但也不需要** —— 点商品即可开新单。
