# 非功能需求基线

> 本文件是 NFR 默认值的**唯一权威**。项目里任何位置需要这些数值时**只引用，不复述**。
> 本文件在本项目中的落位：`docs/standards/nfr-baseline.md`（已就地改造为**自包含**，
> 所有路径均为本仓库内路径，不依赖任何外部目录）。

## 一、怎么用

- `specs/market-trade-flow/spec.md` 的「非功能需求」一节**只写对本基线的偏离**，格式：
  `NFR-xxx: 偏离项 基线值 → 本项目值，理由: ……`
- **未偏离的条目自动生效，spec 不复述**（复述即违反单一事实来源）。
  > **偏离项里引用基线值是允许的** —— 那是变更记录（"从什么改到什么"），不是复述。
  > 被禁止的是把基线的**整张表或整批数值**抄进别的文件。
- **放宽**（比基线松）须给出理由并拿到同意，且**批准要落到文档里**；
  未获批前该项在 `docs/PROJECT-STATE.md` 里保持为未决项，**不阻塞 G2，但阻塞实现**。
- **收紧**（比基线严）随时允许，无需审批。
- **判断不出该用哪一列时，回到定级规则；仍不确定就按更高一级执行。**
- ⚠️ **P0 项目不要抄 P2 列** —— 个人工具追求 99.9% 是在浪费生命。
- ⚠️ **必须做一次「适用性复核」，不要不声不响地继承。**
  未偏离的行会自动生效，所以**没有人会主动去看它们** —— 这是本基线最大的盲区。
  填完 spec 后，扫一遍这几类最容易"照搬后不合理"的条目：
  **在线率、RTO、RPO、恢复演练频率、变更公告期**，拿它们和项目**实际**的运维能力对照
  （几个开发者？有没有专职运维？停机半天是否真的不可接受？）。
  明显不成比例的，明确处置：要么记为**放宽偏离**（需批准并留痕），
  要么在 spec 里写一行「已复核：本项目采用的级别列适用，予以采用」。
  **一条没人看过的要求，和一条不存在的要求，危害一样大。**

## 二、基线总表

列的含义：**P0** = 个人 / 一次性工具 · **P1** = 团队内部系统 · **P2** = 客户交付 / 涉钱 / 涉敏感数据

### 2.1 性能

| 条目 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 接口响应时间 | 可感知即可，不做承诺 | p95 < 1s，最慢单接口 < 5s | p95 < 500ms，p99 < 2s |
| 页面首屏加载 | 不承诺 | < 3s（常规办公网络） | < 2s（常规办公网络） |
| 吞吐能力 | 单用户顺序操作不报错 | 支撑分级对应的峰值在线人数（如内部系统按 50 并发设计） | 按合同容量指标，至少支撑峰值在线 500 并发，且留 50% 余量 |
| 大文件处理 | **不承诺上限**；要求单个 50MB 不报错（健壮性下限，不是可用上限） | 上传单个 ≤ 10MB；批量任务后台异步执行 | 上传单个 ≤ 50MB；批量任务必须异步且有进度可查 |
| 慢查询 | 不检查 | 数据库单查询 > 1s 须记录并优化 | 单查询 > 500ms 告警，> 2s 视为缺陷 |

### 2.2 可用性

| 条目 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 在线率 | 尽力而为，允许工作日重启 | 工作时间（9:00–18:00）99%，**约 2 小时/月**（见下方注） | 7×24 全年 99.9%，约 **43 分钟/月** |
| 计划停机 | 随时 | 提前 1 个工作日公告，放非工作时间 | 提前 3 个工作日公告 + 客户确认，放业务低谷窗口 |
| 备份频率与保留 | 重要节点手工备份 | 每日自动备份，**保留 14 天** | 每日全量 + 每小时增量，**保留 90 天**，跨机房/异地存放 |
| RTO（恢复时间目标） | 不承诺 | ≤ 4 小时 | ≤ 30 分钟 |
| RPO（数据丢失容忍） | 不承诺 | ≤ 24 小时 | ≤ 1 小时 |
| 恢复演练 | 不要求 | 每半年至少 1 次并留记录 | 每季度 1 次，演练报告归档 |

> **注**：原始材料写 P1 为「每月故障累计 ≤ 约 4 小时」，与「9:00–18:00 在线率 99%」不自洽 ——
> 9 小时/天 × 约 21.7 工作日 ≈ 195 小时/月，其 1% 约为 **2 小时**。
> 本文件按**算术正确值**写为 2 小时；如需放宽到 4 小时，应显式记为对基线的偏离并说明理由。

> **注**：备份保留期与恢复演练频率以**本表**为唯一权威。
> 若后续引入上线检查清单，该清单只能写「以 NFR 基线对应级别列为准，且上线前至少完成一次完整恢复演练」，
> **不得另写一套保留期天数**（同一事实两个数字必然漂移）。

### 2.3 安全

| 条目 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 身份鉴别 | 可单机无账号或简单口令 | 必须登录；接公司统一账号（SSO/企业微信/钉钉）优先；会话超时 ≤ 8 小时 | 强制 SSO + 双因素（管理员与财务操作必须）；会话超时 ≤ 30 分钟（高敏操作） |
| 权限控制 | 不细分 | 基于角色，服务端逐接口鉴权 | 角色 + 数据级权限；权限变更留审计 |
| 传输加密 | 可选 | 外部访问必须 HTTPS（内网可 HTTP，但建议 HTTPS） | 全链路 HTTPS / TLS 1.2+，含内网服务间 |
| 密钥管理 | 不入库即可 | 环境变量或 `.env`（不入 Git）；泄漏后 24 小时内轮换 | 密钥管理服务；定期自动轮换；泄漏即吊销 |
| 审计日志 | 不要求 | 关键操作（登录、审批、打款、权限变更）记录操作人 + 时间 + 结果，保留 180 天 | 全量操作审计；日志防篡改（只增不改/外发归档）；保留 ≥ 3 年或按监管要求 |
| 漏洞管理 | 发布前人工检查依赖 | CI 自动扫描；高危 7 天内修复 | 高危 24 小时内、中危 7 天内修复；每年至少 1 次渗透测试 |
| **数据脱敏** | 不要求 | **日志与测试环境**脱敏（手机号、银行账号掩码） | **展示层按角色脱敏** + 测试环境使用合成数据；**禁止生产数据直接下放** |

> **展示层脱敏属于 P2**。P1 项目如果做了展示层脱敏，那是"收紧"，允许；
> 但不要因为做了展示层脱敏就认为满足 P2 —— P2 还要求合成数据与审计。

### 2.4 可维护性

| 条目 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 代码规范 | 能跑通即可 | 统一格式化与静态检查，CI 强制 | 同 P1，另加圈复杂度与重复率门禁、架构分层依赖方向自动检查 |
| 测试要求 | 主流程手工验证 | 核心业务逻辑有自动化测试；覆盖率阈值见 `docs/standards/quality-gates.md` | 同 P1 且按 P2 列取值；涉钱路径必须有用例级对账测试 |
| 文档要求 | README 三行（是什么/怎么装/怎么跑） | README + ADR + 接口契约；新人按文档 1 天内跑起 | 同 P1，另加运维手册、应急预案、客户交付文档包 |
| 依赖管理 | 锁定版本 | 锁定版本 + 每月检查更新 | 锁定版本 + 每两周检查更新 + 依赖准入评审 |
| 变更追溯 | Git 提交即可 | 提交信息关联任务与需求编号（`T-xxx`/`REQ-xxx`） | 同 P1，且每次发布生成变更清单；涉钱变更经冷却期复核 + AI 交叉检查 |

### 2.5 可观测性

| 条目 | P0 | P1 | P2 |
| --- | --- | --- | --- |
| 日志 | 控制台输出 | 结构化日志（时间/级别/模块/请求 ID），落盘保留 30 天 | 集中日志平台，全链路请求 ID 串联，保留 ≥ 180 天 |
| 指标 | 不要求 | 基础指标：请求量、错误率、响应时间（可手工查看） | 指标看板 + 容量指标（磁盘/内存/连接数），历史保留 ≥ 90 天 |
| 告警 | 不要求 | 错误率突增、磁盘 >80%、服务宕机 三类告警，通知到负责人 | 5 分钟内触达值班人；分级告警；有认领与关闭流程 |
| 健康检查 | 不要求 | 提供 `/healthz` 存活接口 | `/healthz` + `/readyz` 就绪接口，接入负载均衡与自动重启 |

## 三、度量口径（怎么证明达标）

写完目标不等于能验收。以下是判定口径：

- **响应时间**：用压测工具统计 p95 / p99；采样 ≥ 一天真实流量，或压测 ≥ 1000 次。
- **首屏**：在「常规办公网络」（约 20Mbps、RTT ≤ 50ms）测 3 次取中位数。
- **吞吐**：以**错误率 < 0.1% 且 p95 达标**为前提下的稳定并发数。
- **在线率**：每 1 分钟探测 `/healthz`，连续 3 次失败记一次故障；计划停机不计入（P2 除外）。
- **备份有效性**：看「最近一次恢复演练是否成功」，不看备份文件是否存在。
- **密钥**：用 gitleaks 做全历史扫描，零命中。
- **漏洞**：超期未修复的高危漏洞数必须为 0。
- **文档**：做一次「新人 1 天内跑起」演练。

## 四、常见错误

1. 在 `specs/market-trade-flow/spec.md` 里复述基线数值 —— 只允许写偏离项。
2. P0 项目抄 P2 列 —— 浪费，且会把项目拖垮。
3. 判不准级别列时自己拍一个 —— 应回到定级规则；仍不确定按更高一级执行。
4. 把「不要求」当成「禁止做」 —— 基线是下限，做多了不违规。
5. 中途升级了项目级别却不重新核对列 —— 定级变化后必须重核本表。

> 第 3 条的「定级规则」指 `docs/standards/classification.md`。

## 五、本文件的维护

- 项目内本文件在启动阶段建立后，由项目自己维护。
- 修改本文件属于「改变基线」，须同步检查 `specs/market-trade-flow/spec.md` 里
  所有 NFR 偏离项的表述是否仍成立。
