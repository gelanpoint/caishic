# 架构决策树、默认值清单、ADR 规范

> 本文件是架构选型判据的**唯一权威**（决策树、默认值清单、微服务触发条件）。
> 本文件在本项目中的落位：`docs/standards/architecture.md`（已就地改造为**自包含**，
> 所有路径均为本仓库内路径，不依赖任何外部目录）。
> 项目里的 ADR 与 spec 引用决策树分支时，一律按本文件的编号，不复述条件。

## 一、核心立场

> **默认答案永远是先单体。** 任何偏离默认的选择，都必须落一份 ADR 才能执行。

微服务是组织与工程能力成熟后的「拆分权」，不是起点。拆错服务的代价，
远大于「单体跑久了再拆」的代价。

**P0 直接取默认**：单体 all-in-one + 单容器，不走决策树、不写 ADR。

## 二、决策树

先看 **Q1 用户规模/并发** 分档，再决定要不要继续往下问。

```
Q1 用户规模 / 并发
│
├─ 总用户 < 100 且 高峰同时在线 < 20
│   └─ Q1b 有没有「明确可预期的集中峰值」？
│       ├─ 没有，或峰值在单机承受范围内  → 叶子 a：单体 all-in-one （默认）
│       └─ 有明显峰值（峰值为日常 10 倍以上）→ 叶子 b：单体 + 独立数据库 + 缓存
│   （此档不需再答 Q2/Q3/Q4）
│
├─ 总用户 100–10000，或 高峰同时在线 20–500
│   ├─ Q2 核心业务表一年内会超 100 万行？单库会超 50GB？
│   │   ├─ 都不会 → 去 Q3
│   │   └─ 会     → 叶子 b：单体 + 独立数据库（按需缓存），并在 plan 登记容量规划
│   ├─ Q3 有 2 个以上团队，且各模块独立上线、节奏明显不同？
│   │   ├─ 否 → 叶子 b
│   │   └─ 是 → 去 Q4
│   └─ Q4 故障停服 1 小时会造成直接资金损失或合规事故吗？
│       ├─ 否 → 叶子 b（用部署冗余解决可用性，而不是拆服务）
│       └─ 是 → 对照微服务触发条件清单：
│               ├─ 全部满足 → 叶子 c：微服务
│               └─ 任一不满足 → 叶子 b（在 ADR 里记录放弃微服务的原因）
│
└─ 总用户 > 10000，或 高峰同时在线 > 500
    → 超出本树覆盖范围，升级架构评审。
      评审结论出来前仍按叶子 b 起步。
```

**关键**：小用户档不再答 Q2/Q3/Q4；Q2 答「会」直达叶子 b；Q3 答「否」直达叶子 b；
**Q4 答「是」不等于微服务**，必须再过清单。

### 微服务触发条件清单（**必须全部满足**，AND 不是 OR）

> 任何一项答「否」，结论回落到叶子 b。

1. 有 **2 个以上长期稳定的研发团队**（每个团队 ≥3 人），各自独立背交付；
2. 至少 **2 个模块的发布节奏差异 ≥4 倍**，且互相阻塞已被**实际发生的事故/延期**证明；
3. 团队具备（或已采购）**服务治理能力**：服务发现、分布式链路追踪、统一日志、灰度发布；
4. 有**专人负责平台与运维**（P2 项目还要求有 7×24 值班能力）；
5. 单体内的**模块化改造已被尝试并证明不够**。

## 三、三片叶子的形态

| 叶子 | 形态 | 参考技术栈（**默认提案，须与用户确认后再写入项目**） |
| --- | --- | --- |
| **a**（默认） | 一个代码库、一个进程、一个嵌入式或同容器数据库、一个容器（或一台小机器）跑全部 | Python：FastAPI + SQLite + 服务端模板 + Docker 单容器；Node.js：Express/NestJS + SQLite + 服务端模板 + Docker 单容器 |
| **b** | 单体 + 独立数据库（按需缓存），可多容器编排 | Python：FastAPI + PostgreSQL + Redis + Docker Compose；Java：Spring Boot + MySQL + Redis + 单 JAR |
| **c** | 按业务域拆 2–5 个服务起步，各自独立数据库与部署 | 轻量版：各服务 FastAPI/NestJS + 各自 PostgreSQL + MQ + 网关；体系化：Spring Cloud，或 K8s + 服务网格（仅当清单第 3、4 项已确认） |

> 叶子 a/b 都必须遵守**模块边界约束**（模块间只经明确接口调用），
> 这是"以后能拆"的前提。
>
> **本项目采用叶子 a，但参考栈已按 `Q-13` 决策替换**（`Python 3.11+ / Flask / 标准库 sqlite3 /
> 纯静态前端 / 原生进程 + 启动脚本`，不用 Docker）—— 替换理由与现场稳定性硬要求见
> `docs/PROJECT-STATE.md` `Q-13`；**该偏离已落 ADR：`docs/adr/0003-技术栈偏离参考默认值.md`（`已接受`）**。
> **本表的参考栈是提案，不是本项目的选型结论。**

## 四、默认值清单（速查）

**默认选择不需要 ADR**，但结论要一句话写进方案文档。

| 决策项 | 默认答案 | 触发「要」的条件（任一） | 备注 |
| --- | --- | --- | --- |
| 消息队列 | **不要**，用同步调用 / 后台任务表 | 耗时 >10s 且用户无需等待的任务；两模块需解耦且允许分钟级延迟；需削峰（峰值写入超数据库瞬时能力） | 用「数据库任务表 + 轮询」能解决的不引入 MQ |
| 缓存 | **不要**，先直查数据库 | 同一数据分钟级被读 >100 次且变化频率低；或慢查询治理后接口 p95 仍超基线阈值 | 缓存内容必须可从数据库重建；**先加索引再加缓存** |
| 全文搜索 | **不要**，用数据库 LIKE / 内置全文索引 | 搜索字段 >3 个且数据 >10 万行，LIKE 查询 p95 >1s；或需要分词、高亮、相关度排序 | 数据库内置全文检索够用时不上独立搜索引擎 |
| 文件存储 | **单机磁盘卷**（带备份） | 需多副本/跨机器 → 对象存储；总量预计 >100GB 或增长 >10GB/月 → 直接对象存储 | **文件一律不存数据库**；路径与元数据存数据库 |
| 定时任务框架 | **不要**，用系统 cron / 框架自带调度 | 任务 >5 个、需失败重试与执行历史、或需分布式防重 | P2 的涉钱任务必须有执行审计日志 |
| 多环境 | P0：单环境；P1：dev + prod | P2 强制三环境，且 staging 与 prod 配置同构 | 与上线检查项对应 |

## 五、估不出规模时怎么办

- **边界档位拿不准**：往哪边走都行，但**必须在方案里记录按哪一档决策、以及触发重新评估的条件**；
  **不确定就按更重的一档起步**（成本差异在单体范畴内很小）。
- **估不出峰值**：用业务日历估 —— 找出最集中的场景（如月底 3 天、月初 1 天），
  用 `总用户 × 该场景参与率 ÷ 集中小时数` 估算；
  仍估不出就先按叶子 a 起步，把「观测到真实峰值后重走 Q1b」写进 ADR 的重新评估触发条件。
- **禁止**回答「可能会很多」「大概不少」。要给数量级。

## 六、ADR 规范

### 存放与命名

- 目录：**`docs/adr/`**
- 文件名：**`NNNN-决策标题.md`**（四位连续编号 + 短横线 + 简短标题；
  本项目实例：`0001-单体与嵌入式数据库.md`、`0002-环境策略-单环境.md`）
- **全项目只选这一套命名，禁止 `ADR-001.md` 与 `0001-标题.md` 两种写法并存。**
- 编号全项目连续，不允许跳号或重用。

> 为什么放 `docs/adr/` 而不是 `.specify/memory/`：ADR 是给人评审、追溯的正式工程文档，
> 进常规评审流并与代码同走 PR；`.specify/memory/` 放的是机器与 AI 的过程记忆。
> 两份记忆各司其职，**禁止两边各放一份 ADR**。

### 什么时候必须写 ADR

- 选了叶子 b 或 c
- 触发了默认值清单里任一「要」的条件
- 选了与叶子推荐栈不同的技术
- 其他任何偏离默认的选择

**默认选择不需要 ADR**，但要在方案文档里用一句话记下结论。

### 结构（本项目落地实例：`docs/adr/0001-单体与嵌入式数据库.md`）

### 状态值域

```
提议 ──▶ 已接受 ──▶ 已废弃
              └──▶ 被 ADR-xxx 取代
```

- 状态取值：`提议` / `已接受` / `已废弃` / `被 ADR-xxx 取代`
- 复核确认后可写作 `已接受(复核确认)`
- **合并后不可改内容，只可改状态**；已接受的 ADR 只能被新 ADR 取代。

### 评审方式

> **单人开发前提下的评审 = 开一个全新 AI 会话，不带历史，只给它 ADR 与相关文档，让它挑错。**
> 不要求去找"另一名工程师"或"技术负责人"。找不到第二个人不是违规，**不做评审才是**。
> P1/P2 建议另加冷却期（隔半天）后复核一次。

### 维护

- 在根 `AGENTS.md` 的文档索引里列出**全部 ADR 及其状态**。
  （本项目**选定此处**作为唯一登记处，**不另设独立的 ADR 索引文件**
  —— 同一事实两处各写一遍必然漂移。）
- 每半年或每个大版本前，扫一遍各 ADR 的「重新评估触发条件」是否已触发。

## 七、本流程的边界

本环节只产出**决策与 ADR**，不产出方案文档（`plan.md`，**由实现环节创建**）、数据模型与契约 —— 那些属于实现环节。
在 `docs/PROJECT-STATE.md` 的「下一步」里留好钩子。
