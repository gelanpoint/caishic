# 附录 B：中台怎么做

> 这份文档讲中台：数据怎么存、接口怎么定、一笔交易怎么归属到商户、佣金怎么算、怎么保证不重复记账，以及**我们验证到哪一步、哪些还没验证**。

## 一、中台的位置

### 唯一的账口

**佣金、日聚合、结算单、经营看板、退货冲正计算，一律在这里算。** 秤端只做"本地计价 + 上报"，上报的金额只作为**比对输入**，不作为入账依据。

这条边界不是抽象的原则，它有具体的落地方式：**新增的秤端接入接口，在实现上复用的是既有的那一套记账逻辑**，中台里不存在第二份记账实现。

### 中台仍然是单体

分离版把系统拆成了"秤端 × N ↔ 中台 × 1"，但**中台内部还是单体**——一个代码库、一个进程、一个数据库文件。

**这不是微服务。** 拆分的动因是**物理部署**：出现了一类**必须待在摊位现场的终端**。而微服务的触发条件是"组织规模、发布节奏、服务治理能力"那一套，我们逐条对照过，**一条都不满足**：

| 触发条件 | 我们的实际情况 |
|---|---|
| 两个以上长期稳定的研发团队，各自独立背交付 | 一支小队 |
| 至少两个模块的发布节奏差 4 倍以上，而且已经被事故证明 | 没有这个证据 |
| 具备服务治理能力（服务发现、链路追踪、灰度） | 没有 |
| 有专人负责平台与运维 | 没有，运维承诺已经降到"尽力而为" |
| 单体内部的模块化改造已经被尝试并证明不够 | 没试过，现在的模块边界很清楚 |

**五条全否，所以不拆服务。** 我们加的是**一层边缘节点**，它不构成服务网格里的一个服务，也不引入服务发现、网关、消息队列。

## 二、数据怎么存

### 三条全局约定，决定了后面所有设计

| 约定 | 取值 | 为什么 |
|---|---|---|
| **金额一律整数"分"** | 整数 | 对账等式必须**精确成立**，用浮点会造成对账对不上 |
| **重量一律整数"克"** | 整数 | 同上，消除浮点误差 |
| **字段名带单位后缀** | 金额字段以"分"结尾、重量字段以"克"结尾 | 让单位错误**可以被机械查出来** |

另外两条贯穿全库的纪律：

- **全库不出现身份证号与银行卡号字段**——字段名层面就禁止，接口的请求体和响应体也做扫描；收款标识只存脱敏值。
- **不建任何顾客实体，不存可识别顾客身份的信息。** 这是有意的设计，不是遗漏。

### 21 张表，按职责分九组

| 分组 | 表 | 一句话 |
|---|---|---|
| 市场维度 | 市场 | 租户档案，八张业务表的归属对象 |
| 档案 | 商户 / 摊位 / 秤端会话 | 摊主档案 / 摊位档案与脱敏收款标识 / "已绑定摊位"的会话 |
| 设备 | 设备 | 设备注册、市场 + 摊位绑定、**设备令牌摘要** |
| 商品 | 标准品类 / 摊位品类别名 / 商品 / 价目表项 | 品类字典 / "摊位别名 → 标准品类"映射 / 商品档案 / 按营业日的价目表 |
| 交易 | 交易 / 交易明细 | 交易头部（交易号、金额、状态、幂等键、来源）/ 商品行（重量、原价、改后价、金额、改价与抹零标记） |
| 支付 | 支付流水 / 支付回调记录 | **唯一的支付流水表**（收款码与现金都在这里，用支付方式区分）/ 每次回调的到达与幂等命中标记 |
| 冲正 | 退货冲正 | 金额、关联原单号、操作摊位、幂等键 |
| 离线 | 离线暂存队列 | 断网期间的本地持久暂存与补传状态；**补传成功后载荷置空** |
| 佣金与结算 | 佣金口径 / 日聚合 / 结算单 | 口径（收费对象/费率/品种档位/生效期）/ 按摊位 × 营业日的聚合快照（可重算）/ 依据日聚合生成的结算单（可追溯多版本） |
| 信用与留痕 | 摊位信用档案 / 审计日志 | 标价一致率等信用指标（**对顾客可见**）/ **只增不改**的资金链路留痕 |
| 基础设施 | 迁移执行记录 | 记录已执行的迁移脚本，保证启动时按序补齐、不重复执行 |

索引共 **36 条**（其中 **25 条**来自初始建表，**11 条**是秤端拆分时新增的），触发器 **2 个**（都挂在审计日志上，用来拒绝修改和删除）。

### 三处刻意不建表

**同一个事实不存两遍**——这是我们在数据模型上最坚持的一条：

| 不建什么 | 为什么 |
|---|---|
| **不建"改价记录表"** | 改价这件事记在审计日志里（一条记录里带上原价、改后价、改价时间、操作摊位和明细行引用），同时在交易明细上保留终态价格。**同一件事不建两张表**，否则两处会各存一份然后对不上 |
| **不建对账结果表** | "订单总额 = 支付流水 = 分账明细"由原始表**现场算**。**一旦落表，就多了一份会和原始数据对不上的来源** |
| **不建指标表** | 三个使用率指标由原始表现场算。**多存一份派生值，就多一个对不上的地方**（比如库里是 3 笔、接口说 2 笔） |

### 四个状态机，不在流转图里的流转一律非法

| 实体 | 状态 | 关键副作用 |
|---|---|---|
| **交易** | 已计价 → 支付失败 → 已收款 → 已冲正 | 计价完成生成交易号并写明细；收款（现金或回调成功）写支付流水，**先落库再展示凭证**；支付失败可以改记现金或重试；退货冲正写冲正记录并**触发相关营业日的聚合重算** |
| **支付** | 待处理 / 成功 / 失败 / 超时 | 现金直接写成功（带确认时间和操作人）；收款码先待处理，由回调驱动；**同一次回调重复送达只记一个"重复命中"标记，不重复记账** |
| **离线队列** | 已暂存 → 已补传 / 重复丢弃 | 补传成功把载荷置空并记下清除时间（**这是"清除了本地副本"的可核对证据**）；幂等键重复就丢弃这一条并留痕，**不报错、不阻断后续补传** |
| **结算单** | 已生成 | 重算产生**新版本行**，**旧行保留不改**（可追溯、不可物理删除） |

### 两处实现层的口径，写在这里免得实现发散

1. **计价取整**：金额 = (单价 × 重量 + 500) ÷ 1000 取整，四舍五入到分。
2. **标价一致率**：分母是期内的交易明细总数，分子是"没有改过价"的明细数；**抹零不计入，改价计入**；分母为 0 时取 100%。

这两条在需求层面没有规定，属于实现层口径。**要改必须先改约定，不能在实现里悄悄改。**

### 市场维度：已经落地，不是预留

- **八张业务表带市场归属**：商户、摊位、品类、商品、价目表项、佣金口径、日聚合、结算单。其余表的归属**经摊位传递**。
- **这一列有意不带数据库外键**：SQLite 明确不允许给已有表加一个"带非空默认值的外键列"。所以完整性靠"默认市场那一行一定存在"加上应用层校验；非空默认值同时完成了回填——既有的单市场数据全部落到默认市场。
- **这一期只装一个市场**。装载第二个市场是**纯数据操作**（插一行市场，再带市场号插业务数据），**不需要任何建表或改表语句**——这一点我们实测过。
- **摊位号和品类编码的唯一约束已经改成"市场内唯一"**，否则第二个市场就不能再有 `A-01` 摊位或同名品类。

**所以"支持多市场"这件事，这一期交付的是"数据模型和约束已经就位"，不是"多市场的运营流程已经做完"。**

### 设备令牌：明文绝不入库

- 库里只存**令牌摘要**（固定 64 位十六进制长度，并且在数据库层面加了一道长度约束作为最后闸门），**明文一律不入库**。
- **授权只来自这张表**：设备注册时绑定的（市场，摊位）就是它的授权范围；请求体或路径里的摊位号、市场号**一律不采信**。
- **"一个摊位只有一台设备"这个约束我们故意没加**：绑定唯一性靠"设备号唯一"保证就够了。如果连摊位也做成唯一，换秤的时候新设备会直接被数据库挡在门外（报错、然后变成一个 500），而需求里**从来没有要求一个摊位只能有一台设备**——现实中会有替换机、备用机。

## 三、接口约定

### 计数

| 项 | 数量 |
|---|---|
| 功能需求 | **52 条** |
| 验收标准 | **42 条** |
| 非功能需求 | **16 条** |
| 面向浏览器和运营端的接口 | **32 个** |
| 秤端接入接口 | **7 个** |
| 接口合计 | **39 个** |
| 错误码 | **19 个** |
| 数据表 / 索引 / 触发器 | **21 / 36 / 2** |

### 面向浏览器的这一套：通用约定

1. 请求和响应都是 JSON（UTF-8）；本特性**没有文件上传**（不打印、不上传）。
2. **错误响应格式统一**：`{"error": {"code", "message", "detail"}}`，格式只定义在一处。
3. 写操作要求带幂等键（不超过 64 字符）；重复请求返回**第一次的结果**，不是报错。
4. 时间统一格式；**金额整数"分"、重量整数"克"**。
5. **响应体里不出现身份证号和银行卡号字段**；收款标识只以脱敏值出现。
6. 秤端接口一律要求会话令牌，而且**只允许访问该会话绑定摊位的数据**。
7. 认证现状：秤端要会话令牌；**顾客扫码页和运营端这一期不做认证**——这是被明确批准的放宽，不是遗漏。

### 幂等：四种场景，四种键

| 场景 | 幂等键 | 重复提交会怎样 |
|---|---|---|
| 创建交易 / 离线暂存 | 客户端幂等键 | 返回第一次的结果，不新建交易、不重复计佣 |
| 退货冲正 | 客户端幂等键 | 金额与佣金**不再变化**，返回第一次的结果 |
| 支付回调 | 回调单号 | 记一个"重复"标记，**不重复记账** |
| 补传 | 客户端幂等键 | 丢弃这一条并留痕，**不报错、不阻断后续补传** |

> **幂等命中不是错误。** 补传的键重复、支付回调重复，**都返回成功语义**（带一个"这是重复"的标记），不得报错、不得阻断后续处理。这一条是行为要求，不是实现选择。

### 错误码里有一条值得单独说：通用 500

原来那张表里**没有任何通用 5xx 码**。后果是：未预期的异常只会落到框架默认的 500 —— 响应体是 HTML、不符合统一格式、没有任何可追溯标识。**调用方拿到的信息是"服务器炸了"，但不知道这一笔到底记没记。**

补上一个确定的错误码之后，未预期异常的出口变成确定性的：统一格式 + 一个可以报障的请求标识 + **明确告知"结果不确定，不要当成成功"**。

**它不改变任何业务语义**：业务失败还是各归各的码，这个码只兜"没人预料到的那一类"。而且**原始异常和调用栈只进服务端日志，不进响应体**。

### 版本策略

- 面向浏览器的接口，路径**不带版本段**（`v1`）。
- **兼容性变更**（新增可选字段、新增接口、放松校验）直接发布。
- **破坏性变更**（改名、删字段、改语义、收紧校验）必须在**同一次提交里**改完接口约定、数据模型、契约测试和任务清单。
- **兼容期承诺**：这一期是单机演示交付物、没有外部消费方，所以**不做多版本并存**；承诺形式是"同一次提交内全量同步"。**如果这个项目转成真实生产系统，这个承诺要升级成"旧版本至少保留一个发布周期"。**

### 关于"自动生成接口文档"这件事

我们没有引入自动生成接口文档的工具，所以**无法做"实现代码自动生成文档 ↔ 手写文档"的比对**。替代方案的目的是一样的——**防止接口和实现走样，而且能机械失败**：

1. 检查已实现的路由表和手写的接口清单**双向一致**：多一个或少一个接口，检查就红；
2. 逐个接口断言响应的关键字段和状态码，并对**全部响应体**做"没有身份证/银行卡字段"的扫描；
3. 手写的文档骨架和接口清单冲突时，**以接口清单为准**并立即修正骨架。**骨架只是派生视图，不是实现依据。**

## 四、一笔交易怎么归属到商户

这一节讲的是落到数据和接口上的做法（业务层的答案见 [总体方案](02-总体方案.md) 第七节问题 1）。

### 归属链条

```
设备/会话 → 摊位 → 商户
```

- 交易挂在摊位上（外键），摊位挂在商户上（外键）；
- 八张业务表另外带**市场归属**（这一列有意不带外键，理由见第二节）；
- **秤端会话**这张表落实"摊主只能访问本摊位数据"。

### 授权不来自请求参数

这是最容易被做错的一处：**如果信任请求里带的摊位号，那么任何一个能改请求的人都能把交易记到别人头上。**

所以：

| 形态 | 授权来源 |
|---|---|
| 单机版 | 会话令牌绑定的摊位 |
| 分离版 | **设备注册时绑定的（市场，摊位）** |

请求体或路径里出现摊位号、市场号，**一律不采信**；设备和目标不匹配就明确报错，**不重试**。

### 声明只能用来暴露不一致

安装时声明的摊位号，作用只有一个：**和已保存的绑定不符的时候报出来**。它不能把设备绑到别的摊位，**也不会自动改绑**——真要改绑，必须先在运营端解绑。

### 幂等键按摊位作用域

交易的幂等键是 **(摊位, 客户端幂等键)** 的联合唯一，**不是全局唯一**。

**这一点很关键**：离线补传的场景下，不同摊位的秤端完全可能生成字符串相同的键。如果做成全局唯一，第二台秤的第一笔就会被当成重复丢掉；如果做成"谁先来谁占"，就会串号。

### 我们实测过的

**20 个秤端进程并发对 1 个中台**：20 个进程全部正常退出，总耗时 1.43 秒，中台入账 20 笔，**每个摊位恰好 2 笔，零串号**，幂等键零碰撞。

## 五、佣金怎么算

### 佣金口径表

| 字段 | 取值 |
|---|---|
| 收费对象 | 向商户收 / 向顾客收 / 市场自留 |
| 费率 | **万分比整数**（1 到 10000），避免浮点 |
| 品种档位 | 可留空，留空表示对全部品类生效 |
| 生效期 | 起止日期；截止日期留空表示长期有效 |

**佣金按实收金额计算，不按标价。** 这一条很重要——菜市场议价、抹零是常态，按标价算会让基数偏大。

### 从一笔交易到一张结算单

```
交易（已收款）
   ↓  按日聚合
日聚合（摊位 × 营业日）—— 可重算，版本递增，旧版本保留
   ↓  期内各日聚合求和
结算单 —— 重算生成新版本，旧版本不改
```

退货冲正会**触发相关营业日的聚合重算**，所以"日聚合金额与佣金同步减少、且只减一次"这件事是可以当场看的。

**抹零必须从分账基数里减掉。**

### 口径唯一这件事是怎么保证的

佣金、日聚合、结算、看板一律在中台。秤端不承载这些——**这一点是被机械核验的**：扫固件的源码和符号表，出现任何佣金/结算相关的符号就报错。

### 实测：佣金确实是系统算的

在"向商户抽 200 个基点、30 个营业日"的联调档里：

- 系统算出的日佣金合计 **5699 分**；
- 同期已结算订单 **284872 分**；
- 两者相除 = **200.1 个基点**（差额来自逐日四舍五入）。

换成"写进系统 1 个基点"的那一档，佣金合计是 **15 分**。**也就是说佣金跟着系统里的口径变，不是联调程序自己算的。** 而且**两边用的是同一个计算模块**——不存在第二份佣金口径。

### 三个使用率指标，分子分母全部来自系统自己

| 指标 | 分子 | 分母 |
|---|---|---|
| **摊位使用率** | 当天有交易的不同摊位数 | 在营摊位数 |
| **现金交易占比** | 当天成功的现金支付笔数 | 当天全部走秤交易笔数 |
| **价目表维护率** | "当天价目表完整"的摊位数（该摊位全部在售商品当天都有价格） | 在营摊位数 |

三项都导出成万分比整数，**而且每个分子和分母的数值都能被第三方逐一核对**。

**被我们废掉的那个指标**：原来的想法是"日均智能秤交易占比"（走秤笔数 ÷ 市场总交易笔数）。问题是它的分母——**市场总交易笔数**——系统自己拿不到，只能来自人工盘点、抽样统计或外部系统。**这不是"实现口径待定"，而是这个指标本身超出了系统自有数据的范围。** 所以我们换掉了它，并且**禁止在实现里估算这个分母**（比如用"走秤笔数 ÷ 单摊位日均假设值"倒推）——**那是把推断当事实。**

### 这三个指标的证明力，有一个边界要说清楚

原来的检查用例，在**退化状态**下发现不了问题：如果某一天现金笔数恰好等于总笔数（分子 = 分母），那么"真的去查库"和"直接写死一个常量"输出**完全一样**。种子数据的初始状态就是这样——现金 1/1、价目表 10/10。

实测证据：把价目表那个分子写死成常量，原来的用例**照样通过**；把摊位使用率的分子写死，**才会失败**。也就是说，"真的去查"这件事，**有一半没有被检验到**。

修法是**先制造"分子 ≠ 分母"的状态再断言**：删掉某个在营摊位当天一行在售商品的价格（维护率的分子就恰好是分母 − 1），再新增一笔未收款交易（现金分子就严格小于分母）。补完之后：

- 把价目表分子写死 ⇒ **新用例红，而原有用例仍然绿**（这正是盲区的证据）；
- 把现金分子写死成分母 ⇒ **新用例红**；
- 还原 ⇒ 绿。

**这就是"不能只验证结果、要验证灵敏度"的具体含义。**

## 六、怎么保证不重复记账、账实相符

### 涉钱的那条底线：三线重合

**订单总额 = 支付流水 = 分账明细**，而且对**全部**交易成立，包括现金和退货冲正。

怎么做到的：

| 手段 | 内容 |
|---|---|
| 整数存储 | 金额整数分、重量整数克，等式精确成立 |
| **现金进同一张支付流水表** | 现金如果不在支付流水里，等式对它就失效。核心理由是"**现金也走同一条流水，只是支付方式不同**" |
| **不落对账结果表** | 等式由原始表现场算，落表就多了一份会和原始数据对不上 |
| 口径限定 | 对账口径限定在**已结算交易**，在途交易不入账 |

### 退货只冲减一次

- 靠 (交易, 幂等键) 的联合唯一约束保证；
- 重复提交 ⇒ 状态不变、金额不变、写一条"重复命中"的留痕、**返回成功语义**；
- 冲正会触发相关营业日的聚合重算；结算单重算产生新版本，**旧版本保留不改**。

### 支付回调按单号幂等

同一次支付的回调被重复送达时，按**支付单号**幂等：写一个"重复命中"标记，**不重复记账**。

### 补传靠幂等键去重，成功后清除本地副本

- 交易的幂等键按摊位作用域唯一，这是离线补传去重的兜底；
- 幂等键重复 ⇒ 这一条转成"重复丢弃"、留痕，**不报错、不阻断后续补传**；
- 补传成功 ⇒ 载荷置空 + 记下清除时间。**这就是"清除了本地副本"可以被核对的方式。**

### 一处接口约定内部的张力，我们选择不改数据模型

通用约定里说"写操作端点要求幂等键，重复请求返回首次结果"，但**具体场景清单里并没有把"收款"列进去**，而且支付流水表**根本没有幂等键这一列**。

**结论是维持现状，不改数据模型、不加列。** 理由三条：

1. 具体场景清单比泛化表述更具体，**具体清单决定适用范围**；
2. 加一列属于改数据模型，不该由一个实现轮次顺手做掉；
3. **状态机本身就是更强的保护**：交易是单向流转"已计价 → 已收款"，一笔交易只能收一次款。

**实现现状**：重复确认现金收款会按状态机返回"状态不允许当前流转"，**不新增流水**。

如果以后要求"同一个键重发收款也返回第一次结果"，那要先改数据模型和接口约定，再改实现。

## 七、可靠性设计

### 四条不可协商的底线，落到中台的部分

| 底线 | 中台的落法 |
|---|---|
| 密钥绝不入库 | 设备令牌**只存摘要**，而且在数据库层面加了长度约束兜底 |
| 身份证号与银行卡号任何位置都不出现 | 全库字段名禁令 + 请求体和响应体的扫描 + 收款标识脱敏 |
| 离线暂存补传成功后必须清除本地副本 | 载荷置空 + 记下清除时间，作为**可核对证据** |
| **绝不静默丢弃任何一笔交易** | 暂存达阈值只告警、仍然继续接受；写入失败**明确报错且不得标记为成功** |

### 审计日志：只增不改由数据库强制

- 数据库触发器直接拒绝修改和删除审计日志，应用层**不提供任何修改接口**；
- 我们实测过：改和删都会直接报错。

当前记录的十种事件：改价、退货冲正、退货重复命中、离线补传成功、离线补传重复丢弃、支付回调重复命中、暂存写入失败、暂存达阈值告警、佣金口径变更、**秤端上报金额与中台重算不一致**。

其中最后一种的载荷里要记：设备号、幂等键、**秤端上报的金额、中台重算的金额、逐行差异**。**原始值必须留在留痕里，否则差异无法追查。**

### 数据库的运行时配置

WAL 模式（读写可以并行）、打开外键约束、设置忙等待超时（并发写入时等待而不是立刻失败）。

> **要如实说一句**：嵌入式数据库是单写者锁。转向 300 个摊位并发写入的形态时，**第一个瓶颈会出现在并发写入，而不是数据行数**。

### 并发正确性

需求写的是：多个摊位并发写入时，**每笔交易的写入互不覆盖，且交易号唯一**。

落地方式是号段分配 + 有界的冲突重试。这一块在**真并发压测里抓到并修掉过一个丢单缺陷**——这类缺陷只有真并发才暴露得出来。

### 响应时间：一个"随盘不随代码"的已知边界

阈值本身写在质量阈值表里，这里只讲一个实践中的坑：

**同一段代码、同一份负载，在不同磁盘上差一个数量级。**

| 口径 | 快盘 | 仓库所在的慢盘 |
|---|---|---|
| 点按口径（选品 → 计价 → 收款） | p50 43ms / p95 73ms | p50 297~354ms / p95 683~770ms |

根因是**磁盘 fsync 成本**：256KB 写 + fsync 的 p50，快盘 2ms，慢盘 37ms，而且**慢盘上仓库内外一样慢**。所以差异**随盘，不随路径、不随代码**。

**现场处置是把演示数据目录放到用户数据目录（快盘），不改代码、不放宽阈值。** 启动脚本统一处理这件事，而且**不覆盖用户显式设置的目录**；直接跑启动入口时默认行为不变。

**如果现场实测（包括快盘）仍然不达标**，那就记一次放宽并写明根因是磁盘——**先实测再决定，不预判。**

### 两条从真实事故里长出来的规矩

**第一条：输出编码不许依赖环境变量。**
症状是：在没设编码相关环境变量的机器上，启动横幅的中文全变成替换字符，断言失败——而开发机上一直是绿的。修法是让输出在**被重定向或进管道时强制 UTF-8**（写给机器看的必须和系统 locale 无关），**接真实控制台时沿用控制台编码**（中文才显示得对）。测试里捕获子进程输出一律显式指定 UTF-8。**验收基线 = 清掉这些变量之后仍然全绿。**

**第二条：交付前跑一次"新克隆验证"。**
症状是：`.gitignore` 里一行**没有锚定到仓库根**的规则，把仿真的一整个环境层静默忽略了——`git ls-files` 查不到那些文件，工作区里却都在、测试全绿。**本地怎么跑都发现不了。**
修法不是给那个目录开洞，而是**按成因修**：把虚拟环境规则锚定到仓库根。

**第二次兑现更值得记**：新克隆验证抓出一个浏览器端到端用例**在快盘上稳定失败、在慢盘上稳定通过**。逐步排除（换行符、残留进程、测试顺序、页面乱码）之后，把同一份内容解到另一块盘的另一个路径——**通过**；同一时刻快盘上的克隆——**失败**。根因是用例在页面重载后立刻点击，**和应用初始化赛跑**：快盘上应用更快地恢复状态并重排布局，稳定性检查就一直过不去；慢盘上恰好落进静止窗口。

**它在替代码撒谎：快机器上红、慢机器上绿。而现场的机器多半是 SSD。** 修法是改成等待一个**确定性的就绪状态**——如果那个状态永远不出现，用例就会**响亮地失败**，不再靠一次碰运气的点击蒙混。

**由此追加的纪律**：任何一条"全绿"的记录，都要问一句——**它在什么机器上绿？**

## 八、技术选型为什么这么定

| 决策 | 结论 | 一句话理由 |
|---|---|---|
| 架构形态 | 单体 + 嵌入式数据库 | 本期峰值并发不到 20，独立数据库和缓存在这一期没有对应负载；引入它们只增加运维面 |
| 环境策略 | 单环境 | 多环境的前提是"有一个生产环境需要保护"；本期唯一的运行对象是本机 Demo，没有可部署的生产环境 |
| 技术栈 | Flask + 标准库 `sqlite3` + 纯静态前端 + 原生进程，不用容器 | 现场故障面最小；"一条命令启动、不依赖外网"天然满足 |
| 依赖范围 | 运行期只有 Flask；测试和覆盖率工具属于开发期，单列一份清单 | 运行期多一项依赖，现场就多一个装不上的可能 |
| 部署拆分 | 秤端 × N ↔ 中台 × 1，中台仍是单体 | 动因是物理部署，不是组织规模 |

### 关于"依赖范围"那次修订的根因，值得记一句

问题不是"缺依赖"，而是**条款本身写得不清**：技术栈白名单的标题是"允许的技术栈"，同一张表里其他条目的语境都是运行期，**唯独白名单那一条没有写这个限定语**。**把运行期和开发期混在一条白名单里，本身就是条款缺陷。**

所以正确的动作是**澄清条款**（把白名单界定为运行期，开发期工具单列），**而不是"破例把测试库塞进白名单"**。

### 这次技术选型的代价，也如实记

1. **没有自动生成接口文档**（替代方案见第三节）；
2. **没有原生异步**；
3. **换机器要重装依赖**（不做免安装打包）；
4. **内置的 HTTP 服务器不适合生产**。

## 九、中台这套东西，我们验证到哪一步

### 已经跑通并且可以复现的

| 项 | 实测 |
|---|---|
| **接口覆盖** | 主契约 32 个接口全部被真实调用过；覆盖清单是**由实际请求反推**的，再和手写清单**双向逐条比对** |
| **每日对账** | 30 个营业日**全部**"三线相等、差额为 0" |
| **幂等重放** | 同一笔重发 ⇒ **同一个交易号**，列表总数 1 → 1，HTTP 状态码从 201 变 200 |
| **敏感字段扫描** | 扫 2082 条真实响应体，**零命中**；另有合成负例证明扫描器在扫真实数据时确实能命中 |
| **接口性能** | 快盘上 p50 19.6ms / p95 40.6ms（样本 2082） |
| **数据与源码不被改动** | 运行前后源码树指纹一致，而且用例是**独立重算**复核的 |
| **涉钱三线重合** | 订单总额 = 支付流水 = 分账明细，含现金与退货冲正 |
| **并发正确性** | 真并发压测逐笔核对、离线并发零丢弃 |
| **浏览器端到端** | 六步主链真浏览器走查，同机双窗口，退出码 0 |

**关于那个"2082 次调用"**：这是**原来的跑批配置**下的数字。后来用另一套测试配置复测得 1760 次——**两套配置不同，数字不能互换**。如果要以交付口径引用，必须按原配置重跑一次。

### 属于设计推断、还没被现实检验的

- 三个使用率指标的**口径方向**有依据，但"在这套实现下会得到什么数"取决于真实业务量；
- **容量推算是按待验证的日均笔数假设做的**（单摊位 80–150 笔），不是实测；
- 仿真给出的机制只作参考，不作承诺（档位见 [问题梳理](01-问题梳理.md) 第九节）。

### 还没做到的事，一条一条说

1. **传输层是明文 HTTP**，TLS 没实现。放宽获批了，但**批准的是"放宽"，不是"达标"**；中台不能暴露到公网。
2. **设备重复预注册会换发新令牌**，会让已经烧进秤里的旧令牌静默失效。这一期靠运维纪律兜住（预注册只做一次），后面应该拆成"重复预注册"和"轮换令牌"两个明确的入口。
3. **"市场"这个维度没有数据库级外键**，写错市场号会静默产生孤儿行。这类行不会串账，但会"消失"（对账时表现为数据凭空少了）。建议补一个便宜的机械兜底：启动时或测试里断言所有业务行的市场号都真实存在于市场表。
4. **多进程并发建库没测过**：数据库事务会互相阻塞，行为未知。
5. **调用方已经持有事务时再执行迁移会报错**（不能在事务里再开事务），这一条没测。
6. **"建库过程中进程被杀"这句话没有独立证据**：真正的强制杀进程、断电之后的 WAL 恢复路径没有覆盖。
7. **SQL 注释和数据模型里的枚举值缺少机械对账**：已经在实现阶段实测抓到过一处对不上。而且**改注释不会回写已建的库**——数据库把建表语句原文存着，`IF NOT EXISTS` 从不重写它，所以新建的库和已有的库会读到不同的注释。**这类对不上靠人眼几乎必然漏。**
8. **固件侧的存储实现没验证**（属于秤端的未验证项，见 [附录 A](03-附录A-智能秤设计.md) 第九节）。

### 和仿真接线时的三处说明

1. **费率下限是 1 个基点，所以"抽佣 0%"在联调里无法精确表达**——只能用 1 个基点并把这一档标出来。
2. **当天最后一笔固定走收款码**，否则"支付回调"这个接口的覆盖就要靠运气。
3. **配置佣金口径这个接口的语义是"新增一条口径"**：库里已有相同口径就复用并标明，不一致就原样抛错。
