# 总体方案：我们打算怎么做

## 一、一句话说清

> **把交易锚在秤上，把账口收到中台，把摊主的操作减到最少。**

展开成三条可以检验的主张：

1. **秤是唯一的物理锚点。** 交易必须走"选商品 → 称重 → 计价 → 出收款码"，**系统不接受手工输入重量和金额**。
2. **账口唯一。** 佣金、日聚合、结算单、经营看板、退货冲正全部在中台；秤端只做"本地计价 + 上报"，中台收到后用权威实现**重算一遍**，以重算结果入账。
3. **离线不丢一笔。** 断网继续收钱、本地持久暂存、恢复后按幂等键补传、成功后清除本地副本。

这三条不是并列的三件事，是有优先级的：**数据可信度优先于功能数量**。功能少一个可以补，账错一笔就没有第二次机会。

## 二、一笔生意在系统里怎么走

### 主干链路

| 环节 | 系统里发生什么 | 现场在哪里看 |
|---|---|---|
| **商户** | 商户与摊位档案（姓名、联系方式、在营状态），支持按摊位查询 | 运营端 |
| **商品** | 品类字典 + "摊位别名 → 标准品类"映射（**同物异名归一**）；营业前设好价目表，支持"复制昨天价" | 秤端营业前；运营端维护字典 |
| **称重** | 秤端**用图标和快捷键选品，全程不需要任何文本输入**；放上商品读重量 | 秤端 |
| **计价** | 金额 = 单价 × 重量；一单多品**累加**；改价和抹零都留痕 | 秤端 |
| **交易** | 落库生成交易号；改价和抹零**分开统计**；单笔改价超过 50% 会提示确认，**但系统不阻止** | 秤端 |
| **支付** | 收款码和现金两条路；**现金也写进同一张支付流水表**（记下确认时间和操作人）；收款码回调分成功/失败/超时 | 秤端 + 顾客扫码页 |
| **佣金** | 口径可配（收费对象/费率/品种档位），按**实收金额**算；日终按日聚合，退货后按需重算 | 运营端 |
| **经营数据** | 商户端与市场方端两个看板、结算单、对账、三个使用率指标、审计留痕 | 运营端 |

### 一次交易的完整动线（12 步）

1–8 是顺流程，9–11 是异常流，12 是收口。**异常流不是补充说明，是主干的一部分。**

| # | 步骤 | |
|---|---|---|
| 1 | 摊主开机即进入**已绑定摊位**的秤端主界面（常驻，不重复登录） | 正常流 |
| 2 | 营业前设好价目表（支持"复制昨天价"）；交易中**选商品用大图标/快捷键，禁止打字** | 正常流 |
| 3 | 选商品 → 放上商品 → 秤出重量 → 系统按"单价 × 重量"计价 | 正常流 |
| 4 | （可选）临时改价或抹零，**原价与改后价都记下来** | 正常流 |
| 5 | 一单多品就重复第 3–4 步，累加到同一单 | 正常流 |
| 6 | 确认应收金额 → 屏幕出收款码，或者摊主选现金 | 正常流 |
| 7 | 顾客扫码（模拟支付）→ 回调分成功 / 失败 / 超时三条路径 | 正常流 |
| 8 | 支付成功 → 展示交易凭证（交易号 + 明细）→ 交易落库。**系统不提供打印** | 正常流 |
| 9 | **支付失败或超时** → 可重试或改记现金 → **同一单绝不产生两笔交易、两笔佣金** | 异常流 |
| 10 | **顾客退货** → 冲正原单 → 日聚合金额与佣金同步减少，**而且只减一次** | 异常流 |
| 11 | **断网** → 继续正常交易（本地暂存）→ 联网后自动补传 → **订单数不翻倍** | 异常流 |
| 12 | 日终 → 按日聚合 → 生成结算单 → 两端看板出数 → **对账等式成立** | 收口 |

### "成功"长什么样：三个能当场观察的场景

这三个场景是现场连续演示的，每个都能被第三方照着判过或不过：

| # | 场景 | 判据 |
|---|---|---|
| 1 | 顺流程一笔 | 该笔交易在**商户端与市场方端两侧都可见，金额与明细完全一致** |
| 2 | 退货冲正 | 日聚合金额与佣金**同步减少、且只减一次** |
| 3 | 断网补传 | 断网做 2 笔，恢复后自动补传，**订单总数不翻倍**，且**订单总额 = 支付流水 = 分账明细** |

第 3 个是全场最值钱的一段。**只演顺流程，看的人是判断不出数据一致不一致的。**

### 现场演示的六步

1. **选品 → 称重 → 计价**（秤端）：点图标选品，点预设重量或"读秤"，自动出金额。**界面上没有"随便输金额"的入口**——想改价必须走下一步。
2. **收款**：收款码走一遍，再做一笔现金。现金也进同一张支付流水表，否则经营数据是残缺的。
3. **顾客扫码**：摊位信息、本笔明细、本摊标价一致率——**六项真值全部显示，没有一项是空壳**。
4. **改价与退货**：未支付的交易可以改价（有记录，超过 50% 提示确认）；已支付的可以退货冲正，重复提交只冲减一次。
5. **离线与补传**：打开离线开关做 3 笔，全部进本地暂存并显示待补传笔数；切回在线点补传，待补传归零。
6. **运营端**：佣金口径 → 日终聚合 → 结算单 → 对账 → 使用率指标 → 审计留痕。

现场准备了三种降级方案：**同机双窗口**（没有 WiFi 时）、局域网手机真机扫码、端口被占用时按提示换端口。

## 三、三个界面，三种人

| 端 | 谁在用 | 关键约束 |
|---|---|---|
| **秤端** | 摊主 | **只接触本摊位的数据**；只做"选品 / 称重 / 本地计价 / 收款 / 本地暂存 / 上报"六件事 |
| **顾客端** | 顾客，**不登录** | **只展示有真实采集来源的字段**；不采集、不记录任何可识别顾客身份的信息 |
| **运营端** | 市场运营方管理员（以及只读查看者） | 品类字典与别名、佣金口径、日终聚合、结算单、对账、三个指标、审计日志 |
| **演示层** | 三种视角：商家 / 顾客 / 管理员 | 俯视角像素风网页游戏。**只读展示、只调用既有接口**，不新增账口 |

### 角色上有一处刻意的合并

真实业务里，"配佣金口径""对账""审结算单"可能分属运营和财务两个岗位。**这一期合并成"运营方管理员"一个人**，岗位分离和权限矩阵留到后面。

### 顾客端只做一件事：把有来源的信息摆在顾客面前

顾客扫码看到的是：摊位信息、这一笔的明细、以及**本摊标价一致率**。**字段白名单多一个就算失败。** 这不是洁癖，是因为调研里顾客的原话是"扫过好几次空码之后，再也不信这个标签了"——**信任是一次性的，空壳页面比不做更糟**。

### 演示游戏为什么只读不写账

游戏存在的目的是让业务流程**可看、可点**：鼠标挪到摊位上显示这个摊位在卖什么、什么价；点智能秤可以调价、可以上下架；可以切换商家/顾客/管理员三种视角。

它**不新增任何服务端能力、不新增账口、不绕过业务逻辑直接改库**。悬停看到的商品清单和单价**取自服务端的价目表**，不是前端写死的——改一下服务端价格，清单跟着变。调价和上下架走的是真实接口。

**要有言在先的两点**：顾客 NPC 的行为是**本地演示逻辑**，既不代表真实并发，也不代表真实顾客行为；像素画是脚本**程序生成**的，不是手绘，**风格接近度是主观判断**。

## 四、软件怎么搭

### 为什么选最简的那种形态

这一期的负载很明确：**单市场、单机、一条命令启动、峰值并发不到 20**。所以走的是最朴素的形态——**一个代码库、一个进程、一个嵌入式数据库文件**。

不引入消息队列（没有耗时超过 10 秒、用户又不等着的结果）、不引入缓存（先直查数据库，慢就先加索引）、不引入全文搜索、不引入独立数据库服务、不上容器。理由很简单：**这些组件在这一期都没有对应的负载，引入它们只增加现场掉链子的面。**

**但"以后能拆"这件事是要现在做的**：模块之间只走明确的接口，业务逻辑不依赖 HTTP，可以单独被测试直接调用。

### 秤端和中台为什么分开——以及这为什么不是微服务

分开的理由是**物理的**，不是架构偏好：**秤必须放在摊位上**（它是唯一的物理锚点），而**佣金和结算必须在数据汇聚的地方**。两端分离是这两条的直接推论。

目标形态是 **100 台秤 ↔ 1 个中台**。这里有一个最容易犯的错，我们单独写出来：

> **秤端不该承担佣金与结算。** 佣金口径必须唯一，否则 100 台秤会算出 100 套账。

所以中台内部**仍然是一个单体**——一个代码库、一个进程、一个数据库。新增的只是一层边缘节点，不引入服务发现、网关、消息队列。**这是加一层边缘，不是升级成微服务。**

### 代码怎么分层

- **业务逻辑层**：不依赖 HTTP，可被测试直接调用。计价、支付、退货、离线、佣金、结算、指标、审计各归各的模块。
- **接口层**：逐一对应接口约定，只是把业务逻辑暴露成 HTTP。
- **前端**：纯静态，没有构建工具、没有 CDN、没有外部字体图标。
- **入口**：一个启动脚本，负责检测端口占用、建库、导入种子数据、起服务、打印局域网地址和入口地址。

三条边界纪律：

| 纪律 | 内容 |
|---|---|
| 账口唯一 | 佣金、日聚合、结算、看板、退货冲正一律在中台；秤端不实现，并且这一点是被机械核验过的（扫固件源码和符号表） |
| 运行期依赖隔离 | 运行期只有 Flask；测试和覆盖率工具属于开发期，**不得被运行代码引用**，这是扫描验证过的 |
| 接口与实现不分叉 | 写好的路由表和接口约定双向一致，**多一个或少一个接口都会让检查变红** |

### 技术选型与它的代价

| 项 | 我们选的 | 参考做法 | 为什么偏离 |
|---|---|---|---|
| 语言 / 框架 | **Python 3.11+ / Flask** | 异步框架 | 同步模型够用，标准库 `sqlite3` 直接可用，不需要构建、不需要镜像 |
| 数据库 | **标准库 `sqlite3`**（WAL 模式） | 独立数据库服务 | 单机、并发不到 20，独立数据库在这一期是过剩的，而且和"一条命令启动、不依赖外网"冲突 |
| 前端 | **纯静态**（HTML + 原生 JS + CSS） | 服务端模板 / 前端框架 | 无构建、无 CDN，现场少一层掉链子的可能 |
| 部署 | **原生进程 + 启动脚本，不用容器** | 容器 | 演示机只需要装一份运行期依赖；容器运行时是一个多余的故障面 |
| 环境 | **单环境** | 多环境 | 多环境的前提是"有一个生产环境需要保护"，而这一期唯一的运行对象就是本机的 Demo |

**代价我们如实记下来了**：没有自动生成接口文档（所以我们用"路由表 ↔ 接口约定双向比对"来替代，能机械失败）；没有原生异步；换机器要重装依赖；内置的 HTTP 服务器不适合生产。另外语言栈从单一 Python 变成了"Python + 嵌入式 C"，评审和测试成本都上升了。

## 五、硬件设想，以及它和软件怎么咬合

题目允许用模拟接口，也让参赛者自己提硬件设想，**要求是整体方案、软件 Demo 和硬件设想三者逻辑一致**。我们的做法不是"写一段硬件段落"，而是让三者真的接上。

### 边界一句话

**秤端是边缘终端，不是账口。** 它做六件事：选品、称重、**本地计价**、收款（展示收款码或确认现金）、**本地持久暂存**、上报。佣金/日聚合/结算/看板/退货冲正一律不在秤端，而且这一点是被机械核验的。

### 两端之间怎么接

| 项 | 内容 |
|---|---|
| 传输 | 标准 HTTP + JSON，路径带版本段 |
| 鉴权 | **设备令牌**；授权范围**只取自中台保存的设备绑定**，请求里带的摊位号/市场号一律不采信 |
| 接口数 | **7 个**：激活、心跳、商品字典、价目表、交易上报、收款确认、退货申请 |
| 版本 | 请求头带协议版本；不兼容**显式拒绝**，不按最新版猜着解析——**猜错就是静默错算** |

**为什么这里路径带版本段，而面向浏览器的接口不带**：浏览器的页面和接口是同一次发布一起更新的；秤端固件是**烧录在 100 台设备里的**，升级不可能同时完成，所以必须能在路径上区分版本，让新旧固件在过渡期里**被认出来**，而不是悄悄算错。

### 最硬的一条：上报之后中台要重算

```
秤端本地计价 → 上报金额和明细
      ↓
中台用权威实现重算，逐行比对
      ↓
  一致 ⇒ 正常入账
  不一致 ⇒ 三件事同时做，一件都不能省：
           ① 入账金额取中台重算值
           ② 写一条留痕（记下秤端上报值、中台重算值、逐行差异）
           ③ 响应里如实返回"金额不一致"和差异明细
```

**为什么"金额不一致"不做成一个错误码**：那会逼出一个坏选择——要么中台拒收这一笔（**摊主已经收了顾客的钱**，而且这违反"绝不静默丢弃一笔交易"），要么让秤端自己改金额（**账口从一个变成三个**）。所以差异走"标记 + 留痕 + 以中台为准入账"这条路。

这条路径是被灵敏度验证过的：把秤端上报的金额改掉一个分位，检查必须变红。

### 计价出现了两份实现，靠三条对冲保证不出错

C 侧计价是 Python 权威实现的**第二份实现**，这是"两套实现走样"的经典风险。三条对冲，**缺一条结论就不成立**：

| # | 手段 | 为什么不可省 |
|---|---|---|
| a | **固件业务核心不依赖 ESP-IDF**，是纯 C，可以在**主机上**编译并跑单元测试 | 没有它，固件逻辑在没有硬件的情况下完全不可验证 |
| b | **黄金向量**：从 Python 权威实现导出测试向量，**产物可复算、禁止手改** | 没有它，"逐位一致"只是一句口头承诺 |
| c | **中台重算比对** | 没有它，秤端被篡改或算错会直接污染账目 |

计价口径本身只有三句话：**金额 = (单价 × 重量 + 500) ÷ 1000 取整**（四舍五入，不是银行家舍入）；**金额和重量全程整数（分、克），不引入浮点**；**抹零只减总额、不计入标价一致率，改价计入**。

## 六、关键取舍：为什么这样选

### 需求层的取舍

| 决策 | 我们选的 | 被否掉的 | 为什么 |
|---|---|---|---|
| 佣金向谁收 | 不做"向商户按流水抽佣"；佣金引擎照做，但做成**可配置口径** | 向商户抽佣 | 三例失败摆在那里；唯一存活的是向买方收费（这条我们也**没有实现**，见 [问题梳理](01-问题梳理.md) 第九节） |
| 硬件谁出钱 | **市场方出资**，采购范围含**维保与计量检定** | 商户自费购秤 | 免费配秤 + 统一检定维修才被接受；维修不及时就是落灰的第一原因 |
| 交易的物理锚点 | **秤是唯一锚点**，流程强制选品 → 称重 → 计价 | 事后补录、手机下单为主 | 没有锚点，流水就不可信 |
| 现金交易 | **必须支持**，而且进同一张支付流水表 | 只做电子支付 | 只做电子支付会丢掉大部分交易，流水不完整，佣金口径跟着失真 |
| 幂等与冲正 | 退货冲正 + 断网补传都要幂等 | 只做正向交易 | 这是"数据前后一致"这个要求的核心载体 |
| 商品口径 | 品类字典 + 摊位别名映射 | 商品名自由文本 | 别名不归一，按品种统计和分档计佣**直接失效** |
| 摊主操作 | **禁止打字**，大图标/快捷键选品，价目表营业前设好 | 搜索框输入、现场建品 | 绵阳摊主的抱怨就是"操作麻烦""字太小""按键反应慢" |
| 顾客扫码页 | **只展示有真实来源的数据** | 展示证照、溯源等空壳字段 | 空壳页面消耗信任，而信任是一次性的 |
| 验收门槛 | 用**使用率**口径 | 装机量 / 设备数量 | "黑屏也能通过验收"就是这么来的 |
| 硬件档次 | 默认**非 AI 溯源秤档 + 物理价签** | 定制触屏一体秤 / 电子屏价签 | 目标只是"价格可见 + 称重可追溯"，物理价签便宜一个量级 |
| 临时改价是否设硬限制 | **完全不设硬限制**，只留痕 + 软约束 | 设 ±20% 之类的上限 | **我们不向商户抽佣，摊主改价没有逃佣动机**——改低价只影响他自己的收入。硬限制会违背设计原点，而且**必然被绕开**；收摊甩卖降 50% 是常态。用透明度代替管制 |
| 离线暂存满了怎么办 | **200 笔是告警线，不是硬上限**；超了**仍然继续接受新交易，绝不静默丢弃** | 到上限就拒绝新交易 / 丢最旧的一条 | 静默丢弃 = 账实不符，"数据前后一致"的承诺当场作废。宁可暂存把磁盘写满（可恢复），也不能丢一笔（不可恢复） |
| 现金怎么入账 | **记进同一张支付流水表**，用"支付方式 = 现金"区分 | 单独一张现金表，或者改对账等式 | 对账等式必须对**全部**交易成立；现金单如果没有支付流水，等式就失效 |
| 使用率指标选哪三个 | 摊位使用率 + 现金交易占比 + 价目表维护率，**分子分母都来自系统自己** | 价签更新率；"日均智能秤交易占比" | 我们用物理价签替代电子屏，**系统感知不到价签有没有更新**——那是无法验证的假指标；原指标的分母是市场总交易笔数，系统同样拿不到 |
| 业务日和时间的来源 | **可注入**：环境变量指向一个本地时钟文件；不注入时取本机墙钟，行为和以前逐字段一致 | 直接把当前时间硬编码在代码里 | 仿真和跨营业日的回归需要一个"能推进"的业务日。注入时钟**不是伪造时间，是把时钟来源说清楚** |

> **"使用率指标"这一条，是我们用自己定的原则打自己脸的一次。** 我们定的原则是"只展示有真实来源的数据"（那是给顾客页定的）。后来我们把同一个原则用到自己的验收指标上，才发现原来那个"日均智能秤交易占比"**分母根本拿不到**——所以它被废掉了。
> 教训是：**验收指标必须先问"分子分母从哪来"，答不出分母的指标都是假指标。**

### 架构层的取舍

| 决策 | 结论 | 一句话理由 |
|---|---|---|
| 架构形态 | **单体 + 嵌入式数据库** | 本期峰值并发不到 20，独立数据库和缓存在这一期没有对应负载 |
| 环境策略 | **单环境** | 多环境的前提是"有一个生产环境需要保护"，本期唯一的运行对象是本机 Demo |
| 技术栈 | Flask + 标准库 `sqlite3` + 纯静态前端 + 原生进程 | 现场故障面最小；"一条命令启动、不依赖外网"这两条硬约束天然满足 |
| 依赖范围 | 白名单**只约束运行期**，开发期工具单列 | 根因不是"缺依赖"，而是**条款本身没写清运行期还是含开发期**——正确动作是澄清条款，不是破例把测试库塞进白名单 |
| 部署拆分 | 秤端 × N ↔ 中台 × 1；**中台仍是单体** | 动因是物理部署，不是组织规模；微服务的几条触发条件我们逐条对照过，一条都不满足 |
| 秤端技术栈 | **ESP32-S3 + ESP-IDF（C）** | 成本、确定性和可审计性；这一条偏离了原来的"只用 Python"，走了完整的修订程序 |

每一份决策都写了**重新评估的触发条件**，也就是"什么情况发生了我们就要回头重开这个决策"。举两个：

- **单体**：并发写入的摊位数**连续超过 5 分钟**在 20 以上；或者核心表行数触到容量阈值。
- **部署拆分**：秤端超过 500 台；或者出现**第二个市场**且需要跨市场结算；或者固件版本不一致真的导致过一次协议不兼容；或者中台接入的终端出现了秤以外的第二类设备（电子价签、摊位屏等）。
- **秤端技术栈**：纯 C 的核心装不下需求；或者计价口径里出现了整数表达不了的东西；或者单台成本超过推荐档上限；或者**"没有硬件在环"这个缺口真的导致过一次交付事故**。

### 验收和质量上的取舍

| 取舍 | 我们选的 | 为什么 |
|---|---|---|
| 验收看什么 | 三个**分子分母都是系统自有**的使用率指标 | 装机量口径下维护投入的考核收益是 0 |
| 单文件行数上限 | **不放宽**，按接口语义拆文件 | 不为凑行数而拆、也不为了让检查通过而放宽阈值 |
| 覆盖率 | 涉钱路径 ≥90%，整体 ≥70% | 这是**有意取低的诚实值，不是放水**——本期范围是单机演示 MVP，覆盖重点压在涉钱路径和验收场景上 |
| 重复率 | **不设数值阈值**，列为人工抽查的关注项 | 没有自动检测工具，**一个无法自动验证的阈值就是假指标** |
| 安全底线怎么表达 | "必须 0 次 / 100% 通过"，不用百分比 | "身份证字段出现率 0.1%"这种写法逻辑上就是错的——允许 0.1% 就等于允许它出现 |

## 七、你提的五个问题，我们分别怎么答

> 这五个问题出自需求方的原话，我们按原顺序逐条回答：**每条先给结论，再给机制，最后给能当场核对的证据。**

### 问题 1：怎么保证一笔交易正确归属到对应商户？

**答案：归属不靠"请求里填了什么"，靠"这笔交易从哪台绑定设备/哪个会话发起的"。**

| 层 | 做法 |
|---|---|
| 会话层 | 秤端必须持一个绑定摊位的会话令牌，**只允许访问该会话绑定摊位的数据**；越权返回 403 |
| 设备层 | 分离版下，授权范围**只取自中台保存的设备绑定**（市场 + 摊位）；请求体或路径里出现摊位号、市场号也**不采信** |
| 声明不等于授权 | 安装时声明的摊位号只用来**暴露不一致**：和已保存的绑定不符就报错，**不自动改绑** |
| 数据层 | 交易挂在摊位上，摊位挂在商户上；八张业务表带市场归属 |
| 防串号 | 幂等键按**摊位作用域**去重，不是全局去重 |

我们实测过：**20 个秤端进程并发对 1 个中台**，每个摊位恰好 2 笔，幂等键零碰撞，**零串号**。

### 问题 2：怎么保证称重、商品、价格、订单和支付之间的关联？

**答案：用一条不可绕过的强制链把它们钉在一起，再用"三线重合"把它验出来。**

| 关联 | 机制 |
|---|---|
| 称重 → 计价 | 金额 = 单价 × 重量，全程整数分和整数克；重量小于等于 0 或超过 50 公斤**直接不创建交易** |
| 商品 → 价格 | 商品先归一到标准品类；价目表按"摊位 × 营业日"；**没有价目表就不许成交，不允许按 0 元记账** |
| 价格 → 订单 | 订单行同时记重量、原价、改后价、金额、以及"改过价"和"抹过零"两个标记 |
| 订单 → 支付 | 支付流水挂交易号；**一笔交易最多一条成功流水**；现金走同一张表 |
| 状态约束 | 状态单向流转（已计价 → 支付失败 → 已收款 → 已冲正），**不在流转图里的流转一律非法** |
| 可验证性 | **订单总额 = 支付流水 = 分账明细**，由原始表现场算，**不落一张对账结果表**——落表就等于多了一份会和原始数据对不上 |
| 不可绕过 | 界面上**没有"随便输金额"的入口**；改价必须走留痕接口 |

### 问题 3：怎么支撑基于商户实际交易流水的佣金计算？

**答案：能算，而且刻意做成"口径可配 + 按实收金额 + 按日聚合 + 可重算"。** 但方案论证部分同时说明：**这笔钱不该向商户收。**

| 层 | 做法 |
|---|---|
| 口径可配 | 收费对象、费率（万分比整数）、品种档位、生效期，四项都可配 |
| **按实收金额** | 佣金按**实收**算，不按标价——议价、抹零之后不会算错基数 |
| 按日聚合 | 按"摊位 × 营业日"聚合；退货冲正后**按需重算**，版本递增、旧版本保留可追溯 |
| 结算单 | 等于期内各日聚合之和；重算生成新版本，旧版本不改 |
| 抹零 | **抹零必须从分账基数里减掉** |
| 口径唯一 | 佣金/日聚合/结算/看板一律在中台，秤端不承载 |

**跑通的证据**：在"向商户抽 200 个基点、30 个营业日"的联调档里，系统算出的日佣金合计 **5699 分** ÷ 同期已结算订单 **284872 分** = **200.1 个基点**。换一条口径，佣金跟着变——**仿真那边没有第二份佣金口径**，两边用的是同一个计算模块。

**为什么不该收**：见前面三例失败和温州模式。我们把"能算"和"该不该收"当成两件事分开讲——**能算是工程能力，该不该收是业务判断。**

### 问题 4：怎么在业务可靠性、操作效率和硬件投入之间取舍？

**答案：可靠性 > 操作效率 > 硬件投入，顺序不能颠倒。** 每一档都有具体的落点。

| 维度 | 取舍 |
|---|---|
| **可靠性（最高）** | 绝不静默丢弃任何一笔交易：暂存阈值是告警线不是硬上限，超了还继续收；写入失败**明确报错且不得标记为成功**；补传成功后必须清除本地副本 |
| 资金一致 | 金额整数分、重量整数克，对账等式精确成立；现金进同一张支付流水表，否则等式对全部交易不成立 |
| 操作效率 | 禁止打字、图标和快捷键选品、价目表营业前设好、交互不超过 3 次 |
| 效率 vs 管制 | 临时改价**不设硬限制**，只留痕。因为不抽佣就没有逃佣动机，硬限制必然被绕开 |
| 硬件投入 | 默认非 AI 溯源秤档 + 物理价签，不是功能最多最贵的那档 |
| 硬件谁出钱 | 市场方出资，**含维保与计量检定**——只"免费"不够 |
| 验收口径 | 看使用率不看装机量 |
| 架构投入 | 不引入消息队列、缓存、全文搜索、独立数据库；分离版只加一层边缘 |
| 性能的量化边界 | 响应时间**随磁盘不随代码**（同一段代码同一负载，快盘的 p50 43ms/p95 73ms，仓库所在的慢盘 p50 297~354ms/p95 683~770ms；根因是 fsync 成本，256KB 写 + fsync 的 p50 快盘 2ms vs 慢盘 37ms）。处置是**换数据目录到快盘，不改代码、不放宽阈值**——**先实测再决定** |
| 质量控制 | 单文件行数上限不放宽，宁可按语义拆文件 |

### 问题 5：还有哪些关键问题需要在真实业务里进一步确认？

**有，而且我们主动列了清单，不等你问。** 分三类：

| 类别 | 内容 |
|---|---|
| **业务与数据** | 实地回访证据缺 2025–2026 年（现有反面证据集中在 2020–2022）· 硬件成本细项没有公开成交数据 · 底册导入的格式/字段/责任方待确认 · 离线暂存的加密存储 · 批发/团购的纸质凭证 · 使用频率与峰值是待验证假设 · **财务证据链的保留期要你方财务确认** · "市场口径的智能秤交易占比"这个指标的分母系统算不出来 |
| **工程与固件** | 分离版传输层还是明文 · 没有硬件在环 · 固件没在真机上编译运行过 · 秤的标定没做 · 设备重复预注册会换令牌 · 市场维度没有数据库级外键 · 多进程并发建库没测过 |
| **没有公开数据的参数** | 设备年故障率、维修单价、罚款金额、扫码率基线、信任的衰减/恢复速率、商户退出阈值——**只给方向，不给数值** |

详细清单见 [问题梳理](01-问题梳理.md) 第九、十节。

### "可现场运行"这一条我们是怎么落实的

题目写得很明确：**Demo 要现场真实运行，不能拿 PPT、截图或录屏代替。**

| 我们的做法 | |
|---|---|
| 系统是**原生进程**，双击启动脚本即起 | 不用容器、不依赖外网、不引用任何 CDN |
| 仓库里**没有任何 .pptx / .mp4 / .mov / .avi / .gif 演示产物** | 这是可机械核对的 |
| 我们自己走查用的截图**明确标注不是提交物** | 原话是"提交物是系统本身，不是这些图" |
| **三种现场降级方案** | 同机双窗口、局域网手机真机扫码、端口被占用时换端口 |
| **三层"能不能跑"都验过**，不是只验功能 | ① 功能层：六步主链真浏览器走查 ② **依赖层**：在没有 Flask 的环境里自证、服务 3.0 秒就绪、四个页面全部 200 且声明 UTF-8、没有替换字符 ③ **交付层**：包解压后文件与元数据齐全 |
| 交付包在"没有 Flask、没有外网、解压到和开发盘不同的盘"的环境里实测可用 | 见下 |

**为什么"能不能跑"要分三层验**——这是被一次事故逼出来的：第一次给现场准备"无外网兜底包"时，我们只拷了包目录、没拷包的元数据。验收方式是 `import flask` 成功，于是写下"兜底成立"。**真去起服务才炸**——框架在初始化 HTTP 服务器时要读自己的包元数据来拼响应头，缺了它进程直接退出。

**现场的人双击启动脚本，窗口一闪就没了**——这是现场最难当场定位的那种死法。所以现在这条规矩是：**验收"兜底可用"必须真起服务、真打页面**，而且页面判据不能只看 HTTP 200，**还要看 charset 声明和有没有替换字符**。

| 题目的原话 | 我们怎么做的 |

## 九、我们对这套方案的把握程度

这一节讲清楚：**哪些是验证过的、哪些是设计推断、哪些必须到现场才能确认。**

### 已经跑通并且可以当场复现的

- **六步主链**：真浏览器、同机双窗口，逐步走查过一遍，退出码 0。走查过程本身也修掉了几个问题，其中一个是**走查脚本自己在骗人**（断言通过了，但根本没验到东西）——这类"假绿"比走查失败更危险。
- **补传的数据一致性**：现场界面显示的是四个**服务端计数**——"补传 3 笔 · 重复丢弃 0 笔 · 失败 0 笔 · 清除副本 3 笔 · 剩余待补传 0"，不是界面自己编的。
- **涉钱三线重合**：订单总额 = 支付流水 = 分账明细，含现金和退货冲正。
- **分离版的真进程对接**：20 个秤端进程对 1 个中台，全部正常退出，总耗时 1.43 秒，零串号。
- **固件的计价与离线核心**：在主机上编译并跑了 **478 条断言**（计价 137 + 离线队列 153 + 报文编解码 109 + 网络同步 79），两个 C 标准、`-Wall -Wextra -Werror` 零告警。黄金向量逐字节可复算。
- **接口覆盖**：主契约 32 个接口 + 秤端接入 7 个接口，联调时被真实调用过并逐条比对。
- **断网彩排**：用死代理模拟断网，另有旁路和对照实验证明探测确实能区分。

**测试规模**：**696 项**，分接口契约、浏览器端到端、真并发性能、仿真四层。本机实测 **693 通过 / 3 项不适用**——那 3 项断言数据目录必须在 C 盘，在不带盘符的 Linux 路径上必然不成立，属环境断言；**这 3 项没有在 Windows 演示机上单独复跑过**。基础环境是**清掉所有编码相关环境变量**之后的基线——我们有一条规矩：**靠环境变量才通过不算通过**，那意味着"我这台绿、你那台满屏乱码"。

### 属于设计推断、还没被现实检验的

- **每个关键取舍的方向**：它们有调研依据，但**"在这套设计下会怎样"是推断，不是实测**。
- **房屋规模**：容量推算是按待验证的日均笔数假设做的，不是实测。
- **仿真给出的机制**：只作为**机制层面的参考**，不作为承诺。（每条结论的档位见 [问题梳理](01-问题梳理.md) 第九节。）

### 必须到现场才能确认的

**秤端这套东西，我们只在纸面和主机上验证过。** 真实称重采样、触摸响应、WiFi 射频、掉电时序、Flash 磨损、屏幕在菜市场的强光下能不能看清——这些都得上真机才知道。固件里除了网络同步那一块，其余代码从没在 ESP32 上编译运行过。

**这不是"做得不够"，这个阶段本来就该这样**：先把中台和流程做扎实，硬件等选型定了一起上。同样地，以下这些也必须到现场才能有答案：真实市场的网络条件、摊位日均笔数、商户的实际接受度、以及硬件采购的实际价格（我们手上只有零售价和公开中标价，没有批量议价结果）。

### 三件我们明确不会说的事

| 不会说 | 事实 |
|---|---|
| "仿真验证了我们的设计" | **不能**。六条回测全部判定"不成立"，而且四类含义完全不同；仿真没有独立验证任何一条实地失败案例。方案的依据是那 26 条调研结论，不是仿真 |
| "我们实现了温州模式" | **没有**。费率写不进 0%，收费对象字段只记录不参与计算 |
| "固件已经编译通过" | **没有**。真机上从没编译运行过 |

## 十、需求留白的地方，我们主动划了边界

题目写得很清楚："请结合项目背景，**自行分析并作出设计选择**"、
"以上问题用于帮助理解场景，**不代表完整需求清单或唯一解法**……参赛者可以自行识别其他关键问题，并决定哪些内容进入 MVP"。

**我们把这段留白当成正题来答。** 需求边界不完整是既定前提，所以我们的做法不是"假装把需求补完整"，而是**把边界写清楚**：

| 我们主动做的事 | 在哪里 |
|---|---|
| 关键假设分两类：有依据的可以直接用；**没有依据的只给方向、不给数值** | [问题梳理](01-问题梳理.md) 第七节 |
| 主动列出 **15 条"不做"**，每条写明理由——不是"暂缓" | [问题梳理](01-问题梳理.md) 第八节 |
| 主动列出 **15 件"还没做到"的事**，包括"温州模式没实现""仿真不能证明设计对""顾客信任是可恢复的这件事我们是循环论证""固件没在真机上跑过""标定没做" | [问题梳理](01-问题梳理.md) 第九节 |
| 主动列出**还需要你确认的 8 件事** | [问题梳理](01-问题梳理.md) 第十节 |
| 主动承认仿真**没有独立验证任何一条实地失败案例** | [问题梳理](01-问题梳理.md) 第九节 |

> 需求不完整的时候，最危险的不是"漏做了什么"，而是**把假设当成了已确认的需求**。所以我们宁可多写一节"我们不做什么、我们没做到什么"，也不去补一个看起来完整、实际上没有依据的需求清单。
