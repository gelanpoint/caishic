### 铁律 1 · 不可靠的东西不要留给环境（两条，同一类）

- **症状 A（`2026-10-02` 父代理现场验收）**：`cmd /c call D:\...\start.bat` → `exit=255`、`/healthz` 无响应，
  stderr 是 `'免安装打包，见' 不是内部或外部命令` / `'网、不使用' …` / `" was unexpected at this time.`，
  stdout 为空。**真因**：`cmd.exe` 按**控制台代码页**解析 `.bat` 的**字节**，中文被拆断成"命令"；
  出现在 `if ( )` 块内时，真正该显示的提示（"端口已被占用"）被解析错误顶掉。
  **处置**：`start.bat` 改为**纯 ASCII**（实测非 ASCII 字节 = 0），中文一律由 `scripts/launch.py` 打印。
  **注**：AI 在 8 个代码页下**未能复现**该症状 → 结论是"按机制移走整类风险"，不是"修好我复现到的那一行"。
- **症状 B（同一轮复测）**：父代理机器 `364 passed, 3 failed`（AI 本机 `367 passed`），
  报错形态 `assert '已启动' in '…\ufffd\ufffd…'`。**真因**：Python stdout 编码取自
  `PYTHONUTF8`/`PYTHONIOENCODING`/**系统 locale**；干净环境实测 `locale=cp936`、`stdout=gbk`
  ⇒ 子进程写 GBK 字节、捕获方按 UTF-8 解码 ⇒ 满屏 `\ufffd`。AI 本机"绿"只是因为**每条命令都带了
  `PYTHONIOENCODING=utf-8`**。
  **处置**：新增 `app/console.py::force_utf8_stdio()`（**被重定向时强制 UTF-8**、接真控制台时沿用控制台编码），
  `run.py` 与 `scripts/launch.py` 都自定编码；**测试捕获一律显式 `encoding="utf-8", errors="replace"`**。
- **铁律条文**：**输出编码不许依赖环境变量；测试捕获一律显式编码；验收基线 = 清掉
  `PYTHONUTF8`/`PYTHONIOENCODING` 后仍然绿**（由 `tests/e2e/test_demo_launcher.py` 两条回归盯着；
  灵敏度已实测：关掉修复必红 → 还原复绿）。
  > 顺带记一个坑：`cmd /c "set PYTHONUTF8= && python …"` 里 `&&` 前的**空格会被算进变量值**
  > （实测变成 `" "`）→ `Fatal Python error: preconfig_init_utf8_mode: invalid PYTHONUTF8 environment
  > variable value`，Python 直接起不来。正确写法**不带空格**：`set PYTHONUTF8=&& python …`。

**`model ↔ live` 一致性（§7.3）**

- 档位：**30 营业日 × ≤20 走秤笔/日**（`live_run` 缺省只有 4 笔/日，整轮 120 笔，逐笔对账密度不够）；
  model 侧到达数同步降到 140/日，**密度上限是唯一被削减的维度**，且削减发生在**已算好的决策流**上。
- 实测：**30 个营业日 × 270 个字段 + 10 张结算单，0 条不一致**（容差 ≤1 分 / ≤1 笔）。
  比对项 = 走秤笔数 / 总额 / 佣金 / 三指标六个分子分母 / `reconciliation.balanced` / 结算单金额。
- **三处口径差显式量化，不是静默忽略**：① 私下交易（model 侧走秤 600 / 私下 1474 笔 ⇒ model 侧
  `M-04` 0.289，系统侧看不到分母）⇒ 只在走秤通道对账，shadow 笔数与影响单列；
  ② 取整与计量单位（model「每 500g + 银行家舍入」vs 系统「每公斤 + 四舍五入」）：单价按 ×2 换算，
  期望金额用系统那条规则重算，**两套规则差 1 分的笔数 = 1 笔**（单列）；
  ③ 佣金（model 自按日浮点累加 vs 系统逐摊逐日 `half_up`）：model 侧按系统口径独立复算后再比。
- **灵敏度负例**：从 model 事件流里**真删掉一笔成交**，拿**同一份** live 报告重新对账 ⇒
  **变红，报 6 条问题**（日总额差 952 分、日佣金差 19 分、结算单差 547295 分…）。
  ⚠️ 如实说明：**"少一笔"本身在 ≤1 笔的笔数容差内**，所以笔数字段抓不住它，是**金额字段**抓住的 ——
  这不是漏判，是容差的必然结果，报告里写明了。

**档 2 · 匹配矩（POM）—— 做扎实到什么程度（如实说）**

### `T-SIM-11` 实测（`2026-10-04`，仿真线第七任接手：**先查根因，再做材料**）

> `M-04 = [0.594, 0.479, 0.305, 0.183, 0.727, 0, 0, 0]`，**先逆势大涨再直接归零**。
> 本节是**用测量**（不是推断）查到的根因 + 修复 + 对已登记结论的影响。

**查根因的三步（每步都有可复现输出）**

| 步骤 | 测量方法 | 结论 |
| --- | --- | --- |
| ① 归零属于哪一类 | 逐期对照 `merchant_period`/`merchant_month`/`device_day`/`txn`/`consumer_period`/`lost_sale` | **不是设备不可用，也不是消费者崩塌**。**足额臂**第 5 期起 `device_day` 全天 **10/10 在用**（`{'working': 300}`），走秤率**仍然归零** |
| ② 第 5 期大涨的机理 | `merchant_month` 逐摊对照 | 第 4 期在营 3 摊里 **1 摊合规**（走秤 1605 笔）⇒ 0.183；第 5 期 **2 摊合规**（3454+3113=6567）⇒ 0.727。**不是"留下的商户表现更好"，是"抽到合规的摊位数从 1 变 2"** |
| ③ 根因 | monkeypatch 打印逐期 `Q` 与 `P(comply)` | `peer_mean_q` 从 **+0.09 → −7699.88**；在营商户的 `Q` 被扣 `ρ(1−φ)·Q̄_peer = 0.08 × (−7699.88) = −615.7`，而真实每元效用差只有 **~0.13**、温度 **0.05** ⇒ `softmax` 被垃圾值支配 |

**根因（一句话）**：`close_month` 把**已退出/停业**商户按 `volume = max(1.0, 实现流水)` 喂进 `observe()`
⇒「没有流水」变成「流水 1 分」⇒ `normalized = U/1.0 = −29999.75`（退出后只剩设备分摊 30000 与 `p_check·(F+L)=102500`），
**比真实每元效用（~0.25）大 10⁵ 倍**；`Q̄_peer` 又把**全部**摊位（含已退出）算进同伴均值，
于是这个垃圾值按 `ρ(1−φ)` 注入**每一个在营商户**。

**定性：真缺陷**（同时命中「数值溢出」与「空值传播」）—— `max(1.0, 0)` 只为除零兜底，
却把「没有数据」变成「经营失败 −30000」；退出是吸收态，离场商户已不在这个 10 摊同伴网络里。
**连带后果**：`M-19`（商户月净收入分布）的 `min` 被这些与经营无关的常数钉死（修复前 −118775 量级）。
