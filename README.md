# 菜市场数字化交易与佣金系统 MVP

> 一套**断网也能跑通**的菜市场交易与经营数据系统；
> 外加一套**多智能体仿真**，用来回答"这套设计放到真实环境里会发生什么"。

**技术栈**：Python 3.11+ · Flask · 标准库 `sqlite3` · 纯静态前端（无构建、无 CDN、无外部字体/图标库）· 原生进程。
**运行期依赖只有 `Flask`**（见 [`docs/adr/0004`](docs/adr/0004-依赖范围界定-运行期与开发期.md)）。

## 一、30 秒跑起来

**Windows**：双击 `start.bat`（或命令行 `python run.py`）
**Linux / macOS**：`./start.sh`（或 `python run.py`）

首次启动会**自动建库 + 导入种子数据**（幂等，重复启动不重复写），随后打印：

```
【局域网访问】本机 IP：192.168.x.x
  入口 1 · 操作端（秤端）   http://<ip>:8000/scale/
  入口 2 · 顾客扫码页       http://<ip>:8000/customer/
  运营端                    http://<ip>:8000/admin/
  入口导航页                http://<ip>:8000/
 数据文件：<数据目录>/market_trade.sqlite3
```

> 演示数据目录默认放在**用户数据目录**（`%LOCALAPPDATA%\MarketTradeDemo\data`）——这是**实测**决定的：
> 同一段代码、同一负载，接口响应在 C: 上 `p50 43ms / p95 73ms`，在仓库所在卷上 `p50 ~350ms / p95 ~700ms`，
> 根因是磁盘 `fsync` 成本（256KB 写 + fsync 的 p50：`2ms` vs `37ms`，与接口实现无关）。
> 想改回仓库内 `data/`：`set MT_DATA_DIR=` 后再启动。

**重置演示数据**：`python scripts/reset_demo.py`

## 一之二、分离形态（秤端 × N ↔ 中台 × 1，各自独立启动）

上面是**形态 1（单机 all-in-one）**。如果你要的是「**秤端与中台分开部署、经网络对接**」——
比如 100 个商家就是 100 台秤端服务对接 1 个中台——用**形态 2**。两者是**同一份领域代码**，
区别只在「谁托管秤端界面」，不是两套实现（依据 `docs/adr/0005-秤端与中台拆分.md`）。

```bash
# 终端 A —— 只起中台（不托管 /scale/ 秤端界面，该路径返回 404）
python run.py --mode split

# 终端 B —— 起一个秤端（中台没起来也能先起；多开几个终端就是多个商家）
python scripts/scale_host_runner.py --mid http://127.0.0.1:8000 \
    --device-id SC-000001 --stall-no A-01 --price-cents 480 --weight-grams 780
```

看点：

| 项 | 说明 |
| --- | --- |
| **各自独立启动** | 先起秤端、后起中台也行：秤端**不卡死不退出**，先把交易**本地暂存**（`AC-025` 前半段） |
| **真实 HTTP 对接** | 走标准库 `http.client`，不是进程内直调；7 个秤端接入端点见 `specs/.../contracts/scale-midplatform.md` |
| **本地计价用真固件代码** | 现场用 `zig cc` 把 **`scale-fw/core/*.c`**（与 ESP32-S3 上跑的**同一份 C 源码**）编成共享库，`ctypes` 调用 —— **不是 Python 复刻**；中台侧会独立重算并逐行比对（`AC-030`） |
| **补传** | 按 `staged_at` 升序；某条失败**保持暂存**且不阻断后续；成功后**清除本地副本**（`RL-8` / `NFR-013`） |
| **形态 1 不受影响** | `python run.py`（不带参数）的默认行为与启动横幅**逐字节不变** |

> ⚠️ **`scripts/scale_host_runner.py` 不是硬件在环**：它是**主机侧秤端**，真实称重采样、触摸屏、
> WiFi 射频、掉电时序、Flash 磨损**一律未验证**（未决项 `Q-21`）。它调用的确实是真 C 核心，
> 但**不能替代 ESP32-S3 真机**。

## 二、演示主线（对应「Demo 跑通主干」）

| 步骤 | 入口 | 看点 |
|---|---|---|
| 1 | `/scale/` | 商户**点图标选品**（不打字）→ 点预设重量或"读秤" → 自动计价 |
| 2 | `/scale/` | **收款**：现金 与 收款码 两条路（现金同样进支付流水表） |
| 3 | `/customer/` | 顾客扫码，看到**摊位信息 + 本笔明细 + 本摊标价一致率** |
| 4 | `/scale/` | **改价**（收款前）与**退货冲正** |
| 5 | `/scale/` | **离线开关** → 暂存若干笔 → 切回在线 → **补传**，界面待补传归零 |
| 6 | `/admin/` | 佣金口径、日终聚合、结算单、**对账**、使用率指标、审计留痕 |

**现场三种降级方案都在**：同机双窗口（无 WiFi 时）、局域网手机真机扫码、端口被占用时按提示换端口。

## 四、几个关键设计判断（做减法的部分）

1. **不向商户抽佣**：抽佣有**三例仓库内可核的失败**（成都温江、赣州龙南、南宁 7 个市场，见调研报告结论 21）；
   唯一活下来的是**向买方收费**的批发市场（温州菜篮子：向采购方收 0.5%~6%，不收摊位费）。
   系统仍实现**可配置的佣金引擎**（主链路要求），但方案论证部分明确给出"为什么不该收商户这笔钱"。
2. **商户拒绝的真根因是"八两秤"**：南宁商务局原话——"部分经营户之所以屡屡拒绝，说白了就是一些人今后不能再搞'八两秤'了"。
   **系统堵死的是作弊，不是让商户多付钱** —— 这一条决定了整个方案的取舍。
3. **硬件由市场开办方承担，含维护与统一检定**：绵阳政府免费送秤但"维修也不及时"→ 积灰弃用；**衡阳（邮政免费配秤）、杭州（统一配秤并统一检定维修）**的成功经验说明**免费 + 统一检定 + 免维护**三者缺一不可。
   **默认配置选非 AI 秤档**（有真实报价区间），而不是功能最多、最贵的那档。
4. **扫码页只显示"有真实来源"的字段**：字段白名单**多一个即失败**，且每个字段必须有非空真值。空壳页面会让顾客"再也不信这个标签"。
5. **验收看使用率，不看装机量**：装机量口径下维护投入的考核收益为 0 —— 这正是"设备闲置也能通过验收"的机制来源（仿真里复现了这个激励错配）。
6. **离线必须能补传、绝不静默丢弃**：暂存阈值是**告警线不是硬上限**；补传成功后本地副本清空且可被扫描验证。

## 五、验证与质量

- **测试共 753 项**（清掉所有编码相关环境变量后的基线，见下"交付铁律"），分四层：契约 / e2e（真实浏览器 + 真实二维码）/ 性能（真并发）/ 仿真（含多智能体回测与静态报告）。
  **本仓库开发环境（Linux/WSL）实测 750 通过 / 3 项不适用** —— 那 3 项断言数据目录的盘符必须是 `C:`（`tests/sim/test_live_run.py`），在不带盘符的 Linux 路径上必然不成立，属**环境断言**而非缺陷；**这 3 项我们未在 Windows 演示机上单独复跑**；
- 测试分四层：`tests/contract`（**38 端点**契约）· `tests/e2e`（真实 Chromium 走查 + 演示硬要求）· `tests/perf`（真并发压测 + 门禁）· `tests/sim`（仿真）；
- **每个"检查类"产出都带灵敏度负例**（把修复关掉必须变红）——不验证灵敏度的验证是摆设；
- 涉钱红线：**订单总额 = 支付流水 = 分账明细** 三线重合（含现金与退货冲正），有真实链路实测。

### 两条交付铁律（都是真实缺陷换来的）

| 铁律 | 当时的症状 |
|---|---|
| **输出编码不许依赖环境变量**；测试捕获一律显式编码；**验收基线 = 清掉变量后仍绿** | 在没设 `PYTHONUTF8` 的机器上，启动横幅中文全变 `\ufffd`，断言 `'已启动' in log` 失败 —— 而"开发机一直是绿的" |
| **交付前跑一次「新克隆验证」** | `.gitignore` 里未锚定的 `env/` 把 `sim/env/` 整个吞掉：**本地全绿、新克隆必炸** |
