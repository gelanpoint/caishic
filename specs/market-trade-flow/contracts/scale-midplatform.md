# market-trade-flow 秤端 ↔ 中台同步契约（形态 2）

- 特性目录：`specs/market-trade-flow/`
- 数据模型：[../data-model.md](../data-model.md)（**字段语义与校验规则的唯一事实来源**；本文件只写**传输层**约束，不重复定义字段含义）
- 技术方案：[../plan.md](../plan.md)
- 主契约：[rest-api.md](./rest-api.md)（运营端 / 顾客端 / 单机秤端页面，**本文件不改动它**）
- 架构依据：[`ADR-0005`](../../../docs/adr/0005-秤端与中台拆分.md)、[`ADR-0006`](../../../docs/adr/0006-秤端嵌入式技术栈.md)
- Base URL：`/api/scale/v1` ／ 认证方式：**设备令牌**（请求头 `X-Device-Token`）
- 日期：`2026-10-06`
- **状态**：`草稿` —— `ADR-0005` / `ADR-0006` 当前为 `提议`，**未获负责人批准前不得据此写实现代码**（宪法 §6：AI 只起草）

> **本契约存在的理由**：形态 2 下秤端是**资源受限的嵌入式终端**（`ADR-0006`），不能照搬主契约的通用端点集。
> 它只被允许看见「本摊位的商品、本摊位的价目表、本设备的同步状态」三件事，其余一律留在中台。
> 端点数与响应体宽度都是**受约束的设计量**，不是随手裁的。

## 1. 通用约定

1. 请求与响应均为 JSON（UTF-8）。**响应体一律为窄体**：不得下发运营端/看板结构，不得下发与本次调用无关的档案数据。
2. 统一错误响应格式**与 [rest-api.md](./rest-api.md) §1.2 完全同一格式**（`{"error": {"code", "message", "detail"}}`）——
   **定义只在该文件写一次**，本文件只新增错误码，不复述格式。
3. 写操作端点要求请求头 `Idempotency-Key`（长度 ≤64）；服务端据此去重，重复请求返回**首次结果**而非报错。
4. 时间字段一律 ISO-8601 `YYYY-MM-DD HH:MM:SS`；**金额一律为整数「分」、重量一律为整数「克」**（换算与取整口径见 [../data-model.md](../data-model.md) §0）。
5. **响应体中一律不得出现身份证号或银行卡号字段**（`REQ-024`、`NFR-012`）。本契约的响应体同样受 `AC-012` 的扫描覆盖。
6. **授权只来自设备令牌，不来自请求参数**：中台一律以**设备注册时绑定的（市场, 摊位）**为授权范围。
   请求体或路径中**不得**出现可用来扩大授权范围的 `stall_id` / `market_id`；出现了也**不采信**（`REQ-036`、`REQ-032`）。
7. **秤端不是账口**：所有入账金额以**中台重算结果**为准（`REQ-038`）。秤端上报的金额只作为**比对输入**，不作为入账依据（语义见 §5）。
8. **传输层（本期的已知缺口）**：明文 HTTP，仅限受控局域网，**中台禁止暴露到公网**。
   `NFR-008` 的放宽理由已重新登记为**待批准**（见 [../spec.md](../spec.md) §4.2），TLS 为演进项（未决项 `Q-20`）。
9. **协议版本**：请求头 `X-Scale-Proto: 1`；中台发现不兼容按 `MT-2003` 拒绝（见 §4、§7）。
10. 本契约**不引入任何新的运行期依赖**：中台侧仍只用 Flask + Python 标准库（`ADR-0004`）；秤端侧只用 ESP-IDF 组件（`ADR-0006`）。

### 1.1 幂等语义总表（本契约范围）

| 场景 | 幂等键 | 重复提交的行为 | 来源 |
| --- | --- | --- | --- |
| 交易上报（在线 / 补传**同一套语义**） | `Idempotency-Key`（即 `client_idempotency_key`） | 返回**首次结果**（含首次的重算比对结论），不新建交易、不重复计佣 | `REQ-039`、`REQ-015`、`AC-031` |
| 设备激活 | `device_id`（天然唯一） | 返回**既有绑定**，不新建绑定 | `REQ-036` |
| 收款确认 | `Idempotency-Key` | 按交易状态机返回（`priced → paid` 单向），不重复记账 | `REQ-026`、`REQ-029` |
| 退货申请 | `Idempotency-Key` | 冲正**只发生一次**，返回首次结果 | `REQ-042`、`REQ-013`、`AC-002` |

> **在线与补传共用同一个端点**（`POST /api/scale/v1/transactions`）：差别只在**时间**——补传的 `business_date` 取
> 秤端暂存时记下的营业日，中台按该值入账而不是按到达日的墙钟。这与主契约 §3.15 补传的口径同源，
> 故**不另设补传端点**（多一个端点就多一处口径分叉）。

## 3. 端点详情

### 3.1 POST `/api/scale/v1/devices/activate`

设备首次上线（或更换固件后复上线）时调用，取回**绑定**与**运行配置**。

- 请求头：`X-Device-Token`（中台侧预注册时生成并烧录到秤端）
- 请求体：
  `{"device_id": "SC-000123", "firmware_version": "0.1.0", "hardware_rev": "esp32s3-n8r8", "stall_no": "A-012"}`
  - **`stall_no` 可选**：现场安装时由安装工扫码/键入摊位号，用于**声明本机装在哪**。
    - **不带** ⇒ 以中台预注册时的绑定为准（设备出厂即绑定，安装工无需操作）；
    - **带上且与既有绑定一致** ⇒ 正常激活；
    - **带上且与既有绑定不一致** ⇒ **`MT-2005`**（见 §4）。
  - ⚠️ `stall_no` 是**声明**不是**授权**：它不能用来把设备绑到别的摊位，只能用来**暴露不一致**。
    真正的授权范围始终取自中台侧的绑定记录（§1 第 6 条）。**这正是 `MT-2005` 唯一可构造的入口** ——
    没有它，该错误码没有任何触发路径，等于白登记。
- 响应 `200`：
  ```json
  {
    "market": {"market_code": "M-0001", "name": "示例菜市场"},
    "stall": {"stall_no": "A-012"},
    "business_date": "2026-10-06",
    "server_time": "2026-10-06 08:12:33",
    "config": {
      "offline_warn_threshold": 200,
      "customer_base_url": "http://192.168.1.10:8000/customer",
      "catalog_version": 7,
      "price_list_business_date": "2026-10-06",
      "proto": 1
    }
  }
  ```
- 可能错误：`MT-2001`(401)、`MT-2005`(409)、`MT-2003`(409)
- **重复激活**：返回**既有绑定**（不报错、不改绑定）—— 秤端断电重启会反复走这一步，报错会把它卡在开机。

### 3.2 POST `/api/scale/v1/devices/heartbeat`

- 请求体：`{"device_id": "SC-000123", "pending_count": 3, "firmware_version": "0.1.0"}`
- 响应 `200`：`{"business_date": "2026-10-06", "server_time": "...", "config_changed": false, "catalog_version": 7}`
- **`pending_count` 由秤端自报**：中台据此可观测"哪些摊位长期有未补传数据"，但**不据此拒绝任何交易**（`NFR-014`）。
- 可能错误：`MT-2001`(401)、`MT-2003`(409)

### 3.3 GET `/api/scale/v1/catalog`

- 查询参数：`since_version`（可选，缺省 0 表示全量）
- 响应 `200`：`{"catalog_version": 8, "products": [{"product_id": 1234, "name": "本地小白菜", "category_id": 3, "status": "active"}], "categories": [{"category_id": 3, "name": "蔬菜"}]}`
- 响应体**只含秤端选品与计价所需字段**：不含成本、不含佣金相关字段（`REQ-036`、`NFR-015`）。
- 可能错误：`MT-2001`(401)

### 3.4 GET `/api/scale/v1/price-list`

- 查询参数：`business_date`（可选，缺省取中台当前业务日）
- 响应 `200`：`{"business_date": "2026-10-06", "items": [{"product_id": 1234, "unit_price_cents": 320}], "price_list_version": 11}`
- **这是秤端离线计价的唯一依据**（`REQ-037`）。秤端必须缓存之，缓存与中台不一致时**以中台的比对结论为准**（§5）。
- 可能错误：`MT-2001`(401)
- **价目表为空时不得报错**：返回空 `items` 数组。秤端遇空价目表应在选品后**拒绝计价并提示先设价**（对应主契约 `MT-1006` 的语义），
  而不是让秤端在缺价时静默按 0 元成交。

### 3.5 POST `/api/scale/v1/transactions`（核心）

- 请求头：`Idempotency-Key`（必填）、`X-Device-Token`
- 请求体：
  ```json
  {
    "business_date": "2026-10-06",
    "captured_at": "2026-10-06 08:20:11",
    "origin": "online",
    "price_list_version": 11,
    "items": [{"product_id": 1234, "weight_grams": 780}],
    "amount_cents": 250,
    "local_lines": [{"product_id": 1234, "unit_price_cents": 320, "weight_grams": 780, "amount_cents": 250}],
    "round_off_cents": 0,
    "client_idempotency_key": "SC-000123-20261006-0007"
  }
  ```
  - `amount_cents` = 秤端**本地计价**的应收合计（`REQ-038`）；`local_lines` 是它算出来的明细（用于定位差异到具体行）。
  - `origin` ∈ `online` / `offline_backfill`；补传时 `business_date` 必须是**暂存时**的营业日。
- 响应 `201`（新建）/ `200`（幂等命中）：
  ```json
  {
    "transaction_no": "T-20261006-0007",
    "business_date": "2026-10-06",
    "status": "priced",
    "authoritative_amount_cents": 250,
    "reported_amount_cents": 250,
    "amount_mismatch": false,
    "mismatch_detail": null,
    "replayed": false,
    "receipt_url": "http://192.168.1.10:8000/customer/receipts/T-20261006-0007"
  }
  ```
  - **入账金额一律是 `authoritative_amount_cents`**（中台重算值）。
  - `amount_mismatch = true` 时：`mismatch_detail` 必须逐行给出差异（至少 `product_id` 与两个金额），
    且中台**必须已写入一条 `audit_log` 留痕**（`event_type = scale_amount_mismatch`）——**不得静默采信秤端**（`AC-030`）。
  - 不一致**不是错误响应**：仍返回 2xx，因为该笔交易**必须成立**（`RL-9` 绝不静默丢弃），
    差异通过标记 + 留痕暴露，而不是靠拒绝。
- 可能错误：`MT-2001`(401)、`MT-2002`(403)、`MT-2003`(409)、`MT-2004`(422)、`MT-1006`(409 无价目表)、`MT-1012`(409 同键不同体)
- **幂等命中时 `replayed = true` 且 `amount_mismatch` 等字段为「首次」的结论**（不是重新比对的结论）——否则同一笔在重试前后会给出两个说法。

### 3.6 POST `/api/scale/v1/transactions/{transaction_no}/settle`

- 请求头：`Idempotency-Key`（必填）
- 请求体：`{"method": "cash"}` 或 `{"method": "qr"}`
- 响应 `200`（`method = qr`）：`{"transaction_no": "...", "status": "priced", "qr_payload": "http://192.168.1.10:8000/customer/receipts/T-20261006-0007"}`
  - `qr_payload` 是**中台的顾客页地址**：秤端据此**本地生成二维码**显示给顾客（`REQ-043`）。
    秤端**不承载顾客页面**，也不得把 `qr_payload` 指向自己。
- 响应 `200`（`method = cash`）：`{"transaction_no": "...", "status": "paid", "paid_at": "..."}`
  - 现金按主契约 §3.10 口径写入**同一张支付流水表**（`REQ-010`），本契约不另立现金表。
- 可能错误：`MT-1001`(409 状态不允许)、`MT-2001`(401)、`MT-2002`(403)

### 3.7 POST `/api/scale/v1/transactions/{transaction_no}/refund`

- 请求头：`Idempotency-Key`（必填）
- 请求体：`{"amount_cents": 250, "reason": "顾客退货"}`
- 响应 `201`：`{"transaction_no": "...", "status": "refunded", "refund_amount_cents": 250, "commission_delta_cents": -5}`
  - **冲正与佣金扣减均由中台计算**（`REQ-042`、`NFR-015`）；秤端不参与任何金额计算，只提交申请。
- 可能错误：`MT-1003`(422 超过原单）、`MT-1001`(409)、`MT-2001`(401)、`MT-2002`(403)

## 4. 统一错误码表（本契约新增段）

前缀 `MT-2xxx` 为**秤端接入段**，与主契约的 `MT-1xxx` **连续编号、互不重叠**。
格式与字段语义**沿用 [rest-api.md](./rest-api.md) §4**，此处只登记新增码。

| 错误码 | HTTP 状态 | 含义 | 触发条件 | 调用方（秤端）处理建议 | 关联 |
| --- | --- | --- | --- | --- | --- |
| `MT-2001` | 401 | 设备未激活或令牌无效 | `X-Device-Token` 缺失、错误，或设备未在中台预注册 | 进入「未激活」界面并明确提示联系运维；**不得进入营业流程**（否则交易无处入账） | `REQ-036`、`AC-027` |
| `MT-2002` | 403 | 设备与目标的（市场, 摊位）不匹配 | 请求体/路径携带了与绑定不一致的 `stall_id` / `market_id`，或交易号不属于本摊位 | **不重试**；清掉请求里越权的字段 | `REQ-036`、`REQ-032`、`AC-027` |
| `MT-2003` | 409 | 协议版本不兼容 | `X-Scale-Proto` 不在中台支持集合内 | 明确提示「固件与中台版本不匹配，需升级固件」；**不得降级重试** | `ADR-0005` §5 触发条件 3 |
| `MT-2004` | 422 | 上报载荷不合法 | 字段缺失、类型不符、`items` 长度越界、`weight_grams` 越界 | 按 `detail` 逐项修正；**该笔保持暂存**，不得丢弃 | `REQ-041`、`MT-1008` 同类 |
| `MT-2005` | 409 | 设备绑定冲突 | 激活请求携带的 `stall_no` 与中台侧该设备的**既有绑定**不一致（§3.1） | 提示运维先在运营端解绑；**不自动改绑**、**不采信请求里的 `stall_no` 作为新绑定** | `REQ-036` |

> **为什么「金额不一致」不在这里**（§3.5 已说明，此处再点明）：把它做成错误码会逼出一个坏选择 ——
> 要么中台拒绝该笔（**违反 `RL-9` 绝不静默丢弃**，且断网补传的场景下摊主已经收了钱），
> 要么秤端自己改金额（**账口从两个变成三个**）。故差异走「标记 + 留痕 + 以中台为准入账」这条路。

## 5. 上报与重算比对语义（本契约最硬的一条）

1. 中台收到上报后，**必须**用权威计价实现（`app/domain/pricing.py`，主契约同一实现）对该笔重算；
2. 逐行比对：`product_id`、`weight_grams`、`unit_price_cents`、`amount_cents`；
3. **一致** ⇒ `amount_mismatch = false`，正常入账；
4. **不一致** ⇒ 同时做三件事，**一件都不能省**：
   - 入账金额取**中台重算值**（`authoritative_amount_cents`）；
   - 写一条 `audit_log` 留痕（`event_type = scale_amount_mismatch`，含设备号、幂等键、两个金额、逐行差异）；
   - 响应里如实返回 `amount_mismatch = true` 与 `mismatch_detail`。
5. **不得**因不一致而拒绝、丢弃或静默改写秤端上报的原始值 —— 原始值必须留在留痕里，否则差异无法追查。

> 这条语义的**灵敏度**必须被测：人为把秤端上报金额改一个分位，`AC-030` 必须变红。
> 「不验证灵敏度的验证是摆设」（本项目既有纪律，见 `tests/contract/test_admin_report.py::test_usage_metrics_numerator_is_actually_queried` 的先例）。

## 6. 离线与补传（两端的责任边界）

| 环节 | 秤端责任 | 中台责任 |
| --- | --- | --- |
| 断网期间 | 继续接受交易；**本地持久暂存**（定长记录 + CRC）；界面有明确离线标识 | 无（不可达） |
| 达告警阈值 | 提示摊主联系运维，**仍继续接受**（`NFR-014`） | 通过心跳的 `pending_count` 可观测 |
| 暂存写入失败 | **明确报错**且不得把该笔记为已成功（`REQ-030` 的秤端对应） | 无 |
| 网络恢复 | 按 `staged_at` 升序**自动补传**；每条带原暂存时的 `business_date` 与同一幂等键 | 按 `Idempotency-Key` **幂等去重**；同键不同体按 `MT-1012` 拒绝 |
| 补传成功 | **清除本地副本**（`NFR-013`） | 返回首次结果，不重复记账 |
| 补传失败 | 该条**保持暂存**、下一轮重试；不阻断后续 | 按具体错误码返回；**绝不把不成功的条目当成功** |

> **顺序不变量**：补传必须按 `staged_at` 升序。乱序补传不会造成重复记账（幂等兜住），
> 但会让**日聚合的中间态**出现"后发生的先入账"，对账观感变差 —— 故列为契约要求而非实现细节。

## 7. 版本策略

- **当前版本**：`v1`，但路径**带版本段**（`/api/scale/v1/...`）—— 与主契约不同，理由见下。
- **为什么这里带版本段而主契约不带**：主契约的消费方是**同一次发布内的浏览器页面**，
  可以「同提交内全量同步」；秤端固件是**烧录在 100 台设备里**的，升级不能假设瞬时完成，
  故必须能在路径上区分版本，让新旧固件在过渡期内**可被识别**（识别后按版本给出明确结论，而不是悄悄错算）。
- **兼容性变更**（直接发布）：新增可选字段、新增端点、放松校验。
- **破坏性变更**：须升版本段（`/v2`），并在 `ADR-0005` §5 的触发条件下评估是否需要**双版本并存期**。
- 中台对不认识的 `X-Scale-Proto` **必须显式拒绝**（`MT-2003`），**不得**按最新版猜测解析 —— 猜错就是静默错算。
