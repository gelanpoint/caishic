### R0.1 项目定位与评分口径

- **性质**：AI Coding 黑客松比赛作品，**要现场演示真实运行**（不是纸面方案）。
- **业务背景**：菜市场运营方管理多个市场、数百商户，计划从固定摊位租赁转向「按商户实际交易流水收佣金」，
  需要数字化交易系统更真实完整地记录商户经营交易，为佣金结算与经营分析提供数据基础。
  品类以蔬菜、水果、肉类、水产为主，**大量商品需称重计价**；运营方希望合理控制现场硬件投入与实施成本。
- **赛题要求 MVP 至少跑通主干**：商户 → 商品 → 称重 → 计价 → 交易 → 支付 → 佣金 → 经营数据查看。
- **允许 Mock**：电子秤与支付平台；可提出配套硬件设想。重点是业务流程、软件 Demo、硬件设想**三者逻辑一致**。
- **交付物**：① 可现场运行的系统 Demo ② 完整代码 ③ 需求理解与整体方案说明（含关键假设与设计取舍）
  ④ 核心测试及测试结果 ⑤ 项目启动说明。
- **评分构成**：方案完备性 40 分 + Demo 跑通主干且"数据前后一致" 40 分 + AI Coding 与验证过程 20 分。

### Q0.1 失败代价 = `1C`

- **回答原话（父代理）**：「**不作为"纯演示品"降级**」。理由三条：
  ① 赛题硬性要求「Demo 需要现场真实运行，不能仅通过 PPT、截图或录屏代替」—— 交付物是被外部（评委/主办方）当场验收的，评分标准构成事实上的验收条款；
  ② 系统模型化真实资金（交易金额、佣金引擎、结算单、对账），评分明确考察「数据是否前后一致」，这是资金系统的要求；
  ③ 兜底规则是「拿不准就高不就低」。
- **性质确认**：本作品**不适用**「只用汇报演示、不会被真实使用的交付物不适用本分级」这一豁免 —— 它是现场真实运行、被外部当场验收的交付物。
- **采纳为 spec 的**：§元信息（项目级别）、§非功能需求

| 3 | **选商品** → 放上商品 → 模拟电子秤出重量 → 系统按「单价 × 重量」计价 | 正常流 |
| 4 | **（可选）临时改价或抹零**，系统留痕（**原价与改后价都记录**） | 正常流 |
| 5 | 一单多品则重复第 3–4 步，累加到同一单 | 正常流 |
| 6 | 确认应收金额 → 屏幕**出收款码**，或摊主选择**现金** | 正常流 |
| 7 | 顾客扫码（模拟支付）→ 回调结果分**成功 / 失败 / 超时**三条路径 | 正常流 |
| 8 | 支付成功 → 展示/打印交易凭证（交易号 + 明细）→ 交易落库 | 正常流 |
| 9 | **异常 A（支付）**：失败或超时 → 摊主可重试或改记现金 → **同一单绝不产生两笔交易 / 两笔佣金** | 异常流 |
| 10 | **异常 B（退货）**：顾客退货 → 冲正原单 → 日聚合金额与佣金同步减少、**且只减一次** | 异常流 |
| 11 | **异常 C（断网）**：网络中断 → 继续正常交易（本地暂存）→ 联网后自动补传 → **订单数不翻倍** | 异常流 |
| 12 | 日终 → 按日聚合交易与佣金 → 生成结算单 → 商户端与市场方端看板出数 → **对账等式成立** | 收口 |

**父代理指出本代理原 9 步漏掉的三条路径**（原话摘要）：
1. **交易中的临时改价 / 抹零** —— 菜市场议价、凑整是常态；不给入口摊主会弃用，给了必须留痕；
2. **退货冲正** —— 原稿只在 Q1.5 提了退货，操作步骤里没有「顾客退货」这个动作，**异常流不能只活在验收标准里**；
3. **断网离线交易 + 恢复后补传** —— 方案最硬的差异化，也是「数据前后一致」的证明点。

- **采纳为 spec 的**：§用户故事 + §功能需求（正常流 1–8 / 异常流 9–11）+ §边界与例外

### Q1.3 输入是什么（8 类输入，采纳；限制值采纳）

| # | 输入 | 来源与格式 | 限制 |
| --- | --- | --- | --- |
| 1 | 摊主选品 | 点选，来自品类字典 + 本摊位价目表 | **无键盘输入** |
| 2 | 重量 | 模拟电子秤读数（数值） | **> 0 且 ≤ 50 公斤**；计价口径「元 / 公斤」 |
| 3 | 临时改价 / 抹零 | 摊主操作（数值） | **不设硬限制**，见下方决策 |
| 4 | 现金金额 | 面额点选或数字键盘，含找零 | 金额保留 2 位小数 |
| 5 | 支付回调 | 模拟：成功 / 失败 / 超时 + 支付单号 | — |
| 6 | 退货请求 | 关联原单号 + 退货金额 | 金额 ≤ 原单金额 |
| 7 | 离线交易 | 本地持久队列，带客户端生成的**幂等键** | 见 Q2.3 边界值 |
| 8 | 种子数据 | CSV / JSON 文件，启动时导入 | 一次导入，非系统对接 |

#### 关键决策：临时改价范围 = **完全放开、只留痕**（父代理要求连同理由一并落盘）

1. **前提变了，动机就不存在**：本方案**不向商户抽佣**，摊主改价**没有逃佣动机** ——
   改低价对他唯一的影响是少收钱。所以不需要用硬限制去防一个不存在的动机。
   **这是我们必须刻意与所有失败案例区分开的地方。**
2. **硬限制会违背设计原点**（「不增加摊主操作负担」），而且**必然被绕开**：
   他可以用别的商品档位顶替，或者干脆弃用系统。调研里「商户抗议并搬离市场」就是硬性手段的后果（`P-1` /《报告》结论 10）。
3. **真实业务需要灵活性**：收摊甩卖降 50% 是常态；设 ±20% 上限会直接伤害生意。
4. **所以用「透明度」而不是「管制」** —— 这是本方案一贯的原则（《报告》结论 16 的教训：管制式的展示最终只会被当成应付检查的贴纸）：

| # | 软约束 | 说明 |
| --- | --- | --- |
| ① | **留痕** | 记录原价、改后价、改价时间、操作摊位 |
| ② | **佣金基数按实收金额（改后价）** | 这是唯一可执行口径 |
| ③ | **改价计入「标价一致率」** | 作为摊位信用档案的一个指标，且**顾客可见** → **这是软约束**，让摊主自己在「成交」与「信用」之间权衡，而不是系统替他决定 |
| ④ | **单笔改价幅度超过 50% 时提示确认** | 防误操作，**不阻止** |
| ⑤ | **抹零与改价分开统计** | 抹零是找零习惯，不应拖累「标价一致率」 |

> **父代理要求**：把「改价不需要硬限制」的理由写成 spec 里的一条**设计取舍**，
> 因为它恰好证明了我们理解「为什么不抽佣」这个前提的连带好处。

### Q5.1 验收场景（5 条；两处内部矛盾已按父代理修正）

| # | 场景 | 可观察判据 | 对应 |
| --- | --- | --- | --- |
| 1 | **顺流程数据一致** | 现场完成一笔称重交易后，该笔在**商户端与市场方端两侧都可见，金额与明细完全一致** | Q1.5-1 |
| 2 | **退货冲正只减一次** | 对该单发起退货，两侧**日聚合金额与佣金同步减少、且只减一次**；**重复发起同一次退货不会二次冲减** | Q1.5-2 |
| 3 | **断网补传不翻倍** | 断网做 2 笔，恢复后自动补传，**订单总数不翻倍**，且**对账等式成立（订单总额 = 支付流水 = 分账明细）** | Q1.5-3 |
| 4 | **现金交易等价入账** | 一笔现金交易与一笔电子支付交易，在流水、佣金、对账中的处理**完全等价** | 异常 / 边界 |
| 5 | **使用率口径可验收** | 系统能导出 **① 日均智能秤交易占比**（走秤交易笔数 / 总交易笔数）与 **② 价目表维护率**（当日价目表完整且已更新的摊位 / 在营摊位），第三方可凭导出结果判过 / 不过 → ⚠️ **本行的 ① 不可判定，已于 `2026-09-30` 修订为三个系统自有指标，见下方「修正 3」** | D-09 |

#### 修正 1：对账等式对现金单不成立（第 3 条 vs 第 4 条的矛盾）

**选择方案 A**：把现金也记入**同一张支付流水表**，以 `支付方式 = 现金` 标识（含收款确认时间与操作人），
于是第 3 条的等式**依然成立**。

- **被否决的方案 B**：等式改为「订单总额 = 支付流水 + 现金收款记录 = 分账明细」。
- **核心理由（须显式写出）**：**现金也走同一条支付流水，只是支付方式不同。** 这样第 3、4 条才能同时成立。

#### 修正 2：「价签更新率」不可实现，改为「价目表维护率」

- **原指标的问题**：本方案建议**用物理价签替代电子屏**（《报告》结论 1 湖州的做法、结论 24 的成本对比）。
  **物理价签系统感知不到，无法统计「更新率」。**
- **连带违反**：D-08 要求「只展示有真实来源的数据」—— 把系统无从知晓的指标写成验收项，
  就成了**无法验证的假指标**，恰好违反我们自己的 D-08。
- **修正后**：见上表第 5 条的 ① ② 两个指标。**理由**：这两个指标都是**系统自有数据算得出来**的。
  > ⚠️ **该结论于 `2026-09-30` 被进一步修正**：第 5 条的 ① 其实**算不出来**（分母是市场总交易笔数，系统拿不到）——
  > 见下方「修正 3」。**最终形态是三个系统自有指标**（摊位使用率 / 现金交易占比 / 价目表维护率）。

#### 修正 3（`2026-09-30`）：验收指标「日均智能秤交易占比」不可由系统自有数据算出 → 改 `REQ-022` / `AC-005`

- **发现路径**：写 `data-model.md` 的「派生指标口径」时发现，第 5 条场景写的「走秤交易笔数 / **总交易笔数**」——
  **分母系统拿不到**：系统只知道走秤的笔数，不知道摊主私下收了多少笔。
- **性质**：这与 `AC-006` 是**同一个病** —— 把**不可判定**的东西写进验收标准。
  等价地说，它违反了**我们自己的 D-08**（只展示有真实来源的数据）：**我们把自己的原则应用到了自己的验收指标上，然后发现它不合格。**
- **处置（RL-2「规格错了先改规格」）**：当场修订 `spec.md` 的 `REQ-022` 与 `AC-005`，把指标改为**三个分子分母均为系统自有数据**的指标
  （**摊位使用率** / **现金交易占比** / **价目表维护率**），并在 `spec.md` 的「变更记录」留痕（编号未变）。
- **市场口径指标的去向**：真正的「日均智能秤交易占比」（走秤笔数 ÷ 市场总交易笔数）需要一个**外部基准**
  （人工盘点 / 抽样统计 / 外部系统），已转入未决项 `Q-15`，**本期不做**。
- **教训（写进经验留痕）**：**验收指标必须先问"分子分母从哪来"** —— 答不出分母的指标，无论听起来多合理，都是假指标。

- **采纳为 spec 的**：§功能需求（离线状态可视标识与显式切换、现金进同一支付流水表）、§非功能需求（容量与触发条件）、§验收标准（5 条 AC，前三条与 Q1.5 一一对应）、§开放问题清单（财务证据链保留期 Q-10）
