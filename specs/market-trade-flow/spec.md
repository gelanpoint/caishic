## 1. 概述

### 1.0 本 spec 阅读导航（答辩速览）

- **只想懂我们的主张** → §1.1 设计原点 + §1.2 范围声明（本期实现范围 / 方案论证范围）
- **想看怎么算成功** → §1.4 成功的定义（三个可观察场景）
- **想看系统做什么 / 不做什么** → §3 功能需求 + §6 Out-of-Scope（11 条具体排除）
- **想看能被第三方验收的部分** → §7 验收标准（`AC-001` / `AC-002` / `AC-003` 是三条核心）
- **想看我们清楚哪些还没定** → §8 开放问题清单（含已接受的偏离与待批项）

### 1.1 核心主张（设计原点，全篇裁判）

> **在不增加摊主操作负担的前提下，产生可核验的交易数据** —— 数据可信度优先于功能数量。

本系统服务菜市场「按商户实际交易流水收佣金」的转型：**摊主在菜市场摊位现场，用本系统完成一笔称重商品交易的
选品 → 称重 → 计价 → 收款 → 留痕；市场运营方在后台用它完成佣金结算与经营数据分析。**

交易必须走「选商品 → 称重 → 计价 → 出收款码」——**秤是唯一物理锚点**（依据 `discovery.md` D-03）。

**设计论证（不是可判定的验收项，故不写在 §7）**：一次交易的**操作步数不多于现有电子秤** ——
这是本方案判断"摊主是否愿意用"的核心依据（依据 `discovery.md` D-07 与《现实情况调查报告》结论 6：
绵阳摊主因"操作麻烦、字小、按键慢"而弃用）。可判定的形式见 §7 `AC-006`。

### 1.2 范围声明（两个范围必须分开看）

**本期实现范围**：单市场（数据面）、不依赖外网、数据存本地、前端适配手机宽度（模拟顾客扫码）；
并发为演示级（峰值并发 <20）。

**两个交付形态（`2026-10-06` 新增，依据 `docs/adr/0005-秤端与中台拆分.md`）**：

| 形态 | 组成 | 用途 |
| --- | --- | --- |
| **形态 1 · 单机 all-in-one** | 一个进程承载秤端页面、运营端、顾客页与全部账务 | 现场演示主路径；承载 `AGENTS.md` §3 硬要求 3（同机双浏览器窗口） |
| **形态 2 · 秤端 / 中台分离** | 秤端（摊位现场嵌入式终端）× N ↔ 中台（中心服务）× 1，经网络连接 | 与「100 个商家 = 100 台秤 + 1 中台」的目标形态一致 |

**两种形态的总体能力必须一致**：形态 2 不是功能子集，而是同一套能力的**另一种部署方式**
（职责划分见 `ADR-0005` §3）。**形态 1 继续保留**，不因形态 2 落地而废弃。

**方案论证范围**：多市场的**运营流程**（跨市场权限、跨市场结算与报表）、数百商户（单市场约 300 摊位）、
早市峰值 —— 这是**目标形态与演进路径**，**用文字论证，不在本期实现**。
中台**保留市场维度**（`REQ-035`），但本期只装载一个市场。

> **这是一条明确的设计取舍**：本期把"数百商户 + 多市场运营"留给演进路径而不是假装已经支持；
> 但**部署形态**（秤端与中台分机）属本期实现（`REQ-034`）。
> 两者不可混为一谈（依据 `discovery.md` R1 Q0.2、R3 Q2.2）。

### 1.3 角色

| # | 角色 | 说明 |
| --- | --- | --- |
| 1 | 摊主（商户） | 秤端操作；只接触本摊位数据 |
| 2 | 市场运营方管理员 | 后台：品类字典与价目表、佣金口径配置、看板、结算单 |
| 3 | 市场运营方只读查看者 | 只看经营数据，不改配置 |
| 4 | 顾客 | 通过扫码页完成支付与信息查看，**不登录** |
| 5 | 系统 / 运维 | 本期由交付者兼任，不做独立账号体系 |

> 真实业务中，「佣金口径配置」「对账」「结算单审核」可能分属运营与财务两个岗位；
> 本期 MVP 合并为「运营方管理员」单人角色，**岗位分离与权限矩阵留待后续演进**。

### 1.4 成功的定义（现场连续演示三个场景，全部可观察）

1. 完成一笔称重交易后，该笔在**商户端与市场方端两侧都可见，金额与明细完全一致**；
2. 对该单发起退货，两侧的**日聚合金额与佣金同步减少，且只减一次**；
3. 断网状态下做 2 笔，恢复网络后自动补传，**订单总数不翻倍**，且**对账等式成立**。

## 3. 功能需求

### 3.1 正常流

| 编号 | 需求（EARS 句型） |
| --- | --- |
| `REQ-001` | 系统应保存商户与摊位档案（含摊主姓名、联系方式、在营状态），并支持按摊位查询。 |
| `REQ-002` | 系统应维护品类字典与「摊位别名 → 标准品类」的映射；当摊主选取某个别名时，系统应按**标准品类**记账。 |
| `REQ-003` | 当摊主在营业前设置价目表时，系统应支持「复制上一营业日价格」并允许逐条调整。 |
| `REQ-004` | 系统应在秤端以**图标或快捷键**提供商品选择；若完成一次选品，系统应**不需要任何文本输入**。 |
| `REQ-005` | 当商品放上模拟电子秤时，系统应读取重量并按「单价 × 重量」计算金额，重量以公斤为单位、金额保留两位小数。 |
| `REQ-006` | 当同一笔交易加入多个商品时，系统应在**同一笔交易**内累加金额。 |
| `REQ-007` | 当摊主临时改价或抹零时，系统应记录**原价、改后价、改价时间、操作摊位**；当单笔改价幅度超过 50% 时，系统应提示确认且**不阻止**该操作。 |
| `REQ-008` | 系统应将改价计入该摊位的「标价一致率」并纳入摊位信用档案，且该指标对顾客可见；**抹零不应计入**该指标。 |
| `REQ-009` | 当摊主确认应收金额时，系统应提供**收款码**与**现金**两种收款方式。 |
| `REQ-010` | 当摊主选择现金收款时，系统应在**同一张支付流水表**中写入一条 `支付方式 = 现金` 的记录，含收款确认时间与操作人。 |
| `REQ-011` | 当顾客扫码支付时，系统应接收模拟支付回调，并记录成功、失败或超时三种结果之一。 |
| `REQ-012` | 当支付成功时，系统应先将交易落库，再于屏幕展示交易凭证（含交易号与明细）；系统**不应提供打印**。 |
| `REQ-013` | 当顾客退货时，系统应冲正原交易，并使商户端与市场方端的日聚合金额与佣金同步减少；当同一笔退货被重复提交时，系统应**只冲减一次**。 |
| `REQ-014` | 当网络中断时，系统应继续接受新交易并在本地持久暂存；离线 / 在线状态应在秤端有**明确可视标识**，且状态切换可在界面上**显式触发并可复现**。 |
| `REQ-015` | 当网络恢复时，系统应自动补传暂存交易，并按客户端生成的**幂等键**去重，使订单总数不翻倍；当补传成功后，系统应**清除本地副本**。 |
| `REQ-016` | 当本地暂存达到告警阈值时，系统应提示摊主联系运维，并**继续接受新交易**。 |
| `REQ-017` | 系统应支持配置佣金口径（**收费对象、费率、品种档位**），并按**实收金额**计算佣金。 |
| `REQ-018` | 系统应在日终按日聚合交易与佣金，并支持在退货冲正后**按需重算**。 |
| `REQ-019` | 系统应依据日聚合结果生成结算单，供市场运营方查看。 |
| `REQ-020` | 系统应提供对账，使「**订单总额 = 支付流水 = 分账明细**」这一等式可被核验。 |
| `REQ-021` | 系统应提供**商户端**与**市场方端**两个经营看板，展示交易、佣金与经营数据。 |
| `REQ-022` | 系统应导出「**摊位使用率**」（当日有走秤交易的摊位 ÷ 在营摊位）、「**现金交易占比**」（现金笔数 ÷ 全部走秤笔数）与「**价目表维护率**」（当日价目表完整且已更新的摊位 ÷ 在营摊位）三个使用率指标；**上述指标的分子与分母均为系统自有数据**。**口径注（`2026-10-08` 补）**：`status = cancelled` 的交易（`REQ-055` 取消撤销）**在分子与分母中一律排除** —— 它与「未发生」等价，若计入会使「走秤交易」这一事实自相矛盾。 |
| `REQ-023` | 系统应在顾客扫码页**只展示有采集来源的字段**；无采集流程的字段不予展示。 |
| `REQ-024` | 系统在任何接口的请求体、响应体与持久化记录中**不应出现身份证号或银行卡号字段**，收款标识应脱敏存储。 |
| `REQ-025` | 当系统启动时，系统应从本地文件导入种子数据（商户与摊位档案、品类字典与别名映射、商品与价目表），且**不依赖外网**。 |
| `REQ-033` | 当处于离线回归测试或多智能体仿真场景时，系统应允许通过**环境变量**把**业务日与全部时间戳的来源**指向仓库内的本地时钟文件；当该环境变量未设置时，系统应取本机墙钟，即业务日与时间戳的取值与**未引入本能力时逐字段一致**（本能力只改"时钟从哪来"，不改任何记账口径）。 |

### 3.1b 秤端与中台分离（`2026-10-06` 新增，依据 `docs/adr/0005-秤端与中台拆分.md`）

> 本节的需求全部服务于 `ADR-0005` 的形态 2。**形态 1（单机）不受影响**，其行为与本节引入前逐字段一致。

| 编号 | 需求（EARS 句型） |
| --- | --- |
| `REQ-034` | 系统应支持**秤端与中台分离部署**：秤端与中台是两个可独立启动的进程（或设备），二者之间经**网络调用**通信；当对端不可用时，系统应仍能各自启动并进入可用状态（中台不可达不得导致秤端无法开机进入营业界面）。 |
| `REQ-035` | 中台应保留**市场维度**：商户、摊位、商品、价目表、佣金口径、日聚合与结算单均归属于某一市场；当需要装载第二个市场时，系统应**不因新增市场而改动表结构**。本期只装载一个市场。 |
| `REQ-036` | 秤端应通过**设备注册**绑定到唯一的「市场 + 摊位」组合，并以**设备令牌**标识自身身份；中台应拒绝未注册的设备与令牌不符的请求。 |
| `REQ-037` | 中台应向秤端**下发该摊位所属的商品字典、品类与摊位别名映射、价目表**；秤端应缓存之，使**断网时仍可完成选品与计价**。 |
| `REQ-038` | 秤端应**在本地完成计价**并随交易上报金额；中台收到后应用**权威计价实现重算**，当重算金额与上报金额不一致时，中台应**告警并留痕**，且**以中台重算结果入账**。 |
| `REQ-039` | 秤端的上报应携带**客户端幂等键**；当同一键重复上报时，中台应返回**首次结果**且不重复记账；当同一键的请求体不同时，中台应拒绝并给出明确错误码。 |
| `REQ-040` | 当秤端与中台之间网络中断时，秤端应继续接受新交易并**在本地持久暂存**；离线 / 在线状态应在秤端有**明确可视标识**。 |
| `REQ-041` | 当网络恢复时，秤端应自动补传暂存交易；**补传成功后应清除秤端本地副本**。当暂存达告警阈值时，秤端应提示摊主联系运维并**继续接受新交易**；当暂存写入失败时，秤端应明确报错且**不得**把该笔记为已成功。 |
| `REQ-042` | 当摊主在秤端发起退货时，退货冲正应**由中台执行**；秤端**不得**自行计算或扣减佣金。 |
| `REQ-043` | 秤端应展示**指向中台顾客扫码页**的收款码；顾客扫码后访问的是中台，秤端不承载顾客页面。 |
| `REQ-044` | 系统应提供一个**俯视角像素风网页游戏**，作为本系统的**可视化演示界面**：在同一块地图上同时呈现商家（摊位与智能秤）、顾客（走动的人）、管理员（人与电脑）。该界面**只读取/调用既有服务**，**不得**新增账口、**不得**绕过 `app/domain/**` 直接改库。 |
| `REQ-045` | 游戏内应能**切换三种视角**：商家 / 顾客 / 管理员。切换只改变**可执行的操作与可见信息**，不改变服务端鉴权口径（授权仍只来自设备令牌或既有运营端会话）。 |
| `REQ-046` | 鼠标悬停在某个商家（摊位）上时，应显示该摊位**当前在售的商品清单与单价**；该清单**取自服务端价目表**，不得由前端硬编码。 |
| `REQ-047` | 点击**智能秤**应能以商家身份执行操作：**调价**（改单价）与**上/下架商品**。操作须经真实服务端点生效，并可在运营端被观察到。 |
| `REQ-048` | 游戏的全部美术资源必须是**仓库内本地文件**（`AC-037`），且**由仓库内脚本可复算生成**；不得引用任何 CDN、外网地址或二进制大文件。 |
| `REQ-049` | 商家应能**上架 / 下架自己摊位的商品**（改 `product.status`）。该能力是**服务端真实能力**（不是演示层伪造）：下架后该商品**不得**出现在秤端商品列表、价目表维护率统计与顾客可见信息中；**不得**跨摊位操作（越权返回 `MT-1004`）。<br>**背景（`2026-10-06` 由演示游戏需求反查发现）**：`product.status` 字段与索引 `ix_product_stall_status` 自 `0001_init.sql` 起就存在，`data-model.md` §2.7 也用它算「价目表维护率」，但**全仓没有任何端点或领域函数能修改它** —— 即「上下架」是**已建模却未实现**的能力缺口。本需求补齐它。 |
| `REQ-050` | 演示游戏里的顾客 NPC 须**有目的、可观察**地行动：在「前往某摊位 → 停留浏览 → 购买（`REQ-052`）→ 前往下一处或离场」之间推进，而不是无目的地绕圈。移动须受**地图可通行区域**约束 —— **不得穿过**摊位、货箱、电脑、老板 / 管理员等实体；顾客之间须**主动避让**，**不得互相重叠**。<br>**边界**：该行为是**本地演示逻辑**，不代表真实并发、也不代表真实顾客行为（`spec.md` §6 第 15 条；`AC-040`）。 |
| `REQ-051` | 演示游戏里摊位的**外观**须与其**主营品类**一致，且主营品类**由服务端品类字典推导**（`category.code` 前缀：`V` 蔬菜 / `F` 水果 / `M` 肉 / `A` 水产；**无单一主营 ⇒ 杂货**），前端**不得**硬编码某个摊位的品类。改服务端商品品类后外观须随之改变（`AC-041`）。 |
| `REQ-052` | 演示游戏里顾客的**购买行为**须经**既有**成交端点真实落账（契约 §3.6 创建计价 + §3.7 支付），使**管理端看板**（§3.25 / §3.30）能观察到笔数与金额。**不得**新增端点、**不得**绕过 `app/domain/**` 直接改库（`REQ-044`）；购买失败须**明确记录**，**不得静默丢弃**（`RL-9`）。<br>**背景（`2026-10-07` 负责人现场观察）**：演示游戏此前**完全没有购买行为** ⇒ 管理端看板恒为 `txn_count=0` / `gross_amount_cents=0`，演示时"后台看不到数据"。 |

### 4.1 放宽批准记录（`Q-11`，2026-09-30 获批）

**批准结论**：`NFR-001`～`NFR-011` 的放宽**已获父代理批准**。

**批准范围仅限「运维可用性与灾备类」** —— 在线率、RTO/RPO、备份与异地、恢复演练、停机公告、
身份鉴别与传输加密、日志与告警平台、依赖周期检查。理由：本项目的运维能力（单机演示、无专职运维、无外部用户）
与 `P2` 基线的设计前提（7×24 生产系统）不匹配；按环境缩水"运维能力"是合理取舍。

**以下三类明确不予放宽**（写进批准记录，作为本项目不可松动的红线）：

| 不放宽的三类 | 对应条目 | 为什么不能松 |
| --- | --- | --- |
| **安全红线** | `NFR-012`（身份证 / 银行卡不入库、收款标识脱敏）、`NFR-013`（离线暂存同步后清除本地副本） | 这是 `P2` 定级的根据（涉敏感数据）。**松了等于定级作废。** |
| **数据完整性与可核验** | `AC-001` / `AC-002` / `AC-003` 三条核心、对账等式（`REQ-020`）、`NFR-014`（绝不静默丢弃）、`NFR-009` 中「**只增不改**」部分 | 这几条就是本方案的**全部价值主张**。**「数据前后一致」一旦可放宽，整个 Demo 就没有可证明的东西了。** |
| **可追溯证据链** | 改价留痕（`REQ-007`）、退货冲正（`REQ-013`）、幂等命中记录（`REQ-015`） | 佣金基数的证据链，缺一条就无法自证。 |

> 一句话理由：**「运维能力」可以按环境缩水，「数据可信」不能** —— 否则我们和在武汉被曝光的那批黑屏设备没有区别
> （依据 `docs/调研报告-现实情况.md` 结论 4）。

### 4.2 `NFR-008` 放宽理由的重新登记（`2026-10-06`，**已批准**）

**为什么必须重新登记**：`NFR-008` 原先的放宽依据是一句**事实判断** ——「全部本机访问，无跨网络调用」。
`ADR-0005` 的形态 2 落地后，**这个事实不再成立**，跨网络调用真实存在。
沿用旧批准记录会让一条已失效的理由继续充当豁免依据 —— 那正是本项目一直在防的「把假设当事实」。

| 项 | 内容 |
| --- | --- |
| 重新登记后的理由 | ① 受控局域网内调用，**禁止把中台暴露到公网**；② 设备令牌鉴权 + 设备↔摊位绑定（`REQ-036`），未注册设备与令牌不符一律拒绝；③ 载荷不含身份证号与银行卡号，`NFR-012` 仍为**收紧项**、未放宽 |
| **未达标的部分（如实登记）** | 本期**未实现 TLS**。基线 P2 要求「全链路 HTTPS / TLS 1.2+ 含内网」，本形态为明文 HTTP ⇒ **这是放宽，不是达标** |
| 已知缺口的处置 | 登记为未决项 `Q-20`（负责人：父代理/负责人；影响：受控局域网内的窃听与中间人；不挡本期实现） |
| **批准状态** | **`已批准`（`2026-10-06`，负责人会话内明确批准）** —— 批准范围：接受「受控局域网 + 设备令牌 + 禁止暴露公网」作为本期的传输层约束，**同时承认这是放宽而非达标**。按 `RL-2`，AI 只起草、批准由负责人落盘 |
| 不以「反正都在内网」为由结案 | 该说法与「运维能力按环境缩水」不是同一类：前者是**安全边界**，后者是**可用性承诺**。故本条单列，不并入 §4.1 的运维类放宽批次 |

## 6. Out-of-Scope

**以下 11 条均为具体功能排除（依据 `discovery.md` R0.3 与 R2 Q4.1）：**

1. 本系统**不**做外送服务。
2. 本系统**不**做顾客端历史价格折线图。
3. 本系统**不**做真实**支付平台**对接（支付仍为 Mock）。
   **硬件侧口径修订（`2026-10-06`，依据 `ADR-0005`/`ADR-0006`）**：秤端**提供**面向 ESP32-S3 的嵌入式实现与硬件选型（含成本出处），
   但**不做**真实硬件采购、产线试制与硬件在环验收（登记为未决项 `Q-21`）；形态 1 的现场演示仍可用模拟秤读数。
4. 本系统**不**做**多市场的运营流程**（跨市场权限、跨市场结算与跨市场报表）。
   中台**保留市场维度**（`REQ-035`），本期只装载一个市场 —— **保留维度 ≠ 交付多市场运营**。
5. 本系统**不**做完整权限体系（不做 SSO、不做权限矩阵、不做岗位分离）。
6. 本系统**不**做 AI 图像识别自动识别商品（交易中一律人工选品）。
7. 本系统**不**做电子价签、摊位屏、大屏等**非秤类硬件**的对接。
8. 本系统**不**做发票开具与税务申报。
9. 本系统**不**做会员、积分、优惠券等营销体系。
10. 本系统**不**做商户贷款、授信、集采等金融与供应链业务（"银行付费"属方案论证内容，不在交付范围）。
11. 本系统**不**做顾客端独立 App / 小程序（顾客只在扫码页完成支付与信息查看）。

**演示游戏的排除项（`2026-10-06` 追加，依据 `REQ-044`~`REQ-048`）：**

12. 演示游戏**不**做游戏性目标（无关卡、无积分、无胜负、无存档）—— 它是**经营过程的可视化演示**，不是一款独立的游戏产品。
13. 演示游戏**不**做美术资源的商业级制作（不外包、不采购素材库）—— 像素资源由**仓库内脚本生成**，风格统一优先于精细度（`REQ-048`）。
14. 演示游戏**不**新增任何服务端能力：不新增端点、不新增表、不新增账口。它**只**调用既有端点（`NFR-016`）。
15. 演示游戏**不**做真实顾客的多人联机（顾客 NPC 的行为是**本地演示逻辑**，不代表真实并发）。
