## 1. 概述

### 1.0 本 spec 阅读导航（答辩速览）

- **只想懂我们的主张** → §1.1 设计原点 + §1.2 范围声明（本期实现范围 / 方案论证范围）
- **想看怎么算成功** → §1.4 成功的定义（三个可观察场景）
- **想看系统做什么 / 不做什么** → §3 功能需求 + §6 Out-of-Scope（11 条具体排除）
- **想看能被第三方验收的部分** → §7 验收标准（`AC-001` / `AC-002` / `AC-003` 是三条核心）
- **想看我们清楚哪些还没定** → §8 开放问题清单（含已接受的偏离与待批项）

### 1.1 核心主张（设计原点，全篇裁判）

> **在不增加摊主操作负担的前提下，产生可核验的交易数据** —— 数据可信度优先于功能数量。

本系统服务菜市场「按商户实际交易流水收佣金」的转型：**摊主在菜市场摊位现场，用本系统完成一笔称重商品交易的
选品 → 称重 → 计价 → 收款 → 留痕；市场运营方在后台用它完成佣金结算与经营数据分析。**

交易必须走「选商品 → 称重 → 计价 → 出收款码」——**秤是唯一物理锚点**（依据 `discovery.md` D-03）。

**设计论证（不是可判定的验收项，故不写在 §7）**：一次交易的**操作步数不多于现有电子秤** ——
这是本方案判断"摊主是否愿意用"的核心依据（依据 `discovery.md` D-07 与《现实情况调查报告》结论 6：
绵阳摊主因"操作麻烦、字小、按键慢"而弃用）。可判定的形式见 §7 `AC-006`。

### 1.2 范围声明（两个范围必须分开看）

**本期实现范围**：单市场、单机、一条命令启动、不依赖外网、数据存本地、前端适配手机宽度（模拟顾客扫码）；
并发为目标为演示级（峰值并发 <20）。

**方案论证范围**：多市场、数百商户（单市场约 300 摊位）、早市峰值 —— 这是**目标形态与演进路径**，
**用文字论证，不在本期实现**。

> **这是一条明确的设计取舍**：本期以单机单体承载端到端主干，把"数百商户"留给演进路径而不是假装已经支持。
> 两者不可混为一谈（依据 `discovery.md` R1 Q0.2、R3 Q2.2）。

### 1.3 角色

| # | 角色 | 说明 |
| --- | --- | --- |
| 1 | 摊主（商户） | 秤端操作；只接触本摊位数据 |
| 2 | 市场运营方管理员 | 后台：品类字典与价目表、佣金口径配置、看板、结算单 |
| 3 | 市场运营方只读查看者 | 只看经营数据，不改配置 |
| 4 | 顾客 | 通过扫码页完成支付与信息查看，**不登录** |
| 5 | 系统 / 运维 | 本期由交付者兼任，不做独立账号体系 |

> 真实业务中，「佣金口径配置」「对账」「结算单审核」可能分属运营与财务两个岗位；
> 本期 MVP 合并为「运营方管理员」单人角色，**岗位分离与权限矩阵留待后续演进**。

### 1.4 成功的定义（现场连续演示三个场景，全部可观察）

1. 完成一笔称重交易后，该笔在**商户端与市场方端两侧都可见，金额与明细完全一致**；
2. 对该单发起退货，两侧的**日聚合金额与佣金同步减少，且只减一次**；
3. 断网状态下做 2 笔，恢复网络后自动补传，**订单总数不翻倍**，且**对账等式成立**。

## 3. 功能需求

### 3.1 正常流

| 编号 | 需求（EARS 句型） |
| --- | --- |
| `REQ-001` | 系统应保存商户与摊位档案（含摊主姓名、联系方式、在营状态），并支持按摊位查询。 |
| `REQ-002` | 系统应维护品类字典与「摊位别名 → 标准品类」的映射；当摊主选取某个别名时，系统应按**标准品类**记账。 |
| `REQ-003` | 当摊主在营业前设置价目表时，系统应支持「复制上一营业日价格」并允许逐条调整。 |
| `REQ-004` | 系统应在秤端以**图标或快捷键**提供商品选择；若完成一次选品，系统应**不需要任何文本输入**。 |
| `REQ-005` | 当商品放上模拟电子秤时，系统应读取重量并按「单价 × 重量」计算金额，重量以公斤为单位、金额保留两位小数。 |
| `REQ-006` | 当同一笔交易加入多个商品时，系统应在**同一笔交易**内累加金额。 |
| `REQ-007` | 当摊主临时改价或抹零时，系统应记录**原价、改后价、改价时间、操作摊位**；当单笔改价幅度超过 50% 时，系统应提示确认且**不阻止**该操作。 |
| `REQ-008` | 系统应将改价计入该摊位的「标价一致率」并纳入摊位信用档案，且该指标对顾客可见；**抹零不应计入**该指标。 |
| `REQ-009` | 当摊主确认应收金额时，系统应提供**收款码**与**现金**两种收款方式。 |
| `REQ-010` | 当摊主选择现金收款时，系统应在**同一张支付流水表**中写入一条 `支付方式 = 现金` 的记录，含收款确认时间与操作人。 |
| `REQ-011` | 当顾客扫码支付时，系统应接收模拟支付回调，并记录成功、失败或超时三种结果之一。 |
| `REQ-012` | 当支付成功时，系统应先将交易落库，再于屏幕展示交易凭证（含交易号与明细）；系统**不应提供打印**。 |
| `REQ-013` | 当顾客退货时，系统应冲正原交易，并使商户端与市场方端的日聚合金额与佣金同步减少；当同一笔退货被重复提交时，系统应**只冲减一次**。 |
| `REQ-014` | 当网络中断时，系统应继续接受新交易并在本地持久暂存；离线 / 在线状态应在秤端有**明确可视标识**，且状态切换可在界面上**显式触发并可复现**。 |
| `REQ-015` | 当网络恢复时，系统应自动补传暂存交易，并按客户端生成的**幂等键**去重，使订单总数不翻倍；当补传成功后，系统应**清除本地副本**。 |
| `REQ-016` | 当本地暂存达到告警阈值时，系统应提示摊主联系运维，并**继续接受新交易**。 |
| `REQ-017` | 系统应支持配置佣金口径（**收费对象、费率、品种档位**），并按**实收金额**计算佣金。 |
| `REQ-018` | 系统应在日终按日聚合交易与佣金，并支持在退货冲正后**按需重算**。 |
| `REQ-019` | 系统应依据日聚合结果生成结算单，供市场运营方查看。 |
| `REQ-020` | 系统应提供对账，使「**订单总额 = 支付流水 = 分账明细**」这一等式可被核验。 |
| `REQ-021` | 系统应提供**商户端**与**市场方端**两个经营看板，展示交易、佣金与经营数据。 |
| `REQ-022` | 系统应导出「**日均智能秤交易占比**」与「**价目表维护率**」两个使用率指标。 |
| `REQ-023` | 系统应在顾客扫码页**只展示有采集来源的字段**；无采集流程的字段不予展示。 |
| `REQ-024` | 系统在任何接口的请求体、响应体与持久化记录中**不应出现身份证号或银行卡号字段**，收款标识应脱敏存储。 |
| `REQ-025` | 当系统启动时，系统应从本地文件导入种子数据（商户与摊位档案、品类字典与别名映射、商品与价目表），且**不依赖外网**。 |

### 3.2 异常流

| 编号 | 需求 |
| --- | --- |
| `REQ-026` | 若支付回调为失败或超时，当摊主重试或改记现金时，系统应保证**同一笔交易不产生两笔交易记录与两笔佣金**。 |
| `REQ-027` | 若重量小于等于 0 或大于 50 公斤，当摊主尝试计价时，系统应拒绝计价并给出提示。 |
| `REQ-028` | 若退货金额大于原单金额，当摊主提交退货时，系统应拒绝该退货。 |
| `REQ-029` | 当同一次支付的回调被重复送达时，系统应按**支付单号**幂等处理，不重复记账。 |
| `REQ-030` | 若本地暂存写入失败（如磁盘空间不足），系统应向摊主给出明确错误提示，且**不得**把该笔交易标记为已成功记账。 |
| `REQ-031` | 当多个摊位并发写入时，系统应保证每笔交易的写入互不覆盖，且交易号唯一。 |
| `REQ-032` | 当摊主使用秤端时，系统应只允许其访问**本摊位**的数据。 |

> 异常流覆盖核对：异常路径（`REQ-026`/`REQ-028`/`REQ-030`）· 边界值（`REQ-027`/`REQ-028`）·
> 并发（`REQ-031`）· 权限（`REQ-032`）· 数据量（`REQ-016`、§4 `NFR-001`）· 失败处理（`REQ-026`/`REQ-029`/`REQ-030`）。

## 4. 非功能需求

**只列对基线的偏离项。** 取值来源：`docs/standards/nfr-baseline.md`（该文件是 NFR 默认值的唯一权威）。**本节不复述基线数值清单。**

> **基线适用性复核（已做，不留白继承）**：本项目级别列为 `P2`。由于本期实现范围是**单机演示环境**、
> **无专职运维、无外部用户**，P2 列的**运维类**条目（在线率 / RTO / RPO / 备份保留 / 恢复演练频率 /
> 变更公告期 / 集中日志与告警）与本项目实际能力**明显不成比例**，逐条按下表记为**放宽偏离**并申请批准；
> **未列入下表的条目视为采用 `P2` 列基线值**。

| 编号 | 维度 | 目标（本项目值） | 相对基线的偏离与理由 |
| --- | --- | --- | --- |
| `NFR-001` | 吞吐与并发 | 支撑本期实现范围的峰值并发 <20 | **放宽**：基线 P2 要求"支撑峰值在线 500 并发且留 50% 余量" → <20。理由：本期为单市场单机演示，300 摊口径仅作文档论证（§1.2） |
| `NFR-002` | 在线率 | 尽力而为：演示与验收期间可用，允许工作日重启 | **放宽**：基线 P2 为 7×24 全年 99.9% → 不承诺。理由：单机演示环境、无专职运维、无外部用户 |
| `NFR-003` | RTO / RPO | 不承诺；以「重置脚本 + 种子数据重建」恢复 | **放宽**：基线 P2 为 RTO ≤ 30 分钟、RPO ≤ 1 小时 → 不承诺。理由同上 |
| `NFR-004` | 备份 | 不做自动备份；提供数据导出与重置脚本 | **放宽**：基线 P2 为每日全量 + 每小时增量、保留 90 天、跨机房异地 → 本期不做 |
| `NFR-005` | 恢复演练 | 不做定期演练；以「一条命令从零重建」验证可恢复性 | **放宽**：基线 P2 为每季度 1 次且报告归档 → 本期不做 |
| `NFR-006` | 计划停机公告 | 不设公告期 | **放宽**：基线 P2 为提前 3 个工作日公告 + 客户确认 → 本期无外部用户，不适用 |
| `NFR-007` | 身份鉴别 | 秤端以「已绑定摊位」的会话运行；运营端单管理员 | **放宽**：基线 P2 为强制 SSO + 双因素 → 本期不做（对应 §6 Out-of-Scope 第 5 条） |
| `NFR-008` | 传输加密 | 不适用：全部本机访问，无跨网络调用 | **放宽**：基线 P2 为全链路 HTTPS / TLS 1.2+ 含内网 → 本期无网络调用 |
| `NFR-009` | 审计日志 | 保留改价留痕、退货冲正、离线补传与幂等命中记录，**只增不改**；保留期见 §8 `Q-10` | **放宽**：基线 P2 为全量操作审计 + 防篡改 + 保留 ≥3 年 → 本期仅覆盖资金链路关键操作，防篡改不做、年限待定（`Q-10`） |
| `NFR-010` | 可观测性 | 结构化日志落盘 + 本地健康检查接口 | **放宽**：基线 P2 为集中日志平台、指标看板、5 分钟内触达值班人的告警 → 本期无运维值班 |
| `NFR-011` | 依赖管理 | 锁定版本 | **放宽**：基线 P2 为锁定版本 + 每两周检查更新 + 依赖准入评审 → 本期不做周期性检查 |
| `NFR-012` | 数据脱敏 | **收紧**：任何接口请求体 / 响应体与持久化记录**不得出现身份证号与银行卡号**；收款标识脱敏 | **收紧**（无需审批）：比基线 P2 的「展示层按角色脱敏」更严 —— 从入口杜绝而非仅展示层遮蔽 |
| `NFR-013` | 离线暂存数据处置 | **新增**：离线暂存交易属敏感数据处理范围，**补传成功后必须清除本地副本**；加密存储列为演进项（§8 `Q-7`） | **新增要求**，基线未覆盖 |
| `NFR-014` | 本地暂存不丢数据 | **新增**：暂存达告警阈值时仍继续接受交易，**绝不静默丢弃任何一笔** | **新增要求**，基线未覆盖（对应 `discovery.md` D-12） |

> **采用基线（未偏离，仅此说明，不复述数值）**：接口响应时间、涉钱路径的用例级对账测试、变更追溯关联需求编号 —— 直接采用 `P2` 列。
> **放宽类偏离（`NFR-001`～`NFR-011`）需要批准**：批准前在 `docs/PROJECT-STATE.md` 保持为未决项 `Q-11`，**不阻塞 G2、但阻塞实现**。

### 4.1 放宽批准记录（`Q-11`，2026-09-30 获批）

**批准结论**：`NFR-001`～`NFR-011` 的放宽**已获父代理批准**。

**批准范围仅限「运维可用性与灾备类」** —— 在线率、RTO/RPO、备份与异地、恢复演练、停机公告、
身份鉴别与传输加密、日志与告警平台、依赖周期检查。理由：本项目的运维能力（单机演示、无专职运维、无外部用户）
与 `P2` 基线的设计前提（7×24 生产系统）不匹配；按环境缩水"运维能力"是合理取舍。

**以下三类明确不予放宽**（写进批准记录，作为本项目不可松动的红线）：

| 不放宽的三类 | 对应条目 | 为什么不能松 |
| --- | --- | --- |
| **安全红线** | `NFR-012`（身份证 / 银行卡不入库、收款标识脱敏）、`NFR-013`（离线暂存同步后清除本地副本） | 这是 `P2` 定级的根据（涉敏感数据）。**松了等于定级作废。** |
| **数据完整性与可核验** | `AC-001` / `AC-002` / `AC-003` 三条核心、对账等式（`REQ-020`）、`NFR-014`（绝不静默丢弃）、`NFR-009` 中「**只增不改**」部分 | 这几条就是本方案的**全部价值主张**。**「数据前后一致」一旦可放宽，整个 Demo 就没有可证明的东西了。** |
| **可追溯证据链** | 改价留痕（`REQ-007`）、退货冲正（`REQ-013`）、幂等命中记录（`REQ-015`） | 佣金基数的证据链，缺一条就无法自证。 |

> 一句话理由：**「运维能力」可以按环境缩水，「数据可信」不能** —— 否则我们和在武汉被曝光的那批黑屏设备没有区别
> （依据 `docs/调研报告-现实情况.md` 结论 4）。

## 5. 边界与例外

| 场景 | 系统的行为 |
| --- | --- |
| 重量 ≤ 0 或 > 50 公斤 | 拒绝计价并提示（`REQ-027`） |
| 金额精度 | 一律保留两位小数；抹零与改价分别统计（`REQ-007`/`REQ-008`） |
| 退货金额 > 原单金额 | 拒绝该退货（`REQ-028`） |
| 同一笔退货重复提交 | 只冲减一次，不报错、不二次扣减（`REQ-013`） |
| 同一次支付回调重复送达 | 按支付单号幂等，不重复记账（`REQ-029`） |
| 离线补传的幂等键与已有交易重复 | 丢弃该条补传并写入审计日志，不报错阻断后续补传（`REQ-015`/`NFR-009`） |
| 单笔改价幅度 > 50% | 提示确认，仍允许继续（`REQ-007`） |
| 本地暂存达到告警阈值 | 提示摊主联系运维，**继续接受新交易**（`REQ-016`/`NFR-014`） |
| 本地暂存写入失败（磁盘空间不足） | 明确报错，且不得标记为已成功记账（`REQ-030`） |
| 最长离线时长 | ≤ 24 小时须完成补传，超时告警（`discovery.md` R4 Q2.3） |
| 顾客身份 | 系统不采集、不记录可识别顾客身份的信息；退货记录只含时间、金额、关联原单号、操作摊位 |
| 同一摊位多笔并发 | 交易号唯一、写入互不覆盖（`REQ-031`） |
| 摊主访问非本摊位数据 | 拒绝（`REQ-032`） |

## 6. Out-of-Scope

**以下 11 条均为具体功能排除（依据 `discovery.md` R0.3 与 R2 Q4.1）：**

1. 本系统**不**做外送服务。
2. 本系统**不**做顾客端历史价格折线图。
3. 本系统**不**做真实硬件对接与真实支付平台对接（秤与支付均为 Mock）。
4. 本系统**不**做多市场多租户。
5. 本系统**不**做完整权限体系（不做 SSO、不做权限矩阵、不做岗位分离）。
6. 本系统**不**做 AI 图像识别自动识别商品（交易中一律人工选品）。
7. 本系统**不**做电子价签、摊位屏、大屏等**非秤类硬件**的对接。
8. 本系统**不**做发票开具与税务申报。
9. 本系统**不**做会员、积分、优惠券等营销体系。
10. 本系统**不**做商户贷款、授信、集采等金融与供应链业务（"银行付费"属方案论证内容，不在交付范围）。
11. 本系统**不**做顾客端独立 App / 小程序（顾客只在扫码页完成支付与信息查看）。

| `AC-005` | **Given** 系统已有交易与价目表数据，**When** 执行使用率指标导出，**Then** 导出结果**包含**「日均智能秤交易占比」与「价目表维护率」，且第三方可凭该结果判定达标与否。 | `(追溯:REQ-022)` |

| `AC-007` | **Given** 一笔交易进行中，**When** 摊主改价且幅度超过 50%，**Then** 系统提示确认后仍可继续，且记录中**同时存在原价与改后价、改价时间、操作摊位**。 | `(追溯:REQ-007)` |
| `AC-008` | **Given** 某摊位发生改价与抹零，**When** 查看该摊位信用档案与「标价一致率」，**Then** 改价**计入**、抹零**不计入**。 | `(追溯:REQ-008)` |
| `AC-009` | **Given** 一笔支付回调为失败或超时，**When** 摊主改记现金并完成收款，**Then** 系统中该笔**只有一条**交易记录、**只计一次**佣金。 | `(追溯:REQ-011, REQ-026)` |
| `AC-010` | **Given** 一笔已成功的支付，**When** 同一次回调被重复送达，**Then** 交易与佣金**不重复记账**。 | `(追溯:REQ-029)` |
| `AC-011` | **Given** 顾客扫开扫码页，**When** 查看页面任一字段，**Then** 每个字段都能指出其采集来源；不存在无来源的展示字段。 | `(追溯:REQ-023)` |
| `AC-012` | **Given** 系统完成若干笔含支付信息的交易，**When** 扫描全部接口请求体、响应体与持久化记录，**Then** **零命中**身份证号与银行卡号字段，且收款标识为脱敏值。 | `(追溯:REQ-024)` |
| `AC-013` | **Given** 一台未安装过本系统的机器且无外网，**When** 执行一条启动命令，**Then** 系统成功启动并已从本地种子文件导入商户档案、品类字典与价目表。 | `(追溯:REQ-025, REQ-001)` |
| `AC-014` | **Given** 品类字典中存在别名映射，**When** 摊主选取某别名完成一笔交易，**Then** 该笔交易与统计均归入**标准品类**。 | `(追溯:REQ-002)` |
| `AC-015` | **Given** 上一营业日已设置价目表，**When** 摊主执行「复制昨天价」，**Then** 价目表被复制且可逐条调整。 | `(追溯:REQ-003)` |
| `AC-016` | **Given** 一笔交易已加入一个商品，**When** 再加入第二个商品，**Then** 两个商品金额累加在**同一笔交易**内。 | `(追溯:REQ-006)` |
| `AC-017` | **Given** 摊主尝试计价，**When** 重量为 0 或超过 50 公斤，**Then** 计价被拒绝并提示；**When** 退货金额大于原单金额，**Then** 退货被拒绝。 | `(追溯:REQ-027, REQ-028)` |
| `AC-018` | **Given** 本地暂存已达到告警阈值，**When** 摊主继续完成新交易，**Then** 系统提示联系运维且**新交易仍被接受**，无任何一笔被丢弃。 | `(追溯:REQ-016)` |
| `AC-019` | **Given** 本地暂存写入失败，**When** 摊主完成一笔交易，**Then** 系统给出明确错误提示，且该笔**未被标记为已成功记账**。 | `(追溯:REQ-030)` |
| `AC-020` | **Given** 多个摊位同时提交交易，**When** 写入完成，**Then** 每笔交易均被完整保存、交易号唯一、**互不覆盖**。 | `(追溯:REQ-031)` |
